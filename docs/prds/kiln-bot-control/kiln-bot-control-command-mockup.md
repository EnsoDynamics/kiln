# Kiln bot control — command-line mockup

**Proposed interface, not implemented.** Read alongside the [PRD](kiln-bot-control-prd.md). These are text transcripts of what a bot would execute on the Mac and what Kiln would return. The person can speak naturally; the bot constructs the commands.

The examples use fictional records. Customer returns and its phase names come from Kiln's existing `src/test-support/sample-snapshots.ts`; Shipping labels is a second illustrative PRD. Paths under `/work/` are fictional absolute Mac paths; operation/session IDs are shortened for readability. Timestamps are UTC, as in repository documents; readable runtime output uses the caller's time zone and labels it. JSON never contains comments or terminal decoration.

## The everyday commands

The target is the **same PRD file or folder used with `kiln run`**. There is no new run-name system to learn.

```text
kiln status                              # list current and unfinished work
kiln status <PRD-path>                    # inspect one PRD
kiln logs <PRD-path>                      # recent output, small bounded page
kiln logs <PRD-path> --max-lines 20           # ask for fewer lines
kiln logs <PRD-path> --older-output-cursor <cursor>    # preceding page from the same session
kiln reply <PRD-path> --message-file <reply-file> # send the note and resume
kiln resume <PRD-path>                    # resume without a note
```

This overview shows command shapes. Changing commands also carry a status token and a command ID, shown in the complete examples below. These protect against acting on an old stop or repeating an instruction. Their meaning and source are explained next; the person does not invent either.

For readability in longer examples, these two **ordinary shell variables contain paths**, not Kiln identifiers:

```sh
returns_prd=/work/acme-shop/docs/prds/customer-returns
labels_prd=/work/acme-shipping/docs/prds/shipping-labels
```

An absolute path works from any directory. A relative path has the same meaning it has in `kiln run`: relative to the caller's directory. Quotes preserve paths containing spaces.

## What the arguments mean

A **status token** is a value Kiln returns with the status you just read. Sending it back means “act only if the relevant state is still the one I saw.” It is not reply text, a password, or a Claude session ID. If the stop changed, Kiln refuses rather than sending the reply somewhere else. The bot copies the token without interpreting it.

A **command ID** identifies one instruction from the person, such as “send this reply.” The bot generates it. If a connection breaks and the bot retries that same instruction, it reuses the same ID so Kiln does not send the reply twice. The bot generates a new ID for a different instruction. A **session ID** instead identifies the Claude or Codex conversation; Kiln supplies that separately.

| Argument | Meaning | Where its value comes from |
|---|---|---|
| `<PRD-path>` | Which PRD to inspect or control | The same file/folder used with `kiln run`, or the absolute path returned by status |
| `--message-file /tmp/kiln-reply.txt` | Read this file's contents as the reply message; no attachment is uploaded | The bot writes the person's reply into a temporary UTF-8 text file |
| `--message-from-stdin` | Read the reply message from the command's standard input; this flag takes no value | The bot supplies text directly through its command runner, or a quoted heredoc as shown below |
| `--expected-status-token status_labels_7` | Act only on the relevant state just inspected | Copy `status_token` from `kiln status <PRD-path> --json` |
| `--command-id cmd_labels_reply_1` | Identify this one instruction for safe retries; not a coding session | Generated by the bot; examples use readable IDs, real callers must use unique values |
| `--json` | Return structured data for the bot instead of formatted text | Optional output choice; it changes presentation, not behavior |

Reply requires exactly one message-input option. Other run-changing commands require the status token and command ID but have no message-input flag. Read-only commands need neither safety argument. Login has its own scope check, explained in its examples below.

## The main conversation

```text
Doug: How many Kilns are running, and what are they doing?

Bot: Two are open. Customer returns is working on phase 3,
     Returns dashboard; its last output was 18 seconds ago.
     Shipping labels needs you on phase 2, Carrier selection.
     It stopped at 12:54 UTC and asks which carrier to use.

Doug: What exactly did it ask?

Bot: “The requirements name both UPS and FedEx as the default.
     Which should I use for domestic shipments?”

Doug: Tell it UPS for domestic shipments and keep going.

Bot: Your reply was delivered to Shipping labels' stopped session.
     It has resumed phase 2. Customer returns is still working.
```

The bot learns these facts through the commands below, not by reading the web page.

## Send the reply and resume

Covers AC-ACT-02, 04 and 05; AC-CLI-02.

**You say:** “Tell Shipping labels: use UPS for domestic shipments, and continue with the phase.”

The bot first reads status to get `status_labels_7`, then supplies your words using **one** of these equivalent alternatives. Neither form attaches a file to Claude or Codex.

### Option A: the bot writes the reply into a temporary file

**The bot runs:**

```sh
cat > /tmp/kiln-reply.txt <<'KILN_MESSAGE'
Use UPS for domestic shipments. Continue with the phase.
KILN_MESSAGE

kiln reply "$labels_prd" \
  --message-file /tmp/kiln-reply.txt \
  --expected-status-token status_labels_7 \
  --command-id cmd_labels_reply_1 \
  --json
```

`--message-file` takes the path to the **reply's contents**. The quoted heredoc delimiter keeps the text literal; the file contains the message, not a path for Claude to open as an attachment.

### Option B: the bot supplies the reply directly, without a temporary file

**You say the same thing. The bot can instead run:**

```sh
kiln reply "$labels_prd" \
  --message-from-stdin \
  --expected-status-token status_labels_7 \
  --command-id cmd_labels_reply_1 \
  --json <<'KILN_MESSAGE'
Use UPS for domestic shipments. Continue with the phase.
KILN_MESSAGE
```

“Standard input” is text supplied directly to the running command. The bot normally provides it through its execution tool; the quoted heredoc above shows the equivalent terminal invocation. Choose one option, not both. Missing both message options, or supplying both, is an input error.

**Kiln returns for either alternative:**

```json
{
  "schema_version": "1",
  "ok": true,
  "prd_path": "/work/acme-shipping/docs/prds/shipping-labels",
  "command_id": "cmd_labels_reply_1",
  "operation": {
    "id": "op_reply_1",
    "state": "completed",
    "outcome": "session_resumed",
    "session_id": "sess_labels_2",
    "note_delivered": true
  },
  "run_state": "implementing"
}
```

`kiln resume` has no message and serves Resume or Resume now according to the current state; its complete example is below. If checks already pass, the outcome is `advanced_after_checks` with `note_delivered: false`. If the work is still starting, the initial operation state is `accepted`; query its receipt:

**You say:** “Did my reply get sent?”

**The bot runs:**

```console
$ kiln command-status "$labels_prd" --command-id cmd_labels_reply_1
Checked 2026-10-26 13:01:00 UTC
op_reply_1 · Completed · Session resumed · note delivered
```

`--command-id` here reuses the ID of the reply instruction whose outcome is being checked. It does not start another instruction.

Completed here means the requested action finished, not that phase 2 finished. Retrying the same command ID and inputs returns this receipt, even if the run has since advanced. Reusing that ID for different input is an error.

## Pause, continue and check work

Covers AC-ACT-03. These are independent examples, not a sequence. Before each changing command, the bot runs `kiln status "$returns_prd" --json` (or `"$labels_prd"` for Shipping labels), then copies the returned `status_token` into the shell variable `latest_status_token`. Each example's command ID is generated for that instruction. The reply-text flags are absent because none of these commands sends a message.

### Pause after this phase

**You say:** “Pause Customer returns after this phase.”

```sh
kiln pause "$returns_prd" \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_pause_1
```

**Result:** `op_pause_1 · Completed` — Pause requested; the current session continues.

### Cancel a pending pause

**You say:** “Actually, keep Customer returns going.”

```sh
kiln pause "$returns_prd" --cancel-pending-pause \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_cancel_pause_1
```

**Result:** `op_cancel_pause_1 · Completed` — Pending pause cancelled.

### Continue a paused run

**You say:** “Customer returns is paused; continue it.”

```sh
kiln continue "$returns_prd" \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_continue_1
```

**Result:** `op_continue_1 · Accepted` — The next eligible activity will start.

### Resume without a message

**You say:** “Resume Shipping labels without adding a message.”

```sh
kiln resume "$labels_prd" \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_resume_labels_1
```

**Result:** `op_resume_labels_1 · Completed` — Same stopped session resumed. If checks already pass, the receipt instead states that work advanced.

### Recheck work finished elsewhere

**You say:** “I finished the fix myself. Check Shipping labels again.”

```sh
kiln check-again "$labels_prd" \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_check_1
```

**Result:** `op_check_1 · Completed` — Completion checks failed; still Needs you. Failed checks follow. Passing checks instead report whether work advanced.

### Change automatic usage recovery

**You say:** “Do not resume Shipping labels automatically when usage resets.”

```sh
kiln settings "$labels_prd" --resume-after-usage-limit off \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_auto_resume_1
```

**Result:** `op_auto_resume_1 · Completed` — Resume after a usage limit: off. `on` enables it instead.

### Change keep-awake

**You say:** “Keep the Mac awake while Customer returns works.”

```sh
kiln settings "$returns_prd" --keep-awake on \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_awake_1
```

**Result:** `op_awake_1 · Completed` — Keep awake: on. `off` disables it instead.

### Confirm outside-workspace work was handled

**You say:** “I dealt with the changes outside Shipping labels’ workspace. Record that.”

```sh
kiln outside-confirmation "$labels_prd" --confirm-resolved \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_confirm_1
```

**Result:** `op_confirm_1 · Completed` — Confirmation recorded for the facts reviewed; no session starts.

### Clear that confirmation

**You say:** “Clear my outside-workspace confirmation for Shipping labels.”

```sh
kiln outside-confirmation "$labels_prd" --clear-confirmation \
  --expected-status-token "$latest_status_token" \
  --command-id cmd_clear_confirmation_1
```

**Result:** `op_clear_confirmation_1 · Completed` — Confirmation cleared; no session starts.

`--cancel-pending-pause` cancels the pause request without interrupting current work. `--confirm-resolved` records the person's explicit outside-workspace confirmation; `--clear-confirmation` removes it. They are mutually exclusive within their respective command choices. Unavailable controls return a refused operation and its reason, with no effect.

**You say:** “What are Shipping labels' runtime settings?”

```sh
kiln settings "$labels_prd"
```

With no setting flag, this only reads current settings; no status token or command ID is required. `--resume-after-usage-limit` and `--keep-awake` accept `on` or `off`. Check again can advance work, so it requires the same safeguards as other changing commands.

## Read a small tail of recent output

Covers AC-SEE-06. Logs are **not the full transcript**. With no options, Kiln reads the active session, otherwise the most recent saved session, and returns its newest 50 lines at most. The entire stdout response is capped at **16 KiB**, including headers or JSON metadata and escaping. The defaults are proposed in OUTPUT-001.

**You say:** “What has Customer returns been doing most recently?”

**The bot runs:**

```console
$ kiln logs "$returns_prd"
Checked 2026-10-26 13:00:06 UTC
Customer returns · phase 3 · session sess_returns_3
Latest 50 lines · range 201–250 · older output available
[The 50 actual output lines, in oldest-to-newest order.]
Earlier: kiln logs /work/acme-shop/docs/prds/customer-returns --older-output-cursor page_returns_200
```

The bracketed line above stands for content in this mockup, not a product omission. A short explicit request is shown in full.

**You say:** “Just show me the last two lines from Customer returns.”

**The bot runs:**

```console
$ kiln logs "$returns_prd" --max-lines 2 --json
```

```json
{
  "schema_version": "1",
  "ok": true,
  "observed_at": "2026-10-26T13:00:06Z",
  "prd_path": "/work/acme-shop/docs/prds/customer-returns",
  "session_id": "sess_returns_3",
  "snapshot_end_line": 250,
  "requested_lines": 2,
  "response_byte_limit": 16384,
  "byte_limit_reached": false,
  "lines": [
    {"number": 249, "at": "2026-10-26T12:59:40Z", "text": "Dashboard changes saved.", "fragment": null},
    {"number": 250, "at": "2026-10-26T12:59:42Z", "text": "Running the returns dashboard integration checks.", "fragment": null}
  ],
  "has_older": true,
  "next_before": "page_returns_248",
  "next_command": "kiln logs /work/acme-shop/docs/prds/customer-returns --older-output-cursor page_returns_248 --max-lines 2 --json"
}
```

**You say:** “What came immediately before those two lines?”

**The bot runs:**

```console
$ kiln logs "$returns_prd" --older-output-cursor page_returns_248 --max-lines 2
Checked 2026-10-26 13:01:00 UTC
Customer returns · session sess_returns_3 · snapshot through line 250
Earlier page · range 247–248 · older output available
247  2026-10-26 12:59:36 UTC  Updating dashboard filters.
248  2026-10-26 12:59:38 UTC  Saving dashboard changes.
Earlier: kiln logs /work/acme-shop/docs/prds/customer-returns --older-output-cursor page_returns_246 --max-lines 2
```

The cursor fixes the execution, session and snapshot. If Kiln has since started phase 4, this page still reads phase 3. It never silently switches to phase 4. A fresh `kiln logs "$returns_prd"` reads the latest tail again.

`--max-lines` is an upper bound on the number of output lines, not a way to bypass the response-size cap. `--older-output-cursor` takes the opaque value returned as `next_before`; copy it unchanged, rather than supplying a date or line number.

**You say:** “Show the last 100 lines from Customer returns' earlier phase-2 session.”

```sh
kiln logs "$returns_prd" --session-id sess_returns_2 --max-lines 100
```

`--session-id` chooses a saved coding conversation, using the ID from `kiln status "$returns_prd" --detail full`. This is the session identifier; `--command-id` is unrelated. Omit `--session-id` to use the active session, otherwise the most recent saved session.

| Condition | Result |
|---|---|
| Requested lines do not fit | Fewer recent lines, `byte_limit_reached: true`, and an earlier-page cursor |
| One line exceeds the response budget | The newest fragment fits; it is explicitly marked as a fragment with its position in the line. The earlier-page cursor retrieves the preceding fragment. Text is not silently truncated. |
| No session or no output yet | Successful empty result, with the reason and no earlier-page cursor |
| Reached the beginning | `has_older: false`, `next_before: null`, `next_command: null` |
| Cursor is invalid or belongs to another PRD/session | Error, exit 2; no other session is substituted |
| Saved output has been removed or cannot be read | Explicit unavailable result, exit 4; no empty-success result |

`--max-lines` accepts 1–200. Larger, zero or negative values are errors, not unlimited requests. Every page stays within the byte cap in text and JSON modes, including errors. There is no follow mode or whole-log dump. To read everything, the caller must explicitly request successive bounded pages; the bot should stop once it has enough context to answer the person.

**You say:** “Before switching accounts, which other Kilns would that affect?”

Checked 2026-10-26 14:00:01 UTC

|---|---|

**You say:** “Cancel that pending account switch.”

```console
$ kiln account login cancel --login-operation-id op_login_1 --command-id cmd_cancel_login_1
op_login_1 · Cancelled. Login cancelled; affected runs remain held.
```

`--login-operation-id` selects the same login, while the new `--command-id` identifies the cancellation instruction. Complete and cancel act only on that operation's original login scope. Kiln rejects a new completion/cancellation request when ownership or current eligibility fails; it never selects another login. Status explicitly reports `expired`, `cancelled`, `failed`, `account_mismatch`, or `local_interaction_required` when applicable; it never calls those success. A request for alternate@example.invalid that verifies primary@example.invalid is `account_mismatch`; neither run resumes. Subsequent commands use the freshly observed account state.

## Command and result conventions

These proposed conventions make the examples reviewable; the technical design supplies the complete field schema. Internal execution identity protects against reuse of the same PRD path for different work, but is not a second public selector.

- **“What can I ask Kiln to do?”** maps to `kiln --help`; **“How do I send a reply?”** maps to `kiln reply --help`. Help describes inputs and output fields; all commands support `--json`.
- Reads return facts only. Changing commands return operation receipts. Run controls target a PRD path and status token; beginning login targets a PRD path and login-scope token. Login completion/cancellation target the existing operation, with its ownership and current eligibility checked under AC-ACT-04.
- A run status token changes when relevant controls or their target change, not whenever another output line arrives. The login-scope token changes when the affected runs or their eligibility change.
- Operation lookup uses a PRD path and command ID for ordinary controls or a login operation ID for login. A replay is checked before applying the old status token, so a successfully completed request can return its old receipt.
- Login status is the explicit place to retrieve still-valid authorization instructions. Ordinary operation receipts, output and logs omit transient login secrets.

| Exit | Meaning |
|---|---|
| `0` | Read succeeded, or changing request accepted; inspect operation state for completion |
| `2` | Invalid input, unresolved PRD path, invalid cursor, or command ID reused with different inputs |
| `3` | State, authorization or account conflict; no requested change accepted |
| `4` | Incomplete inventory, unavailable controller/provider, incompatible instance, or indeterminate operation result |

Querying an operation successfully returns `0` even if its recorded outcome is failure. JSON always names that outcome explicitly. A login awaiting the person is an accepted operation, not a blocked terminal process.
