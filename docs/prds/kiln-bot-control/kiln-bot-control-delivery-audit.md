## Confirmed gap and conflict check

**AC-ACCOUNT-01 — Last-attempt account and plan.** `src/control/projection.ts::accountFacts` chooses the latest saved session/run but falls back to `record.billing.lastLaunch` for public last-attempt identity/plan. A first Claude launch reaches `Engine.runProcess` without a separate account argument (`src/engine/engine.ts`, `launchSession` call); `src/session/claude-session.ts::runSessionProcess` saves its actual launch billing in `SessionRun.billing`. On a later resume with a changed account, `Engine.runProcess` saves the new inspection as execution-level `lastLaunch` before the durable dispatch checkpoint and before a new run is appended. If that checkpoint fails, the command is blocked as uncertain, the old attempt remains the last actual attempt, and `kiln account` or full status labels it with the new prelaunch identity/plan. Its reliable per-attempt billing remains on disk. This is an incorrect observable account fact, not a missing duplicate of otherwise correct data.

**AC-SEE-03 — Account observation time.** When the actual last Claude run already has `run.account`, the same projection prioritizes that identity but still takes `observed_at` from the later execution-level last-launch reading. Account A can appear freshly observed at account B’s later prelaunch time. Independently read facts no longer retain their own observation time. The same provenance repair completes both criteria; no new capability or business decision is needed.

The requirement is to report correlated attempt facts, with explicit unavailable provenance when absent, rather than infer from a nearby or intended account. The design’s Account and Usage Facts section already requires that separation. The billing-safeguards PRD’s AC-RUN-05 likewise requires the account recorded at the current or most recent actual launch; browser parity does not authorize misleading provenance. Source history and governing documents contain no later-built criterion replacing these obligations, and no coherent intentional alternative was found. Both rows are gaps, not Changed outside the requirements. No new business assumption is needed.
