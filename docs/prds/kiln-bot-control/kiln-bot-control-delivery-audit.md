## Confirmed gaps and conflict check

**Usage observation freshness and account binding — AC-SEE-03 and AC-ACCOUNT-01.** `src/agents/metadata.ts::AgentInfo.refreshClaudeForLaunch` performs required auth/model/skill readiness, then spreads the previous account and auth response while explicitly retaining `state.account?.limits` and replacing `updatedAt`. No usage read occurs there. Even with the same account and no concurrency, old gauges acquire the auth-only timestamp. A changed identity can inherit the previous identity's gauges. `Engine`'s billing inspector calls this method; startup `refreshBilling`, explicit account refresh and ordinary launch can reach it. `buildSnapshot` forwards `metadata.account`; `accountFacts` uses `account.updatedAt` for the public usage observation and reports it current without a stale/error marker. Retained cache can preserve the wrong date. Optional usage and required auth readiness may remain separate; reporting must retain the usage reading's own date, availability and account binding. Phase 5's selected saved-attempt billing/Codex provenance is correctly correlated and must remain intact.

**Default logs with unavailable history — AC-SEE-06.** `readHistory` records missing/corrupt/unowned session errors and omits those records from readable sessions. The live logs route discards those errors. `chooseSession` falls back from an unavailable preferred session to the newest readable record; both live and retained paths can silently return older work. With none readable, the live route calls `outputPage(null)`, producing successful `no_session`. The retained client's `!history.complete && !selected` guard does not stop older-session substitution. These are incorrect default target/availability results, distinct from genuine no-session/no-output. Valid explicit selection and frozen cursor paging should remain available when their identities can independently be established.

**Complete helper help — AC-ACT-01.** Packaged `audit snapshot/submit` and `delivery assess/prepare/evidence` contracts say the JSON-file follows an existing contract, without exposing that contract. `commandHelp` emits only those fields; it supplies no schema or discoverable reference. Audit validators require execution/activity/revision and action-specific arrays/report paths. Delivery validators require owner/digest/criteria/requirements and action-specific evidence inputs. Status helpers provide some current values, but no request schema. Help cannot construct a valid call from those values alone. The generic “existing helper-specific errors” placeholder likewise supplies no useful meanings. Completing these references changes discoverability, not the legacy execution formats/exits or authority.

The reverse conflict check found no later-built criterion replacing these obligations and no intentional alternative authorizing the omissions. Billing's required-auth/optional-usage separation does not authorize replacing usage observation dates or account identity. Live-session-control's existing partial supersession changes pause wording/ownership; its later bot command phase is unbuilt at this baseline and does not change logs, account freshness or helper-help completeness. Source history attributes the log selection/help omissions to the original bot-control implementation; the billing readiness assignment predates this repair and never records a choice to misdate usage. These are missing/incorrect promised behaviors, not Changed outside the requirements. No new business assumption or supersession pointer is needed.
