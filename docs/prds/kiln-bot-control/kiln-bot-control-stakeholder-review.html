Kiln control while away from the Mac

Ask a bot what Kiln is doing and keep existing work moving while away from the computer.

01 / SECTION

Find current work and see what needs attention

One question finds work across repositories. The answer separates live work, saved unfinished work and information that may be out of date.

Key acceptance criteria & mockups

  • From any directory, list this operating-system user’s live controllers and saved unfinished executions. Count live controllers separately from working sessions and stopped unfinished work. Include paused, waiting, Needs you and completed-but-open instances; omit completed executions once their controller closes, while retained details remain available by PRD path. There is no age cutoff or all-history listing. AC-SEE-01
  • Show the PRD, repositories, current phase or audit/delivery activity, completed/total phase counts, agent/model, start and latest-activity times, pauses, usage waits and completion/PR links. A quiet session shows its last activity; silence alone does not mean healthy or stuck. AC-SEE-01–02
  • Date the answer and independently read facts. Unreachable or unreadable records make the inventory visibly incomplete; a disconnected controller exposes dated last-known facts and no executable controls. Failure to reach the Mac does not mean zero instances. AC-SEE-01–03
  • Retrieve the complete stop message, failed checks, human requests and recovery choices. Missing messages are explicit; any shortened summary has a way to obtain the full text. Use the same PRD file or directory path as kiln run, including absolute paths and paths with spaces. AC-SEE-04, AC-SEE-07 · AC-CLI-02
  • Inspect account/plan facts for the current or last attempt separately from the currently authenticated account for the next attempt. Show provider-reported usage windows, resets, freshness and recovery permission or uncertainty; unknown identity or usage is explicit. Existing billing safeguards remain authoritative. AC-ACCOUNT-01

Which commands and help should the first release expose?

Cover runs already started: inspect status/output, reply and resume, request/cancel pause, continue, verify finished phases and recheck other recovery states, change keep-awake and automatic usage recovery, and confirm outside-workspace handling.

New-run setup and new spending/deployment authority stay in the browser. The new bot-control commands provide readable text, structured JSON and the documented result/exit contract.

Every existing and new command gets discoverable help in text and JSON. Existing run, add-repository, audit and delivery keep their execution output formats and exit statuses.

Choose Change to specify any controls to add or exclude, or a different help/output boundary.

Why this is proposed

Doug said “once I have it started” and narrowed “anything” to the main actions that keep work moving. The older idea mentions every browser action, but the current request favors this bounded workflow. Including initial setup would add document selection and authority choices the errands example does not need. The current helpers already have distinct execution contracts: audit and delivery emit JSON with their existing success/failure exits, while add-repository emits readable text. Extending their help makes them discoverable without changing how existing callers execute them.

02 / SECTION

Reply, resume or accept finished work deliberately

The person chooses whether to answer, let Kiln continue unfinished work, or verify that a phase is finished. Each action keeps that intention through delays, retries and restarts.

Key acceptance criteria & mockups

  • Reply supplies nonempty literal UTF-8 message text from a file or standard input, never a file attachment. For unfinished work, deliver the reply to the same saved conversation before resuming. No-message Resume keeps terminal discussion/history and requires the person to exit their terminal agent session first; an open phase or uncommitted/unpushed work alone does not prevent it. No special handoff phrase or requirements edit is required. AC-ACT-02
  • If a manual phase reply or resume finds the phase already complete, return phase_already_complete without resuming or advancing. Preserve any unsent reply in its receipt, marked not sent, for the receipt’s lifetime; offer a separate explicit advance choice and never send that reply to later work. AC-ACT-02
  • Verify and advance freshly checks every applicable completion requirement and advances only when all pass, honoring pauses and existing authority. It does not finish, commit or push work to pass checks. Advancing with an unsent reply requires explicit --without-sending-reply acknowledgement. Failed or unreadable evidence leaves the phase stopped with fresh results or an explicit error and honestly dated previous results. Usage waits and other dedicated recovery states keep their own behavior. AC-ACT-02
  • A late command uses the PRD path and a Kiln-supplied status token tied to the relevant execution and stop. A later question in the same conversation has a different token; ordinary new logs do not change it. Stale or ineligible instructions are refused with a way to refresh. A command ID identifies one instruction: retrying the same ID and inputs returns its receipt before checking eligibility, without repeating effects; different inputs with the same ID are refused. AC-ACT-04
  • Acceptance is separate from completion. The caller can query the operation’s progress/outcome/refusal after disconnects or restarts, until saved run history is removed. An uncertain result stays unknown until reconciled; competing browser, bot and automatic actions cannot duplicate work or misdirect a reply. Existing workspace, authentication, billing and delivery checks still apply. AC-ACT-04–05
  • A pause request lets current work continue to the normal pause boundary. Cancelling only withdraws a pending pause; Continue resumes an already paused run. Outside-workspace confirmation applies only to the browser’s reviewed evidence and neither fixes files, proves completion, resumes nor advances work. AC-ACT-03
  • For any started phase of this execution, retrieve all recorded Claude/Codex conversations, including earlier completed phases and replaced/failed sessions, with separate Kiln selectors and provider IDs. Missing records/history are explicit. Handoff returns provider-specific resume instructions and the working directory without executing them; an active Kiln conversation is reported as active. AC-SEE-05, AC-SEE-08
  • Provider sign-in/account switching, new billing or delivery authority, new-run configuration, merging/releasing, notifications and keeping an offline Mac reachable are outside this feature. Returned session text is data; bot instructions come from the person and structured controls. Out of Scope · AC-CLI-03

03 / SECTION

Read a small amount of output, then ask for more

Read recent saved output to understand progress. Older pages stay tied to the conversation and snapshot originally selected.

Key acceptance criteria & mockups

  • Logs use the active session, otherwise the most recent saved session; an explicit session selector can choose an earlier one. Each page is chronological and identifies its session, observation time, range, older-output availability and exact next-page invocation. AC-SEE-06
  • An older-output cursor stays within that execution/session and snapshot even if the run advances. Oversized entries return marked fragments without changing their text; older paging retrieves the omitted prefix. No output, end of history, invalid/mismatched cursor and unavailable saved output are distinct. A fresh unpaged request fetches the newest tail; there is no streaming or whole-log dump. AC-SEE-06

OUTPUT-001Confidence: 80%Unanswered

Should logs count saved entries, and how much should one request return?

Default to the latest 50 saved numbered output entries. The public word “line” and --max-lines count one such entry, which can contain several lines of text.

Keep a hard 16 KiB (16,384 UTF-8 bytes) cap on the entire stdout response, including headers or JSON metadata and escaping. Allow an explicit request for up to 200 entries, still within that byte cap; fetch older output through separate pages.

An entry too large to fit is returned in marked fragments without losing content. One saved assistant message containing three paragraphs counts as one entry, even when its text contains several newlines.

Choose Change to specify a different counting unit, default or cap.

Why this is proposed

Doug requested a small response from the most recent logs and warned that a whole log would be too large. Kiln already saves whole assistant and tool blocks as individually numbered entries (src/session/session-output.ts, SessionOutputReader.readEvent); their text can contain newlines. Counting those entries keeps their existing identity and paging boundaries, while the byte cap bounds the actual response size. Counting every newline separately would change that unit and split saved messages. The proposed counts and byte cap were not specified by Doug; they balance nearby context against filling the bot's conversation with output.
