Kiln v1

Kiln runs the implementation half of the Enso Method without a person in the loop: it implements a refined PRD’s phases one at a time in unattended Claude Code sessions, checks in Git that each landed, and finishes with one pull request ready for human review. When a phase doesn’t land, it stops and hands that exact session back to the person.

This review covers the whole of Kiln v1: starting, running, pausing, stopping, interruptions and the final pull request, on macOS and Linux with GitHub-hosted repositories. Ideas for later versions are kept in a separate document and are not part of this release. All screens use fictional sample data.

For business review. Selected acceptance criteria and all 13 open assumptions. Implementation must use the full PRD and technical design. This is a dated snapshot; source links open the current documents.

01 / SECTION

Point Kiln at a refined PRD and start

The person runs one command, kiln run, with the path to one PRD. Kiln checks the documents in the terminal, then opens a browser screen, Documents found, showing what it found and how it will deliver the feature. Nothing is implemented until the person confirms the documents were refined and presses Start.

Key acceptance criteria & mockups

  • kiln run <path to one PRD> is the only way in, the first time and every time after. Kiln has no other commands: no status, logs, pause or single-phase command. AC-START-01 · AC-CLI-01 · AC-CLI-02
  • Missing or broken documents (no PRD, technical design or phase documents; a phase citing no acceptance criteria; a phase depending on a later one; uncommitted changes in the checkout) stop Kiln in the terminal, saying what and where it looked. The browser never opens and nothing starts. AC-START-02
  • Unconfirmed assumptions are counted on Documents found as information only. Nothing Kiln does waits on stakeholder answers. Business context · AC-START-04
  • Kiln can’t tell from the files whether the documents were refined, so Start stays unavailable until the person confirms they were. AC-START-05
  • One new feature branch and one worktree for the whole PRD, created from the base branch before the first phase. Defaults: feature/<PRD folder>, a worktree beside the repository, and develop as base (or the default branch when there is no develop). These three are fixed once the first phase starts. AC-START-07 · AC-VIEW-08
  • Next to Start, the person sees what Kiln may do (commit and push to the feature branch; open one pull request into the base branch) and may not do (merge, deploy anywhere, touch other branches). AC-START-08
  • In v1 the agent is always Claude Code, pushes happen after every phase, and Kiln always stops at “PR ready for review”. Settings chosen at Start are remembered for the PRD. AC-START-06
  • Kiln installs from npm with one command, runs on macOS and Linux only (no Windows in v1), supports GitHub-hosted repositories only, and has no account, server or cloud service of its own. AC-INSTALL-01 · AC-INSTALL-02 · AC-INSTALL-03 · Depends on

UI-004Affects how fast plan limits are usedUnanswered

Does a new PRD start on the latest Opus at high effort?

On Documents found, Model starts at the latest Opus and Effort at high, for every PRD, whatever Claude Code itself would use on that machine. The person can change both before Start.

The Model list offers the models Claude Code offers the signed-in account.

Trade-off: a strong default suits phases that run for hours unattended and must pass review and test hardening, but it uses plan limits faster (visible in the usage panel).

Alternative considered: start from the model and effort Claude Code already uses on that machine, so Kiln matches the person’s own setup. It lost because that setup is often tuned for interactive work, and the mockup draws Opus at high.

Why this is proposed

The mockup preselects Opus and High but can’t say whether that is a fixed default or the machine’s own setting. The architecture proposal names only the --model and --effort flags, with no default.

02 / SECTION

Let it run, and watch

After Start, Kiln implements the phases one at a time, each in a fresh unattended Claude Code session, and checks in Git that each one landed before starting the next. The person can watch progress, the live session output and the Claude account’s usage, and can change the model and effort for later phases, without interrupting anything.

Key acceptance criteria & mockups

  • Phases run in plan order, one at a time, each in a new unattended Claude Code session with the PRD’s model and effort. A phase that splits itself is followed with no action from the person. AC-RUN-01 · AC-RUN-02 · AC-RUN-04
  • Each session gets the authorization a person would give: implement this phase with the Enso Method skills, work only in the PRD’s worktree and branch, commit and push, and open no pull request, merge nothing, deploy nothing, touch no other branch. AC-RUN-03 · AC-RUN-06
  • A session never waits for an answer. Anything that would ask is refused; a session that needs to ask a question ends, and its question is shown to the person at Needs you. AC-RUN-05
  • A phase is Done only when three checks pass in Git and the phase document: the phase is marked Closed, everything is committed, and everything is pushed. What the session claimed, or how it exited, doesn’t count either way. No AI model judges or explains how a session ended. AC-DONE-01 · AC-DONE-02 · AC-DONE-04
  • Progress is display only. Kiln shows six steps per phase (Build, Deliverable review, Test hardening, Commit, Refactor pass, Push) as it sees them happen, and never claims on its own that an acceptance criterion is met or tested. AC-WATCH-04 · AC-WATCH-11
  • The Claude account panel shows each usage limit’s percent used and reset time, refreshed every 5 minutes and before each phase, without spending usage. A nearly-used limit turns amber and suggests switching accounts. AC-WATCH-08 · AC-WATCH-09
  • Model and effort can change while Kiln works or is paused; a change applies from the next session. Keep-awake can be switched at any time and applies at once. AC-VIEW-08
  • While a session works, Kiln stops the computer sleeping when idle (on by default). Wherever keep-awake is shown, Kiln says closing the lid can still sleep the computer. AC-KEEP-06 · AC-KEEP-07

UI-005Overnight work can stop at a usage limit until someone returnsUnanswered

Does Kiln wait for a usage limit to reset?

No. Kiln starts the next phase on whichever account is signed in, even when a limit is at 100%. A session that runs into a limit is handled like any other stop: if the phase fails the done check, it goes to Needs you showing how the session ended, word for word.

The person then switches accounts with claude auth login, or waits for the reset, and finishes the phase as for any other stop.

Example: the 5-hour window is at 82%, resetting in 1h 12m. If phase 3 reached 100% partway through, phase 3 would go to Needs you; Kiln would not hold it until the reset.

Alternative considered: wait for the reset before starting the next phase when the pre-phase check shows a limit at 100%. Its real advantage is overnight work, which would carry on after the reset instead of sitting at Needs you until morning. It lost because it adds a state and screen copy no mockup shows, and covers only the start of a phase, not a limit reached mid-session.

Why this is proposed

Neither the architecture proposal nor the after-v1 ideas mention waiting for a reset. The PRD’s own rules lead here: Kiln doesn’t rerun a stopped phase and never resumes a session that ended on its own, and the mockups’ answer to a nearly-used limit is to switch accounts. No mockup draws a waiting state.

Does Change edit the model and effort in place, saving each choice at once?

PLAT-001Screen wording is not exact on some Linux desktopsUnanswered

On Linux desktops other than GNOME, is it acceptable that keep-awake also blocks a sleep the person asks for?

Yes. On Linux desktops other than GNOME with systemd 257 or newer, while a session works, keep-awake also refuses a sleep the person chooses from the menu. Closing the lid still sleeps the computer, and sleep works again once the feature reaches Needs you, pauses or completes.

The screens keep the drawn wording, “Stops idle sleep only”, which is exact on macOS and GNOME but not on those other Linux desktops.

Example: on a KDE laptop with a recent Linux release, choosing Sleep from the menu while a phase runs leaves the computer awake. On Ubuntu’s standard GNOME desktop, it sleeps at once.

Alternative considered: qualify AC-KEEP-07 for Linux in the PRD and on the screens, saying that outside GNOME a menu sleep is also blocked. It lost because it adds platform-specific copy to every screen showing keep-awake, for a case that affects only some Linux desktops and is easy to get around.

Why this is proposed

On those desktops, the only hold their automatic sleep respects is one the system also applies to a sleep the person asks for; recent systemd versions stopped exempting the person’s own requests. No other mechanism stops automatic sleep without also blocking a requested one. GNOME has its own idle-only hold, which Kiln uses there.

Source confidence: 70% (impact if wrong: low)

Pause between phases

The person can ask Kiln to pause after the current phase, for example to switch Claude accounts near a usage limit. The current session finishes its work, including commit and push, and then Kiln starts nothing until the person presses Start.

UI-008Unanswered

Does a pause pressed during the last phase hold before the pull-request session?

Yes. A pause pressed during the last phase holds before the pull-request session, as before any other phase: Kiln shows Paused, and the pull-request session starts only when the person presses Start the pull request.

The pause is dropped only when the pull request is already open, because then nothing would start and Kiln completes.

Example: had the person pressed Pause during phase 4, the sample feature’s last phase, Paused would read “Paused after phase 4 · Next: the pull request”, with “5 of 5 phases done” and a Start the pull request button.

Alternative considered: drop the pause and open the pull request straight away, since that session is short. It lost because the person asked Kiln not to start anything, and nothing on screen would say Kiln started anyway.

Why this is proposed

A pause holds every start until Start is pressed, and the pull-request session is handled as one last phase. The usual reason to pause, switching accounts near a usage limit, applies to the pull-request session too. Dropping the pause would silently ignore a request the person can’t take back (UI-002).

04 / SECTION

When a phase doesn’t land: Needs you

When a phase fails the done check, Kiln stops and hands that exact session back with what it said last, which checks failed, and a command to reopen it. The person finishes the phase any way they like, then presses Check again and Kiln carries on.

Key acceptance criteria & mockups

  • Kiln stops and doesn’t retry: no later phase starts and the phase isn’t rerun on its own. AC-STOP-01
  • The screen shows how the session ended, word for word: its last message, exit code and stop time, last skill seen, and its last lines of output when there was no final message. It shows each of the three checks with the fact behind it, e.g. “12 files changed, not committed”. AC-STOP-02 · AC-STOP-03
  • Kiln never guesses a cause or invents a question. Anything said about why a phase stopped is the session’s own words, quoted. AC-STOP-04
  • The person gets a copyable command to reopen the exact session with its history, and a fresh-session prompt for when it can’t be reopened. AC-STOP-05 · AC-STOP-06
  • The phase can be finished any way that leaves the work in the worktree. Check again runs the done check; when it passes, the phase shows Done, “finished by you”, and the next phase starts unless a pause is waiting. Nothing starts until the person presses Check again or runs kiln run. AC-STOP-07 · AC-STOP-08 · AC-RUN-07
  • Kiln never resets, stashes, cleans, force-pushes or deletes branches. Uncommitted work left after a stop stays until the person resolves it. Kiln adds no files or commits of its own to the repository. AC-GIT-01 · AC-GIT-02 · AC-GIT-03

05 / SECTION

Interruptions and picking back up

Kiln runs in the terminal it was started from, with no background service. If it is interrupted by Ctrl+C, a closed terminal, a restart or a sleeping laptop, nothing is lost: the browser says plainly that Kiln is disconnected, and running the same kiln run command picks the work back up.

Key acceptance criteria & mockups

  • Kiln stays in its terminal until Ctrl+C or the terminal is closed, and installs no background service. Closing the browser has no effect. AC-KEEP-01
  • Interrupted work is never thrown away. On the next kiln run, Kiln first runs the done check; if it passes the phase is Done, otherwise Kiln resumes that same session with its full history. A session that can’t be resumed comes to the person at Needs you. AC-KEEP-02 · AC-KEEP-03 · AC-KEEP-04 · AC-KEEP-05
  • Every screen shows whether it is connected. When Kiln has stopped, the view says it is disconnected, that nothing is running, and that kiln run picks up where it left off. AC-VIEW-07
  • Several PRDs can run at once, each from its own kiln run with its own browser address, worktree and branch. A second kiln run for the same PRD says it is already running and starts nothing. AC-MULTI-01 · AC-MULTI-02 · AC-MULTI-03 · AC-MULTI-04
  • The browser view is reachable only from the same machine, and other web pages can’t read or control it. AC-VIEW-01 · AC-VIEW-06

06 / SECTION

Finish with one pull request

When every phase is closed, Kiln starts one last session to open a single pull request for the whole feature into the base branch, and stops there, ready for human review. It never merges or deploys.

Key acceptance criteria & mockups

  • Once every phase is closed, a final session opens one pull request from the feature branch into the base branch (or Kiln completes at once if one is already open). That session may not merge or touch other branches. AC-PR-01
  • Kiln confirms the pull request is open; when it isn’t, Kiln goes to Needs you. AC-PR-02
  • Kiln stops at “PR ready for review”: it doesn’t merge, wait on CI to merge, or deploy anything. AC-PR-03
  • Complete shows the pull request’s number, title, branches, link, commit count and lines changed, every phase Done, and the worktree, which Kiln keeps until the person removes it. AC-PR-04 · AC-GIT-04
  • The pull-request session is shown as one more phase, numbered “PR” and titled “Final pull request”, but isn’t counted in “5 of 5 phases done” and has no progress steps. AC-PR-05

WORK-001Teams that open drafts by habit will stop at Needs youUnanswered

Does a draft pull request count as open?

No. “Open” means open and ready for review, so a draft pull request fails Kiln’s check.

The pull-request session opens its pull request ready for review; if a draft from the feature branch is already open, it marks that one ready instead of opening another.

If the check still finds a draft, Kiln goes to Needs you with “#<n> is a draft”. The person marks it Ready for review on GitHub, then presses Check again.

Alternative considered: count a draft as open, so someone who prefers drafts still reaches Complete. It lost because Complete would then say review is next when nobody has been asked to review.

Why this is proposed

Kiln stops at “PR ready for review”, GitHub’s own term for a pull request that isn’t a draft, and Complete says “Human review is next.” A draft can’t be merged and doesn’t ask code owners for review, so a feature left as a draft would sit unseen. No Enso Method skill opens drafts, and GitHub’s command-line tool doesn’t by default; a draft would come from the person’s own instructions to Claude Code.

2. Full session output for a stopped phase: the step where the session stopped keeps the current-step drawing without the spinner, and the back link reads “Needs you” (not “All phases”), returning to the Needs you screen.

Customer returns is complete.” · On Documents found: “Kiln stopped. Nothing was started.” · During setup: “Kiln stopped before phase 1 started. kiln run picks it back up.”

5. kiln run on a feature already underway prints a summary line, e.g. “Customer returns · 2 of 5 phases done · phase 2b was interrupted”, ending in “phase 2b was interrupted”, “phase 2b needs you”, “paused before phase 3”, “phase 3 is next” or “complete”. Then a ● line with what Kiln does next, followed by “Opened <address>”: “Starting phase 3, Returns dashboard.” · “Resuming phase 2b’s session 7c1e9f2a.” (drawn) · “Resuming the pull-request session 7c1e9f2a.” · “Starting the pull-request session.” · “Phase 2b needs you.” (“still needs you” when its check failed again) · “The pull request needs you.” · “Phase 3 hasn’t started: the phase plan doesn’t read.” · “Paused before phase 3. Press Start phase 3 to go on.” · “Paused before the pull request. 6. During the pull-request session, copy that offers a pause or names a phase changes: Running’s near-limit note reads “Close to the limit.” alone; the Kiln panel reads “interrupts the pull-request session”; Ctrl+C at Needs you for the pull request prints “Kiln stopped. 7. When Claude Code isn’t signed in, one amber line replaces the email and plan: “Not signed in to Claude Code. Run claude auth login.” On Documents found the usage line is left out. Start isn’t held by it; a session that then fails comes to Needs you like any other stop.

8. A time that isn’t today carries its day, everywhere Kiln shows a time on screen (not in the terminal): “Yesterday 11:52 PM” (lowercase after a word: “Stopped yesterday 11:52 PM”); within the last week “Mon 9:17 AM”; earlier “Oct 12, 9:17 AM”. In “Ran … to …” a shared day is given once: “Yesterday 11:20 PM to 12:40 AM”. Today’s times stay as drawn.

9. Field messages on Documents found, each one amber line that holds Start: “Enter a worktree path.” · “Enter a branch name.” · “That isn’t a valid branch name.” · “Choose a base branch.” (when origin names no default branch and has no develop).

10. When a start check fails for a reason other than missing documents, the terminal keeps the drawn frame: amber ✗ and “Can’t start Gift cards.”, one indented grey line per problem, then “Nothing was started.” Lines: “docs/prds/gift-cards/phase-3-returns.md cites no acceptance criteria.” · “The checkout has uncommitted changes: 3 files.” · “phase-2-refunds.md depends on phase 3, which comes later in the plan.” · “phase-2-refunds.md depends on phase 5, which has no phase document.” · “phase-2-refunds.md lists 2c, which has no file.” · “gh isn’t signed in to github.com. Run gh auth login.” · “origin isn’t on GitHub: <url>” · “gh isn’t on the PATH.” (likewise claude and git). On Windows, one line: “Kiln runs on macOS and Linux.”

11. The line under each started progress step on Phase detail: Build, Deliverable review, Test hardening and Refactor pass read “<skill> skill started” with the time and “skill call”; Commit reads “first git commit seen” and Push “git push seen”, each with the time and “Bash call”. This changes one drawn line: Deliverable review’s “…its reviewer subagent is reading the changed files” becomes “…its reviewer subagent is working”, shown only while that reviewer hasn’t finished, because Kiln can see that a reviewer is running but not what it is doing.

12. A phase already closed by hand before Start still appears in the plan on Documents found, with “closed” in green beside its title. The count covers only phases left: “4 phases to implement, in this order · 1 already closed”; “1 phase to implement · 4 already closed”; “No phases left to implement · all 5 already closed”.

Alternatives considered: print nothing when Ctrl+C finds no phase session working (lost: the person gets no word on where Kiln left the feature); leave the reviewer clause out of the Deliverable review line (lost: someone watching a long review would see no sign it is still going); always show the date on times (lost: drawn times carry none, and most times are today’s); leave closed phases out of the list (lost: the person couldn’t tell Kiln had seen them).

Why this is proposed

Amber means needs you, red is Kiln’s accent and green means done, so grey says nothing extra. The Needs you screen has no phase plan (UI-006), so an “All phases” link would lead nowhere drawn. Each terminal line states only what Kiln recorded and reuses drawn copy where it can. Days on times matter because a feature can run overnight or sit at Needs you for days, and “Stopped 11:52 AM” seen the next morning would read as today. Start-check lines name the file, count or address checked so the person can fix it without guessing.

Source confidence: 75% (impact if wrong: low)
