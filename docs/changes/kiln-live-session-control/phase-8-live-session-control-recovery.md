## What the audit found missing

- **AC-LIVE-02:** Browser `LiveComposer.submit` (`view/src/components/LiveComposer.svelte:23–25`) clears its pending instruction even when HTTP returns a still-`submitting` receipt. `Engine.liveView` does not exclude that pre-write gate-acquisition interval, so Send can re-enable while the submission is pending; journal busy protection refuses a repeat rather than disabling it. The same composer uses `messageProblem` to disable nonempty NUL/malformed-Unicode drafts without rendering its reason. Restarted uncertainty also loses running takeover availability, and bot Verify advertises availability during pending release, as detailed below.
- **AC-LIVE-04:** `src/control/projection.ts::statusProjection` chooses takeover wording before `record.pause.requestedAt`. When both requests exist, text/JSON status omits the required independent “Will pause after … finishes. Current work continues.” explanation. The raw pause and cancellation control survive; persistence/cancellation themselves work.
- **AC-MSG-02:** `src/session/claude-session.ts::runSessionProcess` awaits `observations` before calling `onLiveExit`, without a finalization guard. A rejected final observation skips `Engine.endLiveMessages`, leaving an exited attempt's accepted unaccounted input labeled submitted rather than uncertain.
- **AC-MSG-03:** The same exit path can omit the progression hold. A final JSON event without trailing newline is processed after process close and immediately awaited; a gate/identity/lock observation error can bypass exit accounting. After normal provider initialization, the dispatch receipt is already settled and `controlDispatch` cleared; `Engine.runProcess` catches the error but only mutates that completed dispatch object's effects/reason. `settleSession` can therefore reach otherwise-passing completion checks with no message hold. Both browser and bot inputs, and all three supported activity kinds, share this path.
- **AC-MSG-05:** Constructor `recoverLiveMessages` creates/retains a `delivery_recovery` hold, then `Engine.decideQuietly` returns through its existing-hold branch before reconstructing `current`/`recoveredLive`. A still-running gated attempt cannot request takeover because `liveView.available` and `acceptTakeover` require `current.processRunning`; the hold waits for natural exit without requesting its checkpoint. Separately, a crash during combined bot review/Resume or review/Verify can permanently block the explicit recovery path, as described under AC-BOT-02.
- **AC-TAKE-03:** `src/engine/snapshot.ts::needsYouView` builds a live-hold command with `resumeCommand(folder, id).replace("\n", " && ")`. An admitted cwd containing LF is correctly quoted by `claudeCommand`, but this replacement changes its first embedded path newline instead of the separator. The browser command targets another folder and leaves an unconditional second command. Current paused-session bot handoff inherits `currentStop.resumeCommand`; its separate cwd/argv and ordinary raw/fresh-command builders are correct.
- **AC-TAKE-04:** `CommandJournal.submit`'s generic stale-target refusal precedes `Engine.acceptTakeover`. For an explicitly supplied target whose retained activity facts establish that it finished before acceptance, browser takeover and versioned explicit-target requests report only “execution or control state changed,” omitting the required ended-activity explanation. Successor safety works. This finding excludes opaque stale tokens without recoverable old identity, unknown targets and ended attempts whose activity remains unfinished; do not invent certainty or add token-history infrastructure.
- **AC-BACK-02:** `Engine.auditDoneCheck` can return ordinary `passed:false` for source/read errors instead of unavailable. `recoverPhase("resume")` and its later completion rechecks then treat those errors as unfinished work and can dispatch Resume. The design requires staying held on a read/check error. Genuine incomplete/dirty work must remain resumable.
- **AC-BACK-03:** The same audit evaluator replaces old rows/time through `recoverPhase` → `updateStop`, instead of retaining dated results and retry. Missing siblings include `plan.unavailable`, unaccepted report filesystem errors, `submitAudit`'s retained `evidence_unavailable`/503 refusals, `acceptedAudit` private-result reads before the protected currentness catch, and development `ledger.sourceUnavailable`. Conclusive missing/invalid/incomplete evidence remains a fresh failed predicate; unreadable/unavailable sources are check errors. Phase unavailable propagation and the inner accepted-report currentness error wrapper already work.
- **AC-BOT-01:** `Engine.controlView` advertises `verify-and-advance` from `phaseRecoveryTarget() && !busy` even while the old attempt or tracked ownership prevents release. `statusProjection` forwards `available:true` without a reason; browser `PhaseHandoff` disables Verify and engine admission refuses it. This is inaccurate eligibility, not unsafe acceptance. Review-only eligibility with combined `--message-reviewed` is not the finding: those inputs may explicitly acknowledge reviews within an otherwise eligible operation.
- **AC-BOT-02:** Combined reviewed Resume/Verify persists individual acknowledgements in `applyControl` → `reviewMessages` before any dispatch/completion reference. A crash after partial or fully saved review leaves the parent receipt at `stage:applying`. `reconcileControl` handles standalone `message-review`, but this combined action falls through to an indefinitely indeterminate, blocking journal operation; `command-status`/retry cannot settle it, and browser/bot cannot submit remaining reviews or hand-back. Preserve saved acknowledgements and holds, conclusively reconcile the distinguishable pre-effect boundary without replay, and retain true uncertainty where dispatch may have happened. Bot paths also inherit the exit-accounting, restarted takeover, audit-error, command-quoting and known-ended explicit-target gaps above; their pending-release eligibility must agree with browser safeguards.
