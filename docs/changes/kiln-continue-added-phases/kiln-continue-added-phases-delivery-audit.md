## Confirmed missing boundaries and sibling checks

### Preparation return does not reconcile the revised plan

`src/engine/engine.ts::judgeEndedSession` (around line 3382) enters `advancePreparation` for a successfully returned preparation turn before ordinary `doneCheck`. `drive` has the analogous recovery/admission path around line 2469, also before `readPlan`. `advancePreparation` verifies preparation, marks its implementation intent and calls `runProcess` directly. Neither that path nor `recheckPreparationAdmission` compares the accepted plan or known plan sources.

Concrete scenario: Resume performs its preliminary reconciliation, then the resumed preparation turn appends/splits the active plan, or another known shared source adds/changes a leaf missing from the active workspace. When that turn returns, Kiln dispatches dependent implementation without accepting/showing the revised plan or stopping for the discrepancy. `preparationCheckpoint` fingerprints assigned worktrees/configuration/source integration/authority; it does not read known shared-plan documents. Live takeover checks do not close the interval: `observeControlDispatch` clears takeover state when the resumed preparation prompt is submitted.

This violates AC-HANDBACK-01's every-return reconciliation and AC-HANDBACK-03's discrepancy stop. The design's Active execution handback explicitly includes settling a returned provider session. Main-assessor sibling checks covered direct provider settlement and drive recovery; both Claude/Codex converge here. Ordinary implementation/audit/finalization settlement, manual Verify/Resume and unfinished startup do invoke `readPlan`. Existing checkpoint, pause, billing, command ownership and native permission checks remain required alongside the missing reconciliation.

### Retained Codex provenance does not share the discovery deadline

`Engine.checkCompletedPlanOwned` (around line 2229) creates the overall 120-second signal in `git.signal`, but its `readProvenance` callback passes no signal. `completed-plan-accounting.ts::accountCompletedLeaves` awaits that callback for each newly externally closed phase with a retained Kiln owner. `Engine.readRetainedCompletionProvenance` (around line 4636) then scans sessions sequentially; each Codex scan receives a new engine-shutdown plus 120-second timeout. `session/codex-evidence.ts::auditCodexConversation` correctly enforces its individual bound, so several slow scans can keep discovery checking and mutation admission busy past the whole-operation deadline.

The design's Completed feature discovery requires the entire operation to fit the existing 120-second reconciliation deadline. This missing failure boundary belongs to AC-FIND-04. Main-assessor sibling checks covered multiple retained owners/sessions, Git-object/legacy/accounting reads, preparation-permission helpers and shutdown. Git and permission helpers receive the enclosing signal; retained Codex provenance drops it. Preserve the standalone scanner's own bound while propagating the enclosing operation deadline. These findings are code-trace assessments, not runtime timing reproductions.

### Inherited completed scope is not compared

`phaseScopeDigest` includes only the phase document's direct repositories, dependencies and split IDs. `completedScopeProblems` checks closed leaves, while the parser keeps split-parent repository declarations on the parent. Accounting's carried-completion branch likewise compares only the child's direct digest. A fictional in-memory probe using the existing compiled exports removed `comet-api` from a split parent with closed child 1a: the parent repository set changed, child scope stayed equal, `completedScopeProblems` returned no problem and `accountCompletedLeaves` classified 1a as `carried_completed`.

The design requires completed repository scope to remain intact. Its explicit exception permits newly added split-parent repositories to apply to remaining children; it does not permit removal/replacement of inherited completed scope. This affects AC-CONTINUE-03 and AC-FIND-03's unresolved-earlier-work classification. Sibling checks covered completed-source comparison, active comparison, carried accounting and legacy/external original-plan repository handling. Preserve the allowed addition case rather than assigning every later parent repository to earlier receipts.

### Governing-document phase links do not use rename identity

`planSourceFromDocuments` supplies the path/link map for phase scopes but calls `normalizedScope(bytes)` without them for non-phase requirements. Discovery's `semantic` includes that requirements digest. A second fictional in-memory probe kept all phase IDs/scopes/closures and added work identical, renamed a phase file in one candidate and updated only its PRD link: phase scopes stayed equal, completed-scope problems stayed empty, but requirements and discovery semantics differed. When both sources contain the same additions, this makes `discoverCompletedPlan` publish `source_conflict` for a difference that changes no work to run.

This affects AC-FIND-02's meaningful-disagreement rule and AC-CONTINUE-03's harmless rename contract. Phase 4 repaired the phase-file comparison caller, but the governing PRD/design/phase-plan caller still lacks the shared resolution semantics. Exact candidate bytes remain a readiness/proposal input; comparison equivalence must not weaken that separate exact-input contract or substantive requirement-change detection.

### Capacity failures lose their typed interface result

Saved/Git readers and retained baseline/accounting/proposal writers enforce the 8 MiB/10,000 phase bounds, but discovery catches `plan_too_large` as a generic failed check; accounting/proposal capacity errors can also become `DiscoveryWriteFailure`. The check route maps every failed check to 503 `{check}` rather than the required 413 `plan_too_large` with the actual limit. This is an additional AC-FIND-04 failure boundary. Sibling checks covered local/Git candidate limits and retained baseline/accounting/proposal limits, not just the route's status expression. Keep genuine uncertain durable writes separate from a pre-publication capacity refusal.

### Normal Claude preparation does not enforce tracked-process release

`advancePreparation` requires settled output, workspace evidence and Codex safety, then starts `verifyPreparation`. The normal Claude runner closes `LiveOwnedProcesses` after provider exit, but `close()` only stops scanning and awaits its inventory read; it does not release or reject retained descendants, unresolved process observations or scanner obstacles. The existing `requireExited` loop for those identities is in `reconcileTakeover` under an explicit takeover hold, not normal preparation settlement. The supplied `beforeEnd` callback only reads sleep evidence.

The design's Preparation execution requires tracked-process cleanup before verification. Thus an ordinary Claude preparation can reach native checks/implementation while known background preparation work remains alive. This affects AC-CONTINUE-07. Sibling inspection covered ordinary/manual preparation, takeover release, restart and Codex's explicit cleanup gate. Enforce the existing tracked ownership contract without claiming universal detached-process containment or terminating unrelated work.

### Failed discovery can retain grants after known scope movement

`checkCompletedPlanOwned` marks pending authority superseded only when `check.result.proposal.scopeDigest` exists and differs. Discovery can already retain a different delivery-base revision in source facts, or a changed candidate digest, then fail parsing/accounting/readiness without producing a proposal. The pending grant remains pending. If the original inputs return, `pendingForProposal` can match and reuse it.

The target-grant design requires irreversible supersession on any observed non-grant bound-input change, including when older bytes return. This affects AC-CONTINUE-09. Sibling checks covered local/base observations, exceptions after candidate reading, pending-grant lookup/adoption/replay and restart linkage. An unknown source failure alone must not be invented into a changed scope; the missing case is a positively established bound-input change within an otherwise incomplete check.

### Encoded Markdown extensions skip required reference reads

Both `observePlan` and `observeGitPlan` check raw link targets for `.md` before `decodeURIComponent`. A valid governing link ending `%2Emd` is skipped instead of resolved/read. A disposable fictional saved-document probe using the existing compiled `observePlan` rejected a missing `missing-requirements.md`, but accepted the same missing target spelled `missing-requirements%2Emd` and omitted it from the observed document set. Git-object and active/shared readers share the same ordering defect.

This affects AC-FIND-02's coherent required-document observation and AC-FIND-04's missing-source failure boundary. The fix must preserve `kiln:reference` provenance exclusions, replacement-pointer requirements, path/symlink protections and aggregate bounds. This is a reference-reader omission, not a request to fetch remote links.

### Required new-repository read failure is published as a successful check

`evaluateContinuationReadiness` catches failed `originBranches` for a newly named repository as an ordinary problem and continues. `discoverCompletedPlan` then publishes a current blocked proposal/result and advances `lastSuccessfulAt`. The repository's required base read was unsuccessful, so the design requires an incomplete failed check rather than a successful known-readiness conclusion. Existing-repository `remoteBase` failures throw and remain failed; the new-repository branch is the missing sibling. This affects AC-FIND-04. Preserve ordinary known configuration/permission blockers separately from unsuccessful required evidence reads.
