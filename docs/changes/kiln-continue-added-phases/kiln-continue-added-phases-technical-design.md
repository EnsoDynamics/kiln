# Technical Design: Kiln Continue Added Phases

**PRD:** [Kiln Continue Added Phases](kiln-continue-added-phases-prd.md) · **Assumptions:** [CONTINUE-001 and CONTINUE-002](kiln-continue-added-phases-assumptions.md) · **Screens:** [seven-state interactive mock-up](mockups/kiln-continue-added-phases.html)

## Overview

Extend the existing local engine with a retained plan baseline, source reconciliation and an explicit continuation of a completed feature. An unfinished execution accepts compatible additions when control returns; a completed execution discovers additions without starting them. Continue accepts one immutable proposal, prepares a fresh workspace from current delivery bases, and runs the remaining leaves through existing checks, audits and delivery. Earlier executions remain readable history on the same feature page.

CONTINUE-001 governs when discovery runs. CONTINUE-002 requires the revised document set to exist together at the configured remote delivery-base revision for a completed-run restart; an active-run handback keeps its active workspace. Neither discovery nor acceptance creates merge, deployment or spending authority.

## Existing Code

**Posture: Preserve.**

- Reuse the foreground TypeScript engine, instance lock, private atomic JSON records and local Hono/SSE/Svelte interface.
- Reuse phase identity, split ordering and dependency syntax; phase IDs remain scoped to the same PRD.
- Reuse repository discovery, objects-only fetches and protected worktree setup.
- Reuse phase completion, provider provenance, manual recovery, pause, account and billing checks.
- Reuse whole-PRD audit manifests/currentness and development-delivery evidence and target grants.
- Preserve old phase facts, session paths, completion times and actual delivery links; no history is rewritten into a later execution.
- Preserve the explicit already-complete manual-resume choice and the existing local security boundary.
- Keep installed Enso Method skills unchanged; new instructions belong in Kiln's external prompt templates.

## Architecture

No new service, database, queue, watcher or background process. The existing engine and durable command journal are the only mutation owner for this PRD. It serializes plan acceptance, continuation acceptance, setup, scheduling, recovery and final completion; competing state-changing commands receive `busy`, while identical discovery requests share the current read. Snapshot rendering never starts work.

Three boundaries carry the change:

1. **Observation:** read a coherent document set and its source evidence without replacing the accepted plan.
2. **Acceptance:** compare it with retained scope and completion evidence; publish a proposal for a completed feature, or accept compatible active-run changes at handback.
3. **Execution:** schedule only against an accepted plan, with current prerequisites, authority and ordinary completion checks.

A successful observation is not a completion check. A historical delivery is not evidence that the current plan is finished. These distinctions apply to both restricted delivery and enabled development-delivery executions.

## Plan Identity and Comparison

### Retained baseline

Retain a versioned `PlanBaseline` when a new execution starts, whenever a compatible active plan is accepted, and when it completes. Keep the completed baseline immutable. Store source bytes or immutable content-addressed copies so a deleted old worktree or branch cannot erase the comparison basis. Updating the visible current plan must not overwrite the previous baseline before comparison.

A baseline contains the governing PRD identity, document references, parsed ordered phases, normalized scope for each phase, requirement manifest, repository names, dependencies and closure evidence references. Store both an exact document digest and a comparison digest: readiness and stale-proposal checks use exact inputs; detecting a completed phase's material change uses the comparison form.

Phase identity is the existing parsed phase ID, not a title, filename or highest ordinal. A filename change retaining that ID is a rename. Phase order follows existing numeric top-level ordering and declared split-child order. Do not infer work from a maximum number or a separate prose phase table. A split parent never counts as an executable leaf.

### Comparison rules

Use a versioned Markdown structural normalization: normalize line endings, equivalent Markdown emphasis/list formatting and prose line wrapping; preserve words, numbers, code spans/fences, link targets and section structure. Resolve phase-document links to phase IDs before comparing renames. Ignore checkbox state and parsed historical Closed metadata when comparing scope, but compare closure state separately. All other phase content, including phase-specific notes and inherited work stated in the leaf, participates. Existing split-parent repository additions (Multi-Repo Delivery AC-ADD-04) apply to remaining children without retroactively assigning new repositories to earlier completed receipts. A title wording change is material; changing only its Markdown styling is not.

Carry an earlier completed phase forward only when its ID, normalized scope, repositories, dependencies and split structure remain intact and it is still closed. Removal, ID reuse, reopening, splitting a previously completed leaf or unexplained material edits are unresolved earlier-work changes. Show the affected IDs and source differences; do not rerun them or silently call them additions. Unfinished leaves may split through the normal split contract, including judging the first descendant of a splitting session.

Compare requirements independently from phase completion. Revised PRD criteria or design/assumption text invalidate whole-PRD evidence as required by the audit contract; they do not alone invent a new implementation leaf or reopen earlier completed phases. This permits an amendment to assign revised behavior to appended phases while retaining the earlier phase receipts. A completed feature with only prose changes and no new unfinished leaf stays historically complete and reports no new phases, with the observed revision; discovery does not launch audits by itself.

Classify every observed leaf as carried completed, new unfinished, externally completed and verified, externally closed but unverified, or unresolved earlier work. An externally closed phase is not counted as new unfinished implementation, but is prominently listed with its unresolved evidence or planned integration. It can block readiness; it cannot disappear from total-plan accounting. The executable offer count is the number of newly added unfinished leaves, not the total number of added documents. Counts, first eligible phase and readiness are derived from these classifications, never maintained independently.

### Completion evidence from outside Kiln

For phases completed outside this execution, apply the applicable Closed, Committed, Pushed and workspace/provenance checks plus any required development-delivery evidence. An existing Kiln receipt is reusable only for its unchanged scope and identified repository revisions. For work completed before any Kiln session, add an explicit external-completion evidence path: bind the phase scope and repository identities to immutable work revisions, verify the Closed document and committed/published work, then verify its integration coverage. Record provider/workspace provenance as not applicable only when no Kiln session ever owned that work; this is not a passing Stayed receipt. A recorded Kiln session with missing provenance still fails its existing checks. If the source or scope cannot be established, show unresolved evidence.

For work without a retained completion receipt, the governing PRD or technical design may identify immutable work under `## External completion evidence`, using ordinary prose `Phase <id>: repository <name> at commit <revision>.` Repository names and full commit IDs are backtick-quoted; each affected repository, including the PRD repository, has one entry. The phase ID uses the existing grammar. Read only non-quoted, non-fenced text in that section, normalizing Markdown emphasis and prose wrapping; retain its exact source spans. Keeping these references outside the phase document allows a later evidence amendment to identify the commit that contains the closed phase without making that commit refer to itself. These entries identify evidence, not completion or integration permission.

Resolve each name through the existing repository identity/discovery rules and require the complete affected-repository set. The PRD-repository revision must contain the closed phase with the same normalized scope and phase identity as the candidate. Independently verify every identified commit's publication and integration coverage, plus any applicable retained provider and development-delivery checks, before classifying it as externally completed and verified. A missing, malformed, contradictory or incomplete entry remains unresolved with its document location and the missing evidence; a Closed line or the candidate base alone cannot substitute for identified work. Existing unchanged retained completion references remain reusable under the scope rules above and need no new prose entry. A documented preparation source is evaluated under Readiness and Planned Preparation; its availability does not establish published/integrated completion.

Integration proof must cover the identified work in every affected repository. Exact commit ancestry is sufficient; a recorded GitHub merge source/result pair supports verified squash/rebase integration under the existing delivery contract. A closed-unmerged PR, a commit subject or a Closed line is insufficient. Preserve the original completion time and verification time separately; do not invent the former when unknown.

## Source Reconciliation

### Completed feature discovery

Read the shared checkout's saved document bytes and the latest configured remote delivery-base revision of the PRD repository. Resolve the base through the existing origin read and objects-only fetch, and read its files directly from Git objects; discovery creates no checkout and never alters a working branch or index. Read the PRD, design, assumptions when present, phase files and their required local document references as one candidate document set. Retain the path/revision/digest and exact files that are absent, dirty or unintegrated. Resolve local references within the assigned repository, reject escaping paths and symlinks, detect cycles by document identity, and apply the aggregate size/phase limits while reading. A document link cannot authorize reading arbitrary local files or fetching a remote URL.

The old execution workspace is historical evidence, not the discovery source. Its disappearance is not an error when retained evidence and an authoritative current source are available. Known additional sources are limited to repository/workspace identities already recorded by Kiln and explicit source references in the governing plan. Do not enumerate arbitrary branches or search unrelated worktrees for a preferable plan.

Compare each available candidate against the completed baseline, not simply against the other candidate. A shared checkout still matching the baseline while the remote base has compatible additions is an explainable older copy; report both and use the remote candidate. Conversely, compatible local additions absent from the remote base are discoverable but not ready. Where both candidates introduce different scope, or one changes earlier completed work, report conflict and withhold Continue. Equivalent scope with different formatting can be compared, but readiness still requires the exact selected document set to exist at one base commit. Do not assemble a plan from different revisions.

The required sources must either be read successfully or be positively identified as an obsolete historical workspace. A failed origin read is unknown readiness even when local additions are visible; missing/unreadable shared source is a named incomplete check. Retain prior successful results with their old timestamps and label them as earlier results. Never turn a failed read into an empty plan or a fresh zero count.

A candidate read detects concurrent edits by checking its document membership and bytes before/after extraction, and remote revision before publication. If inputs move, publish `source_changed` and allow retry; never combine revisions. Bound the discovery operation to the existing 120-second reconciliation deadline, cancel on engine shutdown, and retain per-source failure facts. Required network failures do not trigger agent work or an unbounded retry loop.

### Implemented completed-check observation (Phase 2a)

Private schema 14 adds `completedPlanCheck`: current status, attempt and last-success timestamps, per-source path/revision/digest/error facts, and either a current result or explicitly earlier retained result. A result references immutable baseline and candidate sidecars and records observed added leaves, earlier-scope problems and relevant documents absent from the delivery base. It is an observation, not an executable proposal or authorization; Phase 2b builds classification/readiness on this boundary.

`Engine.checkCompletedPlan()` joins concurrent reads under the existing engine checking/command admission. `prepare()` checks a historically completed execution before CLI output; `POST /api/continuation/check` serves authenticated same-origin refreshes; the Complete component checks once on mount and exposes the same retry action. Snapshot reads and SSE reconnects do not initiate discovery. The check cannot create provider work, reset execution state, replace the accepted baseline, or change repository checkouts. Legacy recovery uses the recorded delivery revision and original completion receipts, including recursive split-first-leaf ownership; current source bytes alone cannot establish the historical baseline.

### Active execution handback

Reconcile before accepting advancement on manual Verify/Resume, settling a returned provider session, restarting unfinished work, selecting final audits/delivery, and recording completion. Read the active workspace PRD and phase set, then compare known other sources with their last accepted source observations. A stale shared checkout that predates the active plan is not a conflict merely because its Closed lines or phase count lag behind.

An addition, reopened leaf, changed dependency or material scope edit in a known other source that is absent from the active workspace creates a plan discrepancy. Show source path/revision, affected phases and the concrete instruction to reconcile the documents into the active workspace, commit/push under the normal execution rules, then use the existing handback control. Kiln does not import, merge or overwrite those documents itself. Missing required source evidence is a failed reconciliation, not permission to complete. Use the current completion-audit document contract: an explicitly marked `kiln:reference` provenance link is not traversed; governing seeds, unmarked local links and replacement pointers remain required.

After a coherent compatible plan is accepted, atomically record its baseline, added IDs and remaining count before another activity is selected. Require the current activity's normal completion checks before advancing. Once they pass, run the next eligible unfinished leaf automatically; no completed-feature Continue action is involved. Preserve pending/active pauses and usage/billing holds. A plan edit or page load while the person controls the stopped session is observational only and cannot release that stop.

Keep a short handback notice in the snapshot until the next accepted handback or execution end: added IDs, accepted source and remaining leaf count. If reconciliation fails, leave current session facts and earlier done receipts intact, publish a recoverable plan check, and prevent finalization. A stopped, running or interrupted audit is settled under its existing recovery contract; new leaves invalidate its ability to authorize final delivery. After settlement, unfinished leaves precede new whole-PRD audits. Old pending final-delivery work cannot complete ahead of the revised plan.

### Implemented external-completion accounting (Phase 2b1)

Schema 15 extends the completed-plan observation with content-addressed `CompletionAccounting` sidecars and classified leaf rows. The accepted historical baseline, phase receipts and session associations remain unchanged. `completed-plan-accounting.ts` binds ordinary governing-document references or retained Kiln receipts to exact closed scope and all inherited/direct repository identities, then checks published base ancestry or an engine-owned verified merge pair. It rechecks every inspected delivery base before retaining the result. Original completion times are retained only when recorded; the independent verification time is separate.

Retained Kiln sessions require fresh provider history through the existing Claude/Codex readers. The read-only adapter does not replace historical audits or confirmations; Codex readers launch from private state while validating the original workspace roots, so removal of the old worktree does not prevent a history read. Development-delivery assessments use the candidate document digest and the same split/recovery obligation evaluators as normal completion.

The CLI and browser expose seven unfinished Comet additions separately from externally closed phase 8 and carried historical work. The observation and accounting IDs are evidence only: no executable proposal, preparation authorization or first-eligible-phase decision exists yet. Phase 2b2 owns those additions and extends the fixture with explicit preparation. [External-completion validation](kiln-external-completion-accounting-validation.md) records the current proof.

## Readiness and Planned Preparation

A ready finished-run proposal binds every participating repository to its configured base revision and validates the complete revised document set on the PRD base. Include new repositories in existing discovery, base selection and authorization checks. Readiness must not require unrelated working-tree edits to be discarded; only relevant source disagreements, inaccessible repositories or unsafe target workspace paths block it.

For each prerequisite, record one of `integrated_verified`, `preparation_available`, `blocked` or `unknown`, with evidence and recovery action. Verified integrated work is carried forward. A prerequisite awaiting planned preparation is not falsely marked integrated, and does not increase the new-unfinished count.

Preparation is narrowly scoped work inside the first eligible implementation phase, not another phase or a background merge. The phase must explicitly identify the prerequisite, repository, available source branch/commit, intended integration destination and verification required before dependent implementation. Resolve branch names to immutable revisions and include them in the offer. The fictional Comet Library example's local `wt/catalog-accessibility` source is valid even if its last commit is not on origin: source availability for authorized preparation differs from accepting it as already pushed/integrated completion.

A `PreparationBinding` is retained with the proposal: extractor version, owning phase ID, prerequisite IDs, repository identity, source ref and full resolved commit, destination (`assigned_feature` or an explicitly authorized delivery target), governing document/blob/line spans, required authorization kind/target and verification requirements. Never execute extracted shell text or infer permission from a branch name. A structured internal binding is not a new required phase file format.

### Preparation document contract

Use the same versioned Markdown token representation for preparation extraction and scope comparison. Ignore emphasis and prose wrapping for recognition; retain exact bytes and spans. Only ordinary, non-quoted, non-fenced text under `## Phase-specific notes` introduces a preparation item. Its opening is `First step: merge Phase <id>`, optionally joining further `Phase <id>` terms with `and`. IDs follow the existing phase-ID grammar and must name parsed dependencies. A trailing `and the whole-PRD test audit` describes work in the same source; it creates no phase ID.

The item's imperative sentence is `Merge [the local] branch <ref> at <revision> into this phase's branch before building.` Here square brackets mean optional words, and `<ref>` and `<revision>` stand for backtick-quoted values. Also recognize `into branch <destination>` in place of `into this phase's branch`, with a backtick-quoted destination. The parenthetical ``(its last commit is not on `origin`; the branch is shared across worktrees)`` may appear between revision and `into` as a source-availability annotation. Other intervening prose is unsupported, rather than discarded. A revision is at least seven hexadecimal characters and must resolve uniquely to a commit in that repository; retain its full object ID.

An item may start its imperative sentence with `In repository <name>, merge`, with a backtick-quoted repository name. Without that prefix, infer the repository only when the phase has exactly one affected repository under the existing repository rules. One item identifies one repository/source/destination tuple; multiple prerequisites may share it, while distinct tuples require separate items. Retain subordinate instructions and verification requirements with the item. Destination branch names must resolve to the assigned feature branch or an explicitly authorized configured delivery target; unknown targets block readiness.

Compare explicit destination assertions in the phase's dependency text, preparation item and directly linked implementation-plan row or amendment paragraph. Every assertion must agree; a more specific heading or later note supplies no precedence. Unsupported, missing or contradictory preparation text produces a named readiness blocker with its exact spans, missing facts and an ordinary-prose replacement example using the known values. Recovery is to reconcile the existing phase/plan prose through its writing session and commit the coherent documents; the person never edits a private binding or state file. The existing authorization controls and verification must independently pass the contracts below. Extractor version and the resulting tuple, prerequisite IDs and retained source spans participate in proposal identity; changed instructions invalidate the offer.

### Preparation authority

Continue authorizes the displayed phase's ordinary preparation within its assigned feature branch. Planned source integration needs no separate conversation quotation, provider-history inspection or human-authorship check. The proposal binds the exact source, revision, repository, destination and verification requirements so acceptance can revalidate what the person reviewed.

Preparation into a configured delivery-base target additionally requires the existing explicit early-merge target grant for the proposed fresh execution. Its checkbox authorizes the exact repository and branch, with the existing CI/CD disclosure. An earlier completed execution's grant does not transfer. Continue and the target grant remain separate controls; neither broadens spending, deployment or destructive-operation permission. Applicable explicit restrictions remain effective under the existing execution/agent permission controls.

Retain the preparation's required authorization kind (`phase_preparation` or `delivery_target`) and exact required target in its immutable binding. Revalidate the existing controls at acceptance, preparation launch and implementation admission. No original-conversation authority evidence record or provider-source matcher is introduced.

### Target grants before acceptance

When a fully read proposal's planned preparation needs an uncovered delivery-base target, expose the existing explicit human target-grant action under AC-CONTINUE-09. Discovery allocates no execution, workspace or provider activity. On the first accepted grant, the same engine/journal owner reserves a fresh execution UUID and retains `PendingContinuationAuthority` privately, without replacing the completed execution. The action records permission only; it never accepts the work, starts setup or resumes a session.

Bind pending authority to an authority-neutral `scopeDigest`: completed execution/baseline, exact candidate documents, ordered leaves, repository/base vector, preparation/source tuples, required targets and applicable instruction/permission inputs. Exclude pending target-grant revisions and observation times from this digest; `proposalId` still includes the effective authorization revision. Grant-only offer refreshes keep the scope, reserved UUID and grants. Any other bound-input change supersedes them; a changed plan or target needs a fresh applicable grant, never a transfer from the older proposal. Not now only dismisses the offer. A newly applicable denial makes retained authority ineffective and holds dispatch; retain its original receipt. No separate revoke control or preference mutation is introduced.

The continuation variant of the existing grant route takes `{executionId: completedExecutionId, proposalId, authorizationRevision, target, commandId, statusToken}`. Serialize it as a browser-only internal grant action in the existing durable journal, outside the public bot allowlist. Validate the current completed execution, displayed proposal, completely read source/preparation scope, exact required configured target and applicable restrictions. Persist the reserved identity, grant with origin `continuation`, authorization revision and command-receipt linkage before acknowledging it; return authorization and the refreshed proposal, with no launch effect.

Look up identical command receipts before stale-offer rejection; conflicting reuse of `commandId` fails. Different command IDs for the same retained scope/target return its existing grant without incrementing the revision. A grant-only proposal refresh does not make its own recorded approval stale. An unrelated input change returns the refreshed blocked proposal and identifies the old approval as superseded. Restart reconciles the journal through the pending-authority pointer; uncertain durable writes fault mutations under the existing recovery contract. After adoption, replay resolves the original approval through its retained pending-to-acceptance linkage and reports current validity without changing another execution's authority.

Continue revalidates the refreshed proposal and adopts that pending authority's exact UUID/grants into the durable acceptance. With no pending grant, acceptance allocates its UUID normally and starts restricted. Activation adopts the acceptance's retained grants rather than resetting them; both paths retain all ordinary preparation and current-permission checks. The completed execution's grants and remembered preferences supply no authority to either path.

### Preparation execution

On Continue, start a fresh conversation for the owning phase in a retained `preparation` stage, with a preparation-only task and pinned binding. The turn performs the integration, resolves conflicts within its authority, commits the prepared work, submits source references and returns without beginning dependent implementation. Submission never launches verification or another turn while the provider is running. After the turn settles, require its existing workspace/provenance and tracked-process cleanup checks, then independently verify the bound source's integration into its destination. Never retry an uncertain merge before reconciling Git. Missing source, authority, safe workspace or integration proof holds preparation with the concrete blocker.

### Verification of the prepared work

The engine owns the pre-implementation check run because a provider command's success and a later HEAD reading cannot establish which source bytes an ordinary project test used. This is a bounded verification substage under the existing mutation owner, not another phase, provider conversation or service. The preparation provider may investigate failures, but its command claims cannot satisfy this gate.

Recognize subordinate instructions of the preparation item in the ordinary-prose form `Verify before building: run <command>`, optionally followed by `in <directory>` and `with timeout <seconds> seconds`, in that order. The placeholders are backtick-quoted values; a terminal period is optional. Each instruction supplies one check, ordered as written. The command must name an existing documented project validation tool or repository script. Tokenize quoted arguments without expansion into executable and argv; reject shell operators, redirection, substitution, environment-assignment prefixes and inline interpreter evaluation. Support direct commands such as `npm test` and `python -m pytest tests/test_catalog.py`; never execute the containing prose or pass it to a shell. The directory defaults to the item's assigned repository root; an explicit directory is relative to that root, resolves physically inside its assigned worktree, and cannot escape through a symlink. Resolve the executable through the execution's existing environment or a repository script pinned by the checkpoint. Retain the exact instruction span, command, argv, resolved executable, directory and timeout in the binding. Timeout defaults to 1,800 seconds per check; an explicit positive integer through 86,400 seconds replaces it. Unsupported or missing required verification instructions block readiness with their spans and a supported prose example.

Use the project's established validation environment and existing applicable permissions for either selected provider. A missing environment value or credential, explicit command restriction, unavailable required sandbox, or unauthorized external effect is a blocker; the native runner cannot bypass it. The runner adds no command-policy interpreter, credential discovery, wider writable roots or delivery authority. Resolve check definitions, scripts and configuration from the accepted prepared work. Run checks sequentially with the existing bounded subprocess lifecycle and retained output files; the provider remains stopped throughout verification.

Before verification, capture every affected repository's identity, canonical worktree, assigned branch, HEAD, commit-tree ID, index status and actual tracked/nonignored-untracked file fingerprints. Require committed source, no merge conflicts and valid integration coverage. Capture the same inputs before and after each check. Require unchanged source/configuration bytes, branch, HEAD and index; unexpected mutations invalidate verification and remain intact for the preparation conversation to resolve. Ordinary ignored test/build artifacts do not count as source proof. A receipt is successful only when the engine observed the exact process complete with exit zero and matching checkpoints; a timeout, signal, spawn failure, missing output record or ambiguous process result is not success.

Persist each verification attempt's launch intent before spawning, retaining check/binding IDs, checkpoint IDs, process identity, invocation/directory, start/end times, outcome, exit status and output references. A replay returns that attempt's recorded state. Restart reconciles the tracked process before any retry; an unsettled attempt is `unresolved`, never inferred successful or blindly repeated. Failed or interrupted checks can be repeated within this activity after their process and any external effects are reconciled; unknown repeat safety uses existing recovery instead of automatic retry. Require all check receipts at the same prepared checkpoint, recheck source/authority and workspace immediately before implementation dispatch, and durably record the verified checkpoint first. Movement invalidates affected receipts. Admit one implementation turn in the same conversation through ordinary journal, billing, pause and launch gates. Preparation need not close the phase; normal completion checks still require its verified checkpoint and whole-PRD audits cover the combined result. These observations establish the checked workspace at the gate; they do not claim to prevent arbitrary external writers or detect every transient external mutation.

### Native verification permissions

The first native preparation verifier is supported on macOS, the validated runtime. It uses the built-in OS sandbox with write access limited to the assigned worktrees and the existing temporary directories; network access matches the existing execution profile. An unavailable supported sandbox blocks verification before spawning project work. Other platforms report the missing supported verifier instead of running with wider host access.

Before the first check and implementation admission, reread the selected provider's configuration through its existing supported metadata/settings reader. The verifier does not interpret command-policy syntax. Codex command rules use its native `execpolicy check` evaluator. Claude has no separate supported deny-rule evaluator: nonempty static deny rules require retained successful exact-command evidence from the current preparation turn under unchanged settings; ask rules remain blocking. Earlier hook success is never standing permission. The tracked verifier applies the existing synchronous command-hook protocol to each actual check invocation, refusing unsupported hook kinds, asynchronous/once hooks, input/output rewrites and ask/deny results. Malformed structured controls fail closed, and each configured hook timeout is enforced before any later project command. Hooks are existing trusted configuration, never project prose; their command language is not interpreted by Kiln. Policy helpers, custom sandbox restrictions, or an unestablished policy hold verification. Codex checks and environment projection execute through its native model-free sandbox with managed configuration and the assigned roots. Claude uses the effective settings environment in memory; secret values are never retained in checkpoint records. Ordinary Continue and its pinned documented project checks supply the existing phase authority; no original-conversation permission quotation or new human approval is introduced. Configuration facts, resolved executable bytes and the validation environment participate in the prepared checkpoint, without retaining secret values. Qualified Codex’s fresh per-process arg0 shim directory is normalized to its managed namespace; configured PATH entries and actual tool resolution remain bound.

### Implemented readiness offer (Phase 2b2)

Schema 16 adds content-addressed `continuation-proposals/<id>.json` sidecars referenced by `completedPlanCheck.result.proposal`. The read-only proposal records the completed execution/baseline, exact candidate digest, ordered additions, first candidate phase, per-prerequisite readiness, repository/base vector, preparation source/check spans and settings digest. Identical rechecks preserve proposal identity; observations and verification timestamps do not participate. Historical scope remains in the accepted baseline. Carried prerequisite integration is checked against the historical receipt's affected repositories and current bases only when additional unfinished work exists. Earlier split-parent scope does not acquire newly added repositories retroactively.

Preparation under the assigned-feature destination is presented as authorized by the separate future Continue action. Named delivery-base preparation remains blocked pending the exact fresh-run target grant; old execution grants cannot satisfy it. Discovery starts no provider and allocates no execution or workspace. Phase 3 adds pending grants, acceptance/activation and execution-time permission/check enforcement; it may project the retained proposal alongside acceptance fields in the public snapshot. No conversation-permission reader or retained human-message matcher exists.

## Continuation Acceptance and Recovery

### Durable proposal and one acceptance

A successful completed-feature check retains a `ContinuationProposal` and an opaque content-derived `proposalId`. Bind the ID to the completed execution, baseline ID, candidate document bytes, ordered eligible leaves, repository/base revisions, prerequisite source revisions and evidence, preparation bindings, and applicable authority/settings revisions. Exclude check timestamps and display-only observation times so an identical recheck preserves identity.

Continue submits the displayed proposal ID. Under the existing engine owner, reread all bound inputs and required prerequisites before accepting it. A changed input publishes the replacement proposal and returns `proposal_changed`; nothing starts. A missing prerequisite or failed read returns its concrete blocker. Repeated requests for an already accepted proposal return its original acceptance and current preparation status before checking whether the feature is still complete.

Extend the durable command journal with distinct internal continuation-accept/retry actions; do not overload the existing paused-run `continue` action or expose a new bot mutation command. The browser supplies its command ID, completed execution ID and current status token along with the proposal ID. Reuse journal admission, receipt lookup and automatic launch ownership. Keep public bot action validation separate from these browser-only internal actions; adding them to a shared action enum must not make them callable through the bot command route. A journal receipt acknowledges ownership of revalidation; it is not yet authorization for workspace creation. The continuation acceptance is the plan/setup payload referenced by that receipt, not a second dispatch journal. Persist acceptance before any setup or launch: old execution ID, proposal ID, fresh execution UUID adopted or allocated under §Target grants before acceptance, retained grant references, accepted time, pinned plan, intended per-repository bases, branch/workspace names and setup progress. Acceptance is the durable authorization to run this displayed plan, subject to existing permissions. Losing the HTTP response, restarting Kiln or pressing Continue again cannot allocate another execution. There is one pending/current continuation per completed execution. Journal reconciliation must resolve the originating receipt through the retained acceptance even after the current execution UUID changes; matching only the current execution would strand a crash between activation and receipt settlement. Different command IDs submitting the same accepted proposal converge on the same acceptance. An old tab cannot accept an earlier offer after a later execution has begun.

Use deterministic names derived from the new execution UUID, such as `feature/<prd-folder>-continue-<uuid>` and a matching sibling workspace folder, checked against the existing path and branch protections. Never reset or reuse the old delivered branch/worktree. Persist intended names before creation, recognize only exact owned setup artifacts on retry, and report collisions rather than remove anything. Prepare every required repository before any phase starts. Partial setup is a visible `preparing` or `blocked` acceptance, with a **Retry preparation** action; it is not a second offer and never loses the acceptance.

### Start, interruption and completion

Once all workspace setup has passed, reread the pinned plan in the new workspace and atomically activate the new execution. Preserve the previous complete execution as immutable history before replacing active execution fields. If required source/base/authority facts have changed during interrupted preparation, hold setup and present the changed proposal for a fresh choice. Keep the original acceptance and any owned artifacts for explanation; do not silently retarget it. A replacement choice can supersede a blocked acceptance only before any provider activity started and after verifying its owned workspace has no user work. Never delete or overwrite an occupied workspace to recover.

A crash before durable acceptance means no setup was authorized; retry performs a fresh check. A crash after acceptance resumes its same setup intent. A crash after activation resumes the active execution under existing launch-intent and provider dispatch recovery. Missing or ambiguous dispatch evidence remains stopped; replay never starts a second conversation. The start of new work uses a fresh conversation, never an archived session.

The new execution has required completion audits and no accepted current audit, final-session receipt, completed timestamp or development-completion result from the old execution. Carried phase completion references remain historical scope evidence and are not current session owners. An old open PR is retained in history; a new execution cannot silently extend it. Its work must already be covered or explicitly integrated by the approved preparation. Final checks bind the new branch, revised requirements and current repository evidence, then append a new completed execution/delivery beside the earlier one.

An active run's compatible additions stay in the same execution and workspace. Invalidate audit/finalization evidence by the revised requirements and plan fingerprint, retaining the old results as history. Completion phases subsequently added by audits follow the same ordinary loop without another Continue click.

Private schema 17 adds `continuation` with a current acceptance pointer, retained acceptance summaries and immutable execution archive references. ### Local HTTP and engine commands

Use existing loopback Host/Origin/token protections. All new commands terminate through the same engine owner as existing browser, CLI and bot controls. No new user-facing continuation or bot mutation command is added; the preparation commands below are scoped session evidence submissions.

| Route | Request | Successful response |
|---|---|---|
| `POST /api/development-authorization` | Existing active-run request unchanged; continuation variant in §Target grants before acceptance | `200 {authorization, proposal}`; records a target grant only, with journal replay and no setup/launch |
| `POST /api/continuation/check` | `{}` | `200 {check}`; concurrent identical checks join the same read |
| `POST /api/continuation/accept` | `{proposalId, commandId, executionId, statusToken}` | `202 {acceptance}` on first acceptance; `200 {acceptance}` for replay |
| `POST /api/continuation/retry` | `{acceptanceId, commandId, executionId, statusToken}` | `202 {acceptance}` for retrying the same owned setup; no new execution |
| `GET /api/continuation/acceptances/:acceptanceId` | None | `200 {acceptance}` for polling/recovering the durable acceptance, including a completed or superseded one |
| `GET /api/executions` | Optional opaque `cursor` | `200 {executions, nextCursor}`; at most 100 historical summaries |
| `GET /api/executions/:executionId` | None | `200 {execution}`; read-only phase/session associations and delivery facts |

| `POST /api/preparation/result` | `{executionId, phaseId, bindingId, references[]}` | `200 {disposition: submitted \| verified, checks}`; submission records references, while verified reports an already completed engine checkpoint |

Historical session/output reads take an explicit execution ID and resolve only that archive's retained session associations; absent IDs retain the existing current-execution meaning. Unknown IDs return `404 not_found`, never another execution's details. Return display projections, not raw archives containing private authority, tokens or evidence bytes. Acceptance lookup and SSE allow a lost `202` response or page reload to recover progress without another mutation.

The preparation interface grants no authority and never directly executes submitted commands. It is accessible through the pinned Kiln executable's session-facing `kiln preparation status` and `kiln preparation submit <file>` commands, following the audit/development interfaces. A result carries typed references `{kind: git_revision, repository, commit}` or `{kind: command, sessionId, callId}` for integration/provenance inspection; merge coverage is read independently for the binding's repository/source/destination. Command references must belong to the current preparation turn and have retained terminal results; they cannot substitute for the engine-owned check receipts in §Verification of the prepared work. Unknown reference kinds, cross-session references and missing command results are refused. Identical result replay is idempotent; after provider settlement, the engine advances the retained binding into verification under that section's launch rules. GET returns each binding's `preparation | verification | implementation` stage, check definitions and attempt outcomes, with output references available through the owning activity. A verified result is a checkpoint, not phase completion.

Errors use `{ok:false, code, reason, checks[], check?, acceptance?}`: `400 malformed_request`; `403 outside_execution` or existing security refusal; `404 not_found`; `413 plan_too_large`; `409 busy | wrong_state | proposal_changed | stale_acceptance | result_conflict`; `422 plan_invalid | source_conflict | earlier_work_changed | prerequisite_blocked | preparation_unverified | baseline_unavailable`; `503 source_unavailable | check_unavailable`; `500 state_write_failed`. A completed discovery with a known readiness blocker returns `200` and `status: blocked`; a failed/incomplete read returns `503` with `status: failed`. Neither exposes an executable offer. Rejected preparation proof returns `422`; it does not allow dependent execution. An uncertain durable write (including failure after rename) prevents publication/dispatch and faults the mutation owner until restart reconciles the on-disk acceptance, archive and journal. Never restore an assumed old in-memory state and continue: the new state may already be on disk.

`kiln run <PRD>` retains its identity, port and URL. For a completed execution it runs discovery before printing any current nothing-left conclusion, then serves historical delivery with the new check result. It reports additions/readiness and the existing page URL in the terminal; it never implements automatically. Page mount/reload explicitly invokes the check route once, and Check for new phases invokes it again. SSE reconnect alone does not repeatedly initiate checks; a reconnect after a new foreground process may join that process's startup check. No timer polls for plan additions.
