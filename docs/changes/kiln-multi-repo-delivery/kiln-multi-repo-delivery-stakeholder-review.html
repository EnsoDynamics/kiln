Kiln multi-repo delivery

Lets Kiln deliver a PRD whose code spans several repositories: one feature branch and one worktree per repository in a shared workspace, sessions that can add a repository mid-phase, a stop when a session works in a repository’s own checkout, and one linked pull request per repository that changed. A PRD with only its own repository keeps v1’s layout and screens.

Out of this change: running phases in parallel and per-phase branches, cloning repositories, repositories not on GitHub, merging in order or checking the order, and teaching the Enso Method’s phase-split to write the Repositories line. All screens use fictional sample data.

For business review. Selected acceptance criteria and all 10 open assumptions. Implementation must use the full PRD and technical design. This is a dated snapshot; source links open the current documents.

01 / SECTION

Name the repositories and start

A phase document can list the code repositories its phase changes. Before anything starts, kiln run checks it can find and work in each one, and Documents found shows every repository with the branch it starts from. At Start, Kiln makes one feature branch in each repository and gathers a worktree of each in one workspace folder.

Key acceptance criteria & mockups

  • A phase names the repositories it changes on one line under its title, by folder name. The PRD’s repository is named only when the phase changes code in it. A phase with no such line changes only the PRD’s repository, as in v1. A split parent’s repositories join the PRD’s repositories but aren’t passed down to its children. AC-REPO-01
  • Each named repository must be a folder beside the PRD’s repository, be a Git checkout, and have an origin on GitHub. Otherwise kiln run stops in the terminal, naming the repository and the folder it looked in. A named repository’s own checkout may hold uncommitted work, since Kiln branches from the base on origin; only the PRD’s repository must be clean. AC-REPO-02
  • Documents found shows each phase’s repositories and lists every repository with its base branch, the PRD’s repository marked as such. It also says sessions can add a repository they find they need. The terminal’s first line counts the repositories. AC-REPO-03
  • At Start, Kiln creates the feature branch in each repository from that repository’s own base branch (develop, or the default branch when there is no develop), and a worktree of each in one workspace folder, by default .worktrees/<PRD folder>/ in the folder that holds the repositories. Before Start the person can change the folder, the branch name and each base. If Start fails partway, what was set up stays, the folder and branch name are fixed, and the next Start makes only what is missing. AC-SPACE-01
  • Next to Start, Kiln states what it may do in each repository, those added later included: commit and push to the feature branch, and open one pull request into that repository’s base branch once every phase closes. Merging, deploying and touching other branches stay forbidden. AC-PRS-04

Assumptions to confirm

REPO-001Unanswered

Does Kiln find a named repository only as the folder of that name beside the PRD’s repository?

Yes. A named repository is found only as a folder of that name in the same parent folder as the PRD repository’s checkout. A phase naming storefront, in a PRD under ~/devel/acme/product, means ~/devel/acme/storefront.

There is no mapping file and no search elsewhere on the machine. Alternative: also accept a mapping from repository name to folder, for other layouts.

Why this is proposed

The layout this change exists for keeps an organization’s repositories side by side in one folder, as does the Enso Method’s worktree convention, which puts .worktrees/ in that same folder. A mapping file would cover other layouts but adds setup before a first run, and can be added later without changing this rule.

Does a phase document name its repositories on a Repositories line under its title?

Yes. One line under the title, beside the Parent PRD and Technical design lines already there, listing folder names separated by commas, for example “**Repositories:** returns-api, storefront”.

The Enso Method’s phase-split would write the line once the method adopts it; until then a person writes it by hand. Alternative: a “## Repositories” section listing one per line.

BRANCH-001Unanswered

Is the feature branch the same name in every repository?

Yes. One name, feature/<PRD folder name> by default, in every one of the PRD’s repositories. The person can change it once on Documents found, for all repositories together. Example: product, returns-api and storefront each get feature/customer-returns.

Alternative: a name per repository, each editable.

Why this is proposed

One name makes the pull requests easy to find together and matches how people name a cross-repository change by hand. A name already taken in any one repository blocks Start, which is rare with a PRD-specific name.

02 / SECTION

Work across the repositories, one phase at a time

Each phase’s session works in every worktree of the workspace and commits and pushes to the feature branch in each repository it changes. Phases still run one at a time, and a phase is done only when its work is committed and pushed in every repository.

Key acceptance criteria & mockups

  • Each session is told the PRD’s repositories, where each worktree is, and that it commits and pushes to the feature branch in each repository it changes. It is told to stay inside the workspace and to ask Kiln for a missing repository rather than change that repository’s own checkout. AC-SPACE-02
  • A PRD whose only repository is its own keeps v1’s worktree, branch, screens and pull request, PRDs already underway when this ships included. It gains one line on Documents found and the new Stayed in the workspace check. Once a session adds a repository, it becomes a multi-repository PRD and its screens show the repositories. AC-SPACE-03
  • Committed means no worktree in the workspace has uncommitted changes. Pushed means, in each repository, the feature branch matches its copy on origin; a repository whose feature branch has no commits of its own yet passes. Closed is unchanged: the phase document has its Closed line. AC-CHECK-01
  • Needs you names the repository for each failed fact, for example “returns-api: a41c9e2 isn’t on origin yet”. AC-CHECK-02
  • Kiln leaves the workspace folder and every worktree in place after the last phase, and says they are there until the person removes them. AC-SPACE-05

What should work or look differently in this section?

Assumptions to confirm

BRANCH-002Unanswered

Do per-phase branches and workspaces wait for the later parallel-phases version?

Yes. Sessions keep committing straight to the feature branch in each repository, in one shared workspace, one phase at a time, as in v1. Per-phase branches and per-phase workspaces come with parallel phases, not in this change.

What carries over to parallel phases: the feature branch per repository with one name everywhere, each repository’s base branch, finding repositories by folder name, and one pull request per repository. What parallel phases will still change: where a session works, what Pushed means, which workspace the outside check judges, and where an added repository goes.

Alternative: build per-phase branches now, settling what Pushed will mean before parallel phases arrive.

Why this is proposed

Both are needed only when two phases work at once. With one phase at a time, a phase branch would join the feature branch as a plain fast-forward, a step Kiln would have to perform and explain for nothing yet. Building per-phase branches now would settle only one of the four things parallel phases change.

03 / SECTION

Add a repository partway through a phase

When a session finds it needs a repository nobody named, it asks Kiln for it and keeps working. Kiln sets up the branch and worktree, nobody is called in, and the person sees it afterwards, marked “added in phase <n>” on screen and in a terminal line.

Key acceptance criteria & mockups

  • A session asks for a repository by name with a kiln command. Kiln creates the feature branch there from its base branch, adds its worktree to the workspace, tells the session where it is, and the same phase continues. The command works only while kiln run is running for the PRD and a phase is in progress or stopped at Needs you; otherwise it says why and changes nothing. AC-ADD-01
  • Kiln adds a repository only when it passes the checks a named repository gets at Start, the branch name is free there, and its worktree folder is new or empty and not inside a checkout. When a check fails, Kiln tells the session why and changes nothing; the session carries on or ends as it judges, and the done check judges the phase as usual. AC-ADD-02
  • An added repository joins the PRD’s repositories for every later phase and for the pull requests, is marked “added in phase <n>” wherever repositories are listed, and has its base branch fixed. The terminal prints one line when it is added. AC-ADD-03
  • A repository named after Start, because a session split its phase or a person edited the plan, is added before that phase’s session starts. If Kiln can’t add it, the phase stops at Needs you as a broken plan does, naming the repository and the failed check. AC-ADD-04

What should work or look differently in this section?

Assumptions to confirm

REPO-002Unanswered

Does a session that needs another repository get it and carry on, rather than stop at Needs you?

Yes. The session asks Kiln for the repository and keeps working. Kiln sets it up and the phase doesn’t stop. The person sees it afterwards, marked “added in phase <n>” on screen and in a terminal line.

Side effect to weigh: the new feature branch and the record of the new worktree land in the repository the person’s own checkout shares, though that checkout’s files are left as they were. Kiln never deletes branches, so a wrong addition leaves an unused worktree and an empty branch for the person to remove by hand.

Alternative: stop at Needs you and let the person decide.

Why this is proposed

Phase planning can’t always know every repository a phase will touch; the need often shows up only once the code is read. Stopping would hand the person a branch and worktree to set up by hand partway through a phase, which is the babysitting Kiln exists to remove.

CLI-001Unanswered

Does a session ask for a repository with a second kiln command?

Yes. Kiln gets a second command beside kiln run, for example “kiln add-repository storefront”. A session runs it from the workspace folder or any worktree in it, and a person can type it too. When kiln run isn’t running for that PRD, it says so and changes nothing.

This reverses in part Kiln v1’s promise that kiln run would be its only command. Alternative: the session sets up the worktree itself with Git, following instructions in its prompt.

Why this is proposed

The browser view’s connection is guarded so only the person’s own browser tab can use it, and a session has no tab. Letting the session set up the worktree with Git would move setup Kiln owns into every session’s instructions, with no check that the branch name is free. A command is also something a person can type by hand, as everything Kiln asks of a session must be.

REPO-003Unanswered

Does an added repository branch from its default base, with nobody asked?

Yes. A repository added partway through a phase gets its feature branch from develop, or its default branch when it has no develop, the same rule Documents found starts every repository with. Nobody is asked, and the base is fixed from then on.

Example: phase 2b adds notifications, which has no develop, so its branch starts from main and its pull request goes into main.

Why this is proposed

Asking would stop the phase, which REPO-002 rules out. The default is the base most repositories are delivered into, and what the person would have seen on Documents found had the repository been named.

04 / SECTION

Stop when a session works outside the workspace

A change in a repository’s own checkout bypasses the feature branch and its pull request, and can disturb the person’s other work there. A new fourth part of the done check, Stayed in the workspace, reads the session’s transcript for file edits and Git commands in any checkout outside the workspace, and stops at Needs you when it finds one.

Key acceptance criteria & mockups

  • The check reads only the session’s transcript, its subagents’ included, never the state of the checkouts, so the person’s other chats working there never fail it. No model judges it, and a session with no transcript passes. A phase that fails it is Needs you even when the other three checks pass, and Needs you lists it only when it failed. AC-OUTSIDE-01
  • Editing or writing a file outside the workspace fails the check, except the Enso Method’s session logs in .agent-sessions/, which its skills write in each repository’s own checkout by design. Shell commands other than Git pass: Kiln doesn’t see what they change and doesn’t claim to. AC-OUTSIDE-01
  • Needs you names each change and where, for example “Committed 6b0d2fa to main in ~/devel/acme/design-system”. Kiln changes nothing in those checkouts. It offers a copyable prompt asking the reopened session to bring only its own edits into the workspace on the feature branch, adding the repository first if needed, and to leave each checkout as it is and tell the person what still needs putting back. AC-OUTSIDE-02
  • Kiln never resumes such a session on its own. After an interruption, or a usage limit once usage-limit recovery is built, a phase that failed this check goes to Needs you instead. AC-OUTSIDE-04
  • The resume command on Needs you changes to the folder the session started in, and the fresh-session prompt names the workspace and the PRD’s repositories, so a person picking the phase up by hand works where the session did. AC-SPACE-04

Assumptions to confirm

OUT-002New since the last refinement. Decides how often a session is stopped for touching the person’s own checkout.Unanswered

Does any Git command that changes a checkout outside the workspace fail the check, not only a commit or a push?

Yes. Outside the workspace, the check fails on a file edit or on any Git command that changes a checkout’s files, its staged changes or the branch it is on; creates, moves or deletes a local branch; or pushes from it. That covers commit and push, and also add, checkout, switch, stash, reset, merge, rebase and pull.

Git commands that do none of those, such as status, log, diff and fetch, pass.

Example: a phase 3 session that runs git stash and then git switch -c token-fix in ~/devel/acme/design-system stops at Needs you, though it committed nothing there.

Alternative: only git commit and git push fail, beside file edits. That would stop less often, at the cost of letting a stash, branch switch or reset in the person’s checkout through silently.

Why this is proposed

The check exists for two harms: a change that bypasses the feature branch and its pull request, and a change mixed in with the person’s other work in their own checkout. A commit or push is the first. Switching branches, stashing, resetting or pulling is the second: the person’s uncommitted work moves or their branch changes under them, with nothing to show for it in any pull request. Recognizing more Git commands costs nothing extra to read, since the transcript records every shell command either way. Shell commands other than Git, such as a script that writes files, stay unseen under either answer.

Source confidence: 80% (impact if wrong: low)

OUT-001Unanswered

Is a ticked confirmation enough to clear Stayed in the workspace?

Yes. The person deals with the change, with the reopened session’s help or by hand, ticks a confirmation on Needs you and presses Check again. Kiln counts every change outside the workspace the transcript records up to the tick as dealt with, and the rest of the check decides as usual.

A change recorded after the tick, such as one the session makes once resumed, fails the check again and needs a new confirmation. Kiln keeps each confirmation in its record, so it outlasts a restart. The confirmation appears only on Needs you, only when this check failed.

Why this is proposed

The check is about what the session did, which can’t become untrue afterwards, so the person has to say they’ve dealt with it. Kiln can’t tell by looking: the checkout may hold the person’s other work too, and a commit pushed from it can’t be taken back. A confirmation is honest about that, and it is one click.

Source confidence: 75% (impact if wrong: low)

05 / SECTION

Finish with one pull request per repository

The PRD still ends at “PR ready for review”, now with one pull request in each repository that changed. The pull requests link to each other and say which to merge first; the person merges.

Key acceptance criteria & mockups

  • The pull-request session opens one pull request in each repository whose feature branch has commits of its own, into that repository’s base branch. A repository with no commits of its own gets none. The session’s check is that every one of those pull requests is open and that it stayed in the workspace. AC-PRS-01
  • Each description names the PRD, links every other pull request, and says where one must merge before another, for example an endpoint before the page that calls it. The order is the session’s reading of the technical design; Kiln doesn’t check it and still merges nothing. AC-PRS-02
  • Complete shows each pull request with its repository, number, title, branches, link, commit count and lines changed. Phase rows say how many repositories each phase pushed to, with worktree, branch and commits by repository in Details, and the terminal names each pull request. AC-PRS-03
  • Running, Paused, Disconnected, Phase detail and v1’s other Needs you screens aren’t redrawn; they follow the nearest of this change’s drawings. AC-SHOW-01
  • Proven on a real PRD kept in a repository with no code, changing at least two code repositories, with one phase changing two and one session adding a repository, every changed repository ending with its own pull request. Repeated on Windows. Separately, a one-repository PRD’s session adds a repository, and a session that edits a repository’s own checkout stops and is cleared by confirmation. AC-PROOF-01

PR-001Unanswered

Does the PRD’s repository get its own pull request when its only changes are the phase documents?

Yes. The PRD’s repository gets a pull request like any other, even when all it carries is the phase documents’ Closed lines and any Superseded by lines the sessions wrote. Example: product gets #12 with the five Closed lines, alongside returns-api #57, storefront #218 and notifications #9.

Alternative: leave its changes on the feature branch for the person to merge by hand.

Why this is proposed

Those lines are how the Enso Method records that a phase was built. Without a pull request they stay on the feature branch, and the PRD’s own documents never show the work as done. A pull request is also the one route into the base branch Kiln is allowed.
