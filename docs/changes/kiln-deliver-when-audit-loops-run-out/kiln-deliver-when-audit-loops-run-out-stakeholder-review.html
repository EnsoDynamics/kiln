Kiln Deliver When Audit Loops Run Out

Kiln builds whatever its closing audits find, stops looking when the loops run out, and delivers.

Kiln runs the Enso Method's build steps without a person at the keyboard. In Kiln 1.3.0, released 16 November, when the delivery audit still finds work after its last loop, Kiln stops and waits, often overnight, with nothing delivered. This change has Kiln build whatever an audit finds, stop auditing once that audit's loops run out, and open the pull request with what is left listed for you. It also has an audit stop a run only for the reasons any Kiln step stops for. The method's own steps do not change.

01 / SECTION

Two limits, and Kiln moves on when they run out

After the planned phases are built, two closing audits check the work. The delivery audit checks that every requirement is built. The test audit checks that each requirement's tests would notice if it broke, grading them; Weak means a test exists but might not notice. Each run of an audit is one loop, and Kiln then builds or fixes whatever that run found; building is not a loop. In Kiln 1.3.0, when the delivery audit still finds work after its last loop, Kiln stops and asks. After this change Kiln always does what an audit found, and the limit only decides how many times to look: after the last loop's findings are done, Kiln runs no more audits of that kind and moves on. Nothing about the limit needs deciding, so the 1.3.0 setting that chose between delivering and stopping goes away, along with its stop page.

Key acceptance criteria & mockups

  • Two settings, Max delivery audit loops and Max test audit loops, each 4 by default and changeable during a run. Kiln 1.3.0's third setting, After the last test audit loop, is removed, along with the sentence accepting Weak test rows. Source
  • Everything an audit finds is built or fixed, whatever the loop count, test fixes taking as many sessions as they need. After an audit's last loop, no audit of that kind runs again: Kiln goes from the delivery audit to the test audit, and from the test audit to the pull request, so the last loop's own work is not audited again. Source
  • Kiln never stops because a limit is reached. Kiln 1.3.0's loop stop page, with its Allow N more loops and Accept what is left and deliver controls, is removed. The status line names the audit and its loop, such as “Delivery audit loop 2 of 4”, and a phase as for any phase, such as “Building Phase 10”. Source

02 / SECTION

What a delivered run tells you

When the run delivers, the pull request description and the finished page open with For you: everything still open that a person should handle before the work lands. That can be a test gap the test fixes could not close, behavior the code changed beyond what the requirements say, a blocker you chose to carry on past at a stop, a critical finding, or an action to take after release. Then they say how many loops of each audit ran, with no warning attached. kiln status, the command-line view of the same run, shows the same. Kiln never merges its own pull request, so you decide on each listed item before merging.

Key acceptance criteria & mockups

  • The pull request description opens with For you when it lists anything, then the loop counts, such as “Delivery audit: 4 of 4 loops. Test audit: 2 of 4 loops.” If a pull request is already open, even one opened outside Kiln, Kiln writes For you and the loop counts into its description before the run completes. Source
  • The finished page and kiln status show the same loop counts and For you. A critical finding puts For you first, at the top of the page, with that finding at its top. Source · 2
  • Kiln never reports work as done that it did not do. A test still missing, failing or Weak after the last test audit's fixes is listed, not hidden or accepted. Source

03 / SECTION

When Kiln still stops for you

Any step Kiln runs, a phase build or either audit, stops the run at Needs you when the work cannot go on: a blocker, such as an expired key the remaining work needs, or a business question nobody can answer with even 20% confidence. That is already how phase builds behave. An audit was different: it finishes and lists items for a person, and today any item it lists keeps the run from delivering, even one that needs no one. After this change an audit stops for the same reasons as any other step, and the page says Kiln needs you for one thing, whichever step found it. A critical finding is a problem serious enough that it must not ship unnoticed, such as a job that charges a declined card on every retry. A blocker holds the run: Kiln finishes all the work that doesn't need it, then stops. You can press Check again to have Kiln re-check; if you have provided the item yourself, outside Kiln, Continue anyway carries on to delivery. Only you can press it; Kiln never carries on past a blocker by itself. Each item you carry on past is recorded as waived, never as settled, and stays listed under For you.

Key acceptance criteria & mockups

  • Stops at once: a critical finding that Kiln's next step would cause or worsen. Holds the run: a blocker, or a business question nobody can answer with even 20% confidence. Goes on and is reported with the delivery: any other critical finding (listed first), a test gap, behavior changed beyond what the requirements say, and an action for a person that no remaining work needs. An assumption the requirements already state, or a request to confirm or review something, is never an item. Source
  • Every item says its kind, the problem and what you do, and, when it stops or holds the run, what waits on it. Kiln rejects an audit report that leaves these out. Source
