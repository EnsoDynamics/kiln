# Technical Design: Kiln Deliver When Audit Loops Run Out

**PRD:** [Kiln Deliver When Audit Loops Run Out](kiln-deliver-when-audit-loops-run-out-prd.md) · **Assumptions:** [two to confirm, two decided by the team](kiln-deliver-when-audit-loops-run-out-assumptions.md) · **Mockup:** [eight screen states](mockups/kiln-deliver-when-audit-loops-run-out.html)

## Overview

The loop gate gains a third decision beside "start the loop" and "stop": **set the phases aside**. Phases an audit added past the delivery limit are recorded in Kiln's own state as left open, skipped by routing, and reported with the delivery. The one setting **When the loops run out** chooses between setting aside and stopping, for both audits.

The audit report says two things it did not say before, and Kiln acts on both without judging either: how much of each criterion an added phase covers is built, and what kind of item each thing listed for a person is. An item's kind decides whether it stops the run, holds it, or rides to delivery under **For you**. A loop stop gets one page with two answers, Allow and Accept, at either audit. A run delivered with phases left open can be continued on its own feature branch while its pull requests are open.

Everything here is Kiln's. No Enso Method skill changes: both audit skills already leave out a criterion an open completion phase covers, and Kiln writes nothing to the repository that the skills do not already write (principles 1 and 2).

## Existing Code

**Posture: Preserve.** Kiln 1.3.0 is released with audit loop limits.

- Reused: the loop ledger and its `start` epochs; the gate as the one place every decision after an audit passes through; `loop_limit` stops on a finished audit's key and the derived `needs_you` loop stop; the version-2 report and its admission; the outstanding-items ledger, derived from accepted reports; the Accept session and its prompt; the control journal, its receipts and the stop routes; the continuation proposal, acceptance and activation core.
- Not reused: the waiver closures (`effectivePlan`, `effectiveRecordedClosed` and the engine's own waiver check). They count a waived or skipped leaf as closed, and that reading also feeds the phases-done counts and the continuation baseline's completed phases, where a phase set aside must read not started and never completed. Set aside is a predicate of its own (§Phases Left Open).
- Kept: test work still saved after the last test loop stops the run under either choice. Mark complete is offered only where a check fails. A `needs_you` report is never accepted. Marking an audit complete settles no item, and a run delivered after one lists every item still open.
- Kept: the default limits, and every stop control this design does not name.

## Settings (AC-CHOICE-01, AC-CHOICE-02)

The third loop setting is renamed where it is stored, because its old name says it is about the test audit only. Where it is exchanged, the new name joins the released one (§Interfaces).

```
auditLoops:
  deliveryLimit, testLimit              — unchanged
  whenLoopsRunOut: "deliver" | "stop_and_ask"     — default deliver; was afterLastTest
  whenLoopsRunOutSource                 — was afterLastTestSource, same shape
```

`deliver` keeps the sentence the old default gave the test audit, quoted with its source as today. The setting is read fresh at each gate decision. A change at a loop stop therefore applies the next time loops run out, and the stop it was changed at stays until one of its two answers is given (§Loop Stops); at that stop the choice's note in the run's settings says so (mockup state 4). Reading it fresh is also why neither Check again nor a restart re-decides a loop stop: at a stop whose audit has not finished they only read its report again (§Loop Stops). While phases set aside by the setting are left open, no loop stop holds the delivery limit and no pull request session has started, the delivery limit's field in the run's settings, and `kiln settings`, say that raising it builds them at Kiln's next decision whether to start a loop (§The Loop Gate, LOOP-002).

## Report Contract (AC-GOON-03, AC-ITEM-01, AC-ITEM-02, AC-LEFT-01)

The report stays `schemaVersion` 2 with added fields. Kiln does not parse prose or phase documents to learn any of this; the audit states it and the prompt maps the skill's own ending onto it (§Prompts).

```
phaseCriteria: { phase, criterion, built: "partly" | "none" }[]
    — required when completionPhases is non-empty: every criterion each appended phase covers,
      and whether some of it is built or none of it is; `built` describes the criterion as the
      audit graded it, not the phase's share of it, so every row naming one criterion agrees
acceptedTests?: { criterion, state: "weak" | "missing" | "failing" }[]
    — test audits: every criterion whose tests the person's words have accepted and that is
      still below the audit's target as this report stands
needsYou entry:
  id?            — an outstanding item listed again
  kind           — "critical_next_step" | "critical" | "blocker" | "business_question"
                   | "test_acceptance" | "other"
  problem, action
  waitsOn        — what waits on it; required for every kind but critical and other
  criterion      — required for test_acceptance: the criterion whose test it is
  stuck?: true   — test_acceptance only: the row is stuck as this report stands
```

Admission refuses, naming the field, a new report that:

- lists a new item with no `kind`, or relists by `id` an item the ledger holds without one and still gives none;
- is `needs_you` and lists no item whose kind, as given or kept from the ledger, is `critical_next_step`, `blocker`, `business_question` or `test_acceptance`: items of riding kinds leave the work able to go on, so the report gives the outcome the audit reached, with them listed. The released refusal of a `needs_you` report with an empty `needsYou` stands;
- gives a stopping or holding kind without `waitsOn`, or `test_acceptance` without `criterion`, each judged on the item as it stands after the relisting: a field the relisting leaves out takes the ledger's value, so a relisting by `id` needs only `id`, `problem` and `action`;
- appends phases without a `phaseCriteria` row for each, or names a phase there that it did not append;
- lists a `critical_next_step` item under any outcome but `needs_you`;
- is a delivery audit's report that gives the kind `test_acceptance` or gives `acceptedTests`: only a test audit grades tests. An item already of that kind, relisted by `id`, keeps it and goes on to the next test audit, and does not count as a holding item for the `needs_you` rule above;
- is a test audit's `passed` report with `changedImplementation` false, the one report that leads straight to delivery, and lists a `blocker`, `business_question` or `test_acceptance` item.

Two earlier refusals are lifted. A `passed` report may list a new item of kind `critical` or `other`, and the report that leads straight to delivery may list items of those two kinds; both ride to delivery (§Items for a Person). An item that gives no `waitsOn` and needs none is reported as it stands.

`PersonItem` gains `kind` and `waitsOn`, kept across a relisting by `id` unless the relisting gives a new value, as `criterion` is, and `stuck`, which each listing states again: a relisting that leaves it out clears it.

A result accepted by an earlier Kiln has none of these fields. Its phases read as "the audit did not say" (§Phases Left Open) and its outstanding items take a kind at their next relisting.

## Items for a Person (AC-ITEM-01 to AC-ITEM-03)

| Kind | Kiln |
|---|---|
| `critical_next_step` | Arrives only as `needs_you`: the run stops at once, at an item stop |
| `critical` | Rides. Listed first under **For you** at delivery |
| `blocker`, `business_question` | Holds the run |
| `test_acceptance` | Holds the run; once no test loop is left, its stop is a loop stop, unless its report appends phases |
| `other` | Rides. Listed under **For you** at delivery |

**How a hold is measured.** Kiln keeps the measure it has today: the audit that lists or relists an item says, through its outcome, whether the work it leaves depends on it. `completion_phases` or `continue_test` with the item listed means that work does not need it, so the loop runs; `needs_you` means the work cannot go on. Delivery always needs a holding item, which admission enforces on the one report that leads to it. So a holding item stops the run exactly when no other work is left, and the measure is taken again by every later report, including the one from a session Allow or Accept starts. Kiln carries no dependency model of its own, which would be a second source of truth beside the audit's. Admission refuses a `needs_you` report with no stopping or holding item (§Report Contract), so every item stop holds something, and an `items_listed` loop stop always has a test for the person to accept, except on a report from before kinds (§Upgrade).

**When the waiting work is set aside.** A `blocker` or `business_question` whose waiting work is only phases Kiln has since set aside no longer waits on anything Kiln will do in this run, so by the PRD's table it is a person's action reported with the delivery. So is a `test_acceptance` item whose criterion a set-aside phase covers: the skills leave that criterion out while the phase is open, so no audit in this run grades its tests again. The audit that next accounts for either relists it by `id` as `other`, keeping its problem and action, and with no `stuck`, which only `test_acceptance` gives. Without this, the report that leads to delivery could not list it and would have to stop the run for work Kiln has already decided not to do, or for a test no audit looked at.

The stop for a holding item is therefore always on a `needs_you` report, whose activity is unsettled: Reply reaches the audit's own session, which accounts for the settled item in its next report. A person who marks that audit complete overrides the hold, as today; the items still open are then listed under **For you**.

**Item stops and loop stops.** A `needs_you` test report with no test loop left is a loop stop only when it appends no phase and every item of a stopping or holding kind it lists is `test_acceptance`. One that appends phases is an item stop, as AC-TEST-02 in Kiln Audit Loop Limits gives: its outcome says those phases cannot go on without an item, which no test loop settles, and Accept could not report `passed` while they are open. Once that audit settles, by Reply or Mark complete, its phases go through the delivery gate as any appended phases do (§The Loop Gate). One that appends no phase but lists any `critical_next_step`, `blocker` or `business_question` item is an item stop too; once that item is settled and the audit reports again, the stop becomes a loop stop if tests are still left. Either item stop is the page of mockup state 7, with the controls an item stop has while loops are left, and no Allow or Accept. This keeps Allow from ever starting work an item on the same page says cannot go on, and puts a critical finding ahead of the loop question. A loop stop on a finished audit (phases added, test work saved) shows every item its report listed beside its answers; those items do not block the answers, because that report's outcome already said its work does not need them. The one exception is a stop held on a report from before kinds (§Upgrade).

**On the same branch.** A `same_branch` activation writes `completionAudits.carried`: the completed execution's outstanding items, taken at activation from its archived, immutable results. Only kinds that ride are carried (`critical`, `other`, and items from before kinds existed). Accepted tests are not carried. Each keeps its id, kind, `waitsOn`, criterion and listing activity, and is labelled "…, earlier delivery". `personItems` reads the record and starts its ledger from `carried`, so every caller gets them. New ids continue after the highest carried one. The first audit gets them as outstanding and relists or settles them by id. Until an audit settles one, it stays under **For you**. The earlier delivery's settled items and after-delivery actions are not carried. A requirement-placed action is listed again by the new audits, which run against the same requirements, and any other action is an `other` item, which carries. The copy is stored so it stays exact and no read of the run reaches into the archive.

Every stop on an audit, and `kiln status`, show each item with its kind, problem, action and what waits on it (§Interfaces).

## Phases Left Open (AC-GOON-01 to AC-GOON-04)

The ledger gains, append-only:

```
leftOpen: { auditKey, phases: string[], at: ISO-8601 UTC,
            cause: "setting" | "accepted", via?: "browser" | "command_line",
            endedAt?: ISO-8601 UTC }[]
```

A leaf at or under a phase in an entry with no `endedAt` is **set aside**: not to be built in this execution, and not closed. So is a leaf whose Phase dependencies name a set-aside phase, whoever added it. That is derived, transitively, each time the predicate is asked, never stored, and carries no `cause`. Only the ids `dependencyIds` parses count, as the plan start check reads them; prose in the dependencies, or a phase's own, ancestor or descendant id, sets nothing aside. The ids come from the plan the caller holds: a plan it read, an audit snapshot's phase content, or the recorded plan. The recorded plan gains `dependencies?: string[]` per phase, written when the plan is recorded and kept by the order source, and left out of the plan-structure comparison as Attended is, so a plan recorded by an earlier Kiln still matches its baseline. Allow at a delivery stop ends, or splits, the entries §Loop Stops gives (LOOP-003), and so does a delivery limit raised while no loop stop holds it and no pull request session is recorded (§The Loop Gate, LOOP-002), and so does the gate when it starts a settled audit's delivery loop while any of that audit's appended phases are set aside only by dependency, for every set-aside entry, `setting` or `accepted`, holding a phase they depend on (§The Loop Gate), so a dependent of their phases rejoins and is built in plan order in the loop that follows. Accept and the setting set it aside with the phase it depends on, and `{{setAside}}` names it.

One predicate over the ledger and those dependencies answers it, and every place that decides what to build next or whether the work is finished asks it beside the closure checks it asks today:

- Leaf selection skips it, wherever the engine looks for the next open leaf. A phase a person adds during the run with no dependency on a set-aside phase is still built in plan order.
- Report validation's no-open-phase rules for `passed` and `continue_test` do not count it, so the test audit and any later delivery audit can end normally with it open. The skills leave its criteria out on their own.
- The page's next-leaf marker and the terminal summary line's next phase skip it, and the plan's pull request row appears once every leaf is closed or set aside, so a delivered run with phases left open shows its delivery row.
- The final check that no unfinished leaf remains does not count it, and its development-delivery obligations are not asked for. Development-delivery finalization's refusals unless every leaf is closed skip it too.
- It is never done. The phases-done counts on the page, in the terminal summary line and in `kiln status`, and the continuation baseline's completed phases, do not ask this predicate, so it counts as neither done nor waived there. Its plan row reads not started, with a note that it was left open over the limit, or, for a dependent, "left open: depends on Phase N". Kiln writes nothing to the repository: no Closed line, no checkbox, no record file.

The predicate covers only a leaf that is not closed. A leaf in an open entry that a person closes by hand during the run counts by today's closure rules, and the work left does not list it.

**Routing after phases are set aside.** A delivery audit whose appended phases are all set aside, once the gate has decided on it, routes as `passed`, so the test audit follows. A test audit in the same position keeps today's routing for a `completion_phases` test report with nothing built since: a delivery audit first if it changed implementation, then a fresh test audit round, which is not a loop. A test audit may add phases and still have test work unfinished, and its one outcome cannot say both, so counting it as passed could deliver with test work nobody reported; the fresh round asks. Each further round must append a new phase to repeat this, so the number of criteria bounds it.

## The Loop Gate (AC-GOON-01, AC-GOON-03, AC-ITEM-03)

The gate's rows change as follows; rows not listed stand.

| Situation | Gate |
|---|---|
| The next leaf starts a delivery loop and none is left, under `stop_and_ask` | Delivery loop stop, as today; its page names the criteria the appending audit's `phaseCriteria` gives as `none`, or says the audit did not say (`stop.notBuilt`) |
| The same, under `deliver` | Reads the appending audit's `phaseCriteria`. Every row `partly`: appends a `leftOpen` entry with `cause: "setting"` and decides again. Any row `none`, or no `phaseCriteria` at all (a result from an earlier Kiln, or an audit marked complete with no report): delivery loop stop, whose page names those criteria or says the audit did not say |
| Any of a settled audit's appended phases are set aside only by dependency, with no delivery loop, `leftOpen` entry or allowance naming them, whether or not another of its appended phases is the next open leaf | Decided after the raised-limit row and before the first two rows, once for all that audit's appended phases: its first appended leaf in plan order goes through the first row as if it were next. Loop left: count it, end or split every set-aside entry, `setting` or `accepted`, holding a phase any of those phases depend on, transitively, and record the allowance a raise records (no `heldAuditKey` or `count`, `limit` unchanged) with those appended phases and every phase they depend on in those entries in `phases`, so that one loop builds them all in plan order. Under `stop_and_ask`: delivery loop stop. Under `deliver`: the `phaseCriteria` check covers every appended phase; every row `partly` gives a `setting` entry for all of them; any `none`, or no rows, is a delivery loop stop |
| The latest test audit was accepted as `passed` while listing items, and no test loop is left | No stop. Its items are of riding kinds, or it leads to another audit that accounts for them |
| A `needs_you` test report, no test loop left | Item stop when it appends phases; otherwise loop stop or item stop, by its items' kinds (§Items for a Person) |
| An open `leftOpen` entry with `cause: "setting"`, the delivery limit now above the loops used, and no pull request session recorded | Ends or splits the entries as Allow would and appends the allowance §Loop Stops gives a raise (LOOP-003), then starts the delivery loop once no audit is running (LOOP-002) |
| A leaf in the latest delivery allowance's `phases` | Joins the loop that allowance started; the first such leaf counts it, or stops the run as the delivery loop stop when a lowered limit leaves none |

Once a pull request session is recorded, the row no longer applies in this execution, Check again and the route back to the audits after a stale-audits check included. A raise then only changes the limit, which carries into a continuation (§Continuing), and Continue offers the phases after delivery.

So no appended phase of a settled audit is built, set aside or stopped on apart from the others: a phase set aside only by dependency is built with the phases it depends on when their loop starts, as LOOP-003 has Allow build it. The raised-limit row decides first because its allowance names the setting's phases and their dependents, whoever added them, so the dependency row no longer applies to them. The dependency row ends `setting` entries as well as `accepted` ones because a `setting` entry exists only because no loop was left, which is why Allow ends them too, and so every loop it counts builds the phases it names.

The decision stays a pure function of the record, the settings and the effective results. Setting aside and recording the stop are each one record write.

## Loop Stops (AC-ANSWER-01 to AC-ANSWER-05, AC-CHOICE-02)

`PhaseStop.loop.reason` keeps its three released values. `phases_added` and `test_work_saved` are stored on a finished audit's key, as today. `items_listed` keeps its released meaning, a test loop stop whose report saved no test work. It now comes only from a `needs_you` test report that appends no phase and whose stopping or holding items are all `test_acceptance` (§Items for a Person), whose audit has not finished, or, only for an `allowed` epoch recorded before the upgrade, from that Allow's loop when a lowered limit then refuses it (§Upgrade), held on the accepted `passed` report that Allow answered, whose audit has finished. Apart from that case it is no longer stored on an accepted `passed` report, which now holds nothing, and the upgrade clears any such stop (§Upgrade). Kiln tells a stop whose audit has finished from one whose audit has not by `auditFinished`, never by the reason. The page heads this stop **Tests are left for you to accept.**

**A loop stop is answered only by its answers.** At every loop stop:

- Check again is offered only at a stop whose audit has not finished (`auditFinished` false, which only the `items_listed` stop on a `needs_you` report is; the `items_listed` stop a pre-upgrade `allowed` epoch leaves is on a finished `passed` report, a `loop_limit` stop like the other two). There it reruns that audit's completion checks, reading its report again as a restart does, so a report rewritten in a terminal handoff is picked up. It never reruns the gate and the limit stays held. A report admitted by that check then goes through the gate like any other. At a `loop_limit` stop, `check-again` is listed unavailable with the reason.
- A restart leaves a stop whose audit has finished as it found it, without rerunning the gate. At one whose audit has not finished, it reads the report again, as Check again does.
- `kiln settings` and the page refuse to change the limit the stop is on (`limit_held_by_loop_stop`; an instruction that carries it changes nothing). The other limit and the choice stay editable.
- Reply is offered only at a stop whose audit has not finished; `reply` is refused at a `loop_limit` stop, where the audit is settled and nothing would read it. The terminal handoff is unchanged at both.

**Allow up to N more loops** (`allow-more-loops`, `count` ≥ 1) raises that kind's limit to the loops used plus N in the run's settings, where it stays after the stop (§Continuing), appends `allowances: { kind, at, heldAuditKey?, count?, limit, phases? }` to the ledger, and opens no epoch, so the count is kept and the next loop takes the next number. Allow at an `items_listed` stop starts the held audit's session as the loop it allowed, so no test allowance waits for a later audit. Only an `allowed` epoch recorded before the upgrade still marks one (§Upgrade). A delivery allowance's loop is joined by its first leaf (§The Loop Gate). At a delivery stop it also ends every open `leftOpen` entry with `cause: "setting"`, because those phases were set aside only because no loop was left, and Allow leaves loops. The loop builds every phase the held audit appended, those set aside only by dependency included. It also builds each `accepted` phase that a phase the loop builds depends on, and any set-aside phase that one depends on in turn. It ends each `accepted` entry holding such a phase and appends one with that entry's other phases, the same `auditKey`, `at`, `cause` and `via`, so those stay set aside. Other `accepted` entries stay open: the person accepted leaving those phases at an earlier stop, and Continue with N phases offers them after delivery (LOOP-003). Allow records in `phases` every phase the loop will build. A delivery limit raised while no loop stop holds it appends the same record with no `heldAuditKey` or `count`, its `limit` the raised one and `phases` as Allow gives them. The gate counts a leaf at or under a phase in the latest delivery allowance's `phases` in that allowance's loop: the delivery loop started since the allowance whose `activityKeys` hold such a leaf, or, if none has started, a new one while a loop is left. This comes before the join by appending audit, so phases from several audits, and their dependents whoever added them, count as one loop. The loop builds them in plan order and counts once.

**Accept what is left and deliver** (`accept-and-deliver`):

- At a delivery stop, new: one record write appends a `leftOpen` entry for the held audit's phases with `cause: "accepted"`, clears the stop and stamps the receipt, which settles `completed` with outcome `phases_left_open` and records no session started. No session starts and no sentence is quoted. The gate then goes on as after phases set aside by the setting, criteria not built at all included.
- At a test stop, as today, with two changes. Its sentence names only the `test_acceptance` items, each by its criterion. Its prompt lists every other item the held report listed, with its kind, as not accepted by those words and to be kept open in `needsYou`, so later audits and **For you** still account for them. The session's report is admitted like any other, so a holding item still open makes it `needs_you`, an item stop; with only `critical` or `other` items open it reports `passed` and leads to delivery, where they are listed under **For you**.

**The page** (mockup states 4, 5, 6 and 8) is drawn from the snapshot (§Interfaces):

- Status line, at every closing audit, running or stopped: the audit and the loops of its kind used, **Delivery audit (after loop 3 of 3)**, and **(before loop 1)** when none has run. At a delivery stop held on a test audit, the status line names that test audit with the test loops used, **Test audit (before loop 1)** for example, while the heading, `loopHelp` and rows follow the stop's kind: delivery loops, then the waiting delivery loop's row. The lead names the audit that added the work: **The test audit added Phase 12 for a criterion that isn't finished. Building it would be loop 4, and your limit is 3, so Kiln stopped.**
- Heading: **Loop N of M is done.** with what is left: **The audit found more.**, **Test work is left.** or **Tests are left for you to accept.** When the limit was lowered below the loops used, **Loop N is done, over your limit of M.**
- One row per counted loop, then the waiting work as the next loop's row, not started and over the limit. Sessions that are not loops are no longer rows here; they stay in the run's activity list.
- Under the number: the limit it leads to, what the next loop does (at a delivery stop, the phases it builds and the accepted phases that stay open) and that the rest are spare, for example **Loop 4 builds Phase 11 and Phase 12. Phase 10 stays open: you accepted leaving it at an earlier stop, and Continue offers it after delivery.** An accepted phase the loop builds because a built phase depends on it is named among the phases it builds, with why: **Phase 10, which you accepted leaving open, is built too: Phase 12 depends on it.** At a test stop whose only items are stuck rows, the Go on answer says the session cannot work a stuck row without the person saying how.
- One button, labelled for the chosen answer, calls that answer's route.

## What Was Left and For You (AC-LEFT-01, AC-LEFT-02, AC-ITEM-03)

A delivery's work left is derived at the time it is shown, never stored, from the ledger and the immutable accepted results:

- **Phases left open:** each appended phase once, with its `phaseCriteria` rows, and each dependent phase once, with what it depends on, in plan order. **Continue with N phases** still counts leaves. Phases left open are read from the plan recorded when the run delivered, as the finished page's plan rows are. A phase added since delivery is not work this delivery left, and appears only in the Continue offer (§Continuing). An appended phase that also depends on a set-aside phase lists its own rows and adds "depends on Phase N". "no audit assessed its criteria" is only for a dependent no audit appended. Such a dependent has no rows; in the block below its line reads, for example, `- Phase 12 — Refund export: depends on Phase 10, left open; no audit assessed its criteria`. The line saying those criteria's tests were not audited counts only the criteria listed. An appended phase whose adding audit gave no `phaseCriteria` (a result from an earlier Kiln, or an audit marked complete with no report) lists no criteria: its line reads `- Phase 7 — Title: the audit did not say which criteria it covers or how much is built`, and it adds nothing to the tests-not-audited line.
- **Tests accepted:** `acceptedTests` of the latest settled test audit's effective report, then the line the pull request session already gets (the sentences its latest carrying session quoted, with that session's report summary). When `acceptedTests` is empty, the line goes where it goes today, after **Settled during the build**, outside the block. It keeps today's wording and the pull request check does not hold it, whether or not phases were left open.
- **For you:** the items outstanding after the last settled audit, any `critical` first, then the `afterDeliveryActions` of the latest settled delivery audit and the latest settled test audit, whatever outcome each reported, each action text once, compared exactly as given, as the finished page does today. Earlier rounds' lists are history. The separate after-delivery list on the finished page is folded into this one, so a person action appears in one place.

Order is the PRD's: what was left, then **For you**; when **For you** holds a critical finding it moves first with that finding at its top.

**The pull request.** `pullRequestPromptValues` gains one block, built from those three lists; `pull-request-loop-acceptance.txt` moves inside it. The block holds a what-was-left part only when phases were left open or tests were accepted below target, and a **For you** part whenever an item or after-delivery action is open; with neither, Kiln builds no block. The block prints an after-delivery action as its text alone. `pull-request-work-left.txt` wraps the block between two lines, `<!-- kiln:work-left -->` and `<!-- /kiln:work-left -->`, which GitHub stores in the description and does not show, and the session is told to start each description with it word for word. The block reaches both `pull-request-session.txt` and `development-finalization.txt`, which the session gets when delivery authority is set. The **Settled during the build** list carries only settled items; outstanding ones are under **For you**.

The pull request check gains a row, **Pull request says what was left**, run on the open pull request the check already selects in each repository; a repository proven already integrated has no description and no row. Text is normalized by turning every run of whitespace, line breaks included, into one space and trimming both ends. When Kiln built a block, the row passes only when the description, leading whitespace removed, starts with the opening marker, contains it exactly once, and the text between it and the first closing marker after it, normalized, equals the block, normalized. When Kiln built none, the row fails if the description contains the opening marker anywhere. Every repository's description is held to the same block, because the work left belongs to the delivery, not the repository. The check's existing `gh pr list` read adds `body` to the fields it asks for. A session that paraphrases or drops the block stops at Needs you like any failed final check, where Mark complete is offered as for any failed check. This is the first check Kiln makes on a description's content: the lines it prompts for today (settled items, a loop acceptance) are not checked. It is added for this block alone because the claim that nothing is hidden is the point of delivering with work left, and Kiln checks the session's description rather than editing it, so the session stays the one author of the pull request.

**With development deployments on,** the row is a reason inside the development delivery evaluation (Kiln Development Deployments, §One evaluator at every transition). It runs on each repository's remaining review pull request, reading the description from the pull request re-read that evaluation already makes, and holds it to the block by the rules above. A failure names the pull request and the fix, for example `kiln #12: start the description with the work-left block word for word`, and keeps that repository unresolved in `kiln delivery status`, so a finalization session starts to fix it. A checkpoint pull request that has merged is not held to the block. A repository whose work was all delivered or that is unchanged has no review pull request and no row. The PRD repository always has a review pull request when Kiln builds a block, because the audits that produce the block commit there. `development-finalization.txt` tells the session to start each remaining review pull request's description with the block word for word and not to add it to pull requests that have merged.

**The finished page** is headed **Delivered, with work left** only when phases were left open or tests were accepted below target, the two lists AC-LEFT-01 gives, and then shows those lists with the loops used of each kind (mockup state 2). When neither list holds anything, the page keeps the heading it has today (AC-DISPLAY-03 in Kiln Development Deployments, AC-PRS-03 in Kiln Multi-Repo Delivery), even with items open under **For you**, such as a planned production release or behavior changed outside the requirements. **For you** is shown whenever it holds anything, in the place Remaining human actions has today.

## Continuing (AC-LEFT-03)

**Which way.** For an execution that delivered with phases left open, the completed-plan check first reads the state of each of that delivery's pull requests from GitHub. A repository the delivery recorded as already integrated, such as one delivered by an early merge, counts as merged. All open: the same-branch proposal below. Any merged or closed: today's discovery, awaiting merge included. While the PRD repository's delivered work is not in its delivery base and the base's PRD folder is unchanged since the branch forked, the check reports awaiting merge, whether that repository's pull request is still open beside one that merged or was closed unmerged. Once the work is in the base, discovery runs there, accounting for a left-open leaf as below, and another repository's work still on an open pull request is an earlier prerequisite, judged by the rules of AC-CONTINUE-07 in Kiln Continue Added Phases, as for any continuation. A read that fails makes the check `failed`, with retry and no offer, as any failed source read does.

**Same branch.** The proposal's plan is read from the PRD repository's worktree at its HEAD. The feature branch is the only place the left-open phase documents exist until a merge, so it is the plan's source of truth; a phase added since delivery counts once it is committed there. Each repository the completed execution set up is judged by the folder check's predicate (Kiln Missing Worktree Recovery, "The 'run's worktree' predicate"). It must be in place, on the feature branch and clean; untracked files count, ignored files do not. Where it has a pull request, its HEAD must equal origin's feature tip or descend from it, and the pull request's head, read with its state, must equal that tip. Origin is read directly, never through a tracking ref. Commits not yet pushed since delivery, such as a committed added phase, are expected; the first phase session pushes them. Anything else makes the proposal `blocked` with no offer to Continue. The problem names the repository, its saved folder and the fix: commit or remove changes, check out the feature branch, pull when behind, or merge when diverged. A pull request head that differs from origin's tip clears on Check for new phases. Kiln never resets, rebases or force-pushes. A failed read makes the check `failed`, with retry. A missing worktree's problem says Kiln continues only in the run's own worktree and gives the restore commands AC-SETUP-06 shows, built and gated as Folder missing builds them: `git -C <shared checkout> worktree add -f <saved folder> <feature branch>`, after `git -C <shared checkout> fetch origin <feature branch>` when only origin has the branch. The `-f` is needed while git still records the missing folder. When that rule offers no command, the problem gives its reason instead. A folder that holds something else is described with no command, and one Kiln cannot read says what it could not read. Each problem ends "then press Check for new phases or run `kiln check-for-new-phases`". Kiln repairs nothing itself and offers no Folder missing setup for a finished run. A phase that names a repository the completed execution did not set up does not block. The same-branch proposal neither judges nor binds that repository, and acceptance does not set it up. The continued execution adds it on the run's feature branch, in the run's workspace folder, when its phase starts, exactly as AC-ADD-04 in Kiln Multi-Repo Delivery gives. A failure stops that phase at Needs you, and Check again or `kiln run` tries the addition again. The check still reads the shared checkout and the delivery base, as discovery does, but judges only the PRD folder's seed documents (each phase document, the PRD, and each Markdown file whose name holds `technical-design`, `assumptions` or `phase-plan`). Documents they link to, and other files in the folder, do not count. Each source has its own fork point with the feature branch's HEAD: `merge-base` with origin's base tip for the delivery base, and `merge-base` with the shared checkout's HEAD for the shared checkout. So a shared checkout not pulled since before the fork counts only its uncommitted edits (untracked included) and its commits the branch lacks. A document has changed on a source when its normalized copy there differs from its normalized copy at that fork point, or exists only there. A document the source lacks does not block. A changed document is already on the branch when the branch holds the same normalized copy, or when `git merge-file -p` of the branch's, fork point's and source's copies (an absent copy read as empty) exits 0 and prints the branch's copy byte for byte. Any changed document not already on the branch makes the proposal `blocked`. Its problem names each document and source, and says to merge the delivery base into the feature branch or commit the change there. A cherry-pick that touches lines next to the branch's own edits to that document still blocks, as a merge would conflict there; a merge clears it. Kiln does not merge the base into the branch to settle it, and does not continue with only the branch's phases. The three-way check was chosen over clearing only on a merge, because the feature branch usually edits its own design as it is built, so an identical-copy rule would never clear a change the person copied over.

The plan is compared with the completed execution's baseline by the existing rules. Prerequisites are judged on the feature branch, not the delivery base. A carried leaf is `on_feature_branch` when each repository's receipt revision is in that worktree's HEAD. A leaf skipped on a waiver has no work to check and carries on its waiver. In this mode only these count for the first leaf's dependencies and for acceptance. A leaf Closed on the branch without a Kiln receipt is blocked — that covers a left-open phase closed by hand and a phase added already Closed — and the problem says to remove the Closed line so Kiln builds it, or to continue once the pull requests merge, with its External completion evidence. A same-branch proposal has no preparation, so a first open leaf with a preparation instruction blocks with "continue once the pull requests merge". The offer lists the left-open leaves, those set aside for their dependencies included, then any added since, and N counts them all. With nothing left to build, there is no offer.

`ContinuationProposal` gains `mode: "same_branch" | "fresh_base"` (absent on older proposals, read as `fresh_base`). A same-branch proposal's identity binds, per repository, the worktree HEAD, origin's tip and the pull request's number and head, along with the settings digest. Acceptance re-reads these and refuses with `proposal_changed` if any moved. It then activates a fresh execution through the shared activation core. The completed execution's repositories, worktrees, branch and settings are kept unchanged, and so is its development authorization, minus `activationRecovery` (**The development record**, below). The new execution's repository entries are the completed execution's entries as recorded, not the proposal's repositories, so a repository the plan names that they lack has no entry until its phase adds it. There is no workspace preparation, no new branch or folder, and no integration stamped on receipts whose work is not yet in the delivery base. Development deployments and the person's early-merge grants carry, as a Start from the base branch on the Folder missing page carries them (DEV-001). Acceptance's setup-identity check (a `-continue-<execution id>` feature branch and a fresh canonical workspace per repository) applies to `fresh_base` proposals only; a `same_branch` acceptance is checked against the completed execution's branch and worktrees. The baseline carries the completed execution's receipts as they are. A left-open leaf carries none, so in the new execution it is an ordinary open leaf: built in plan order, with no loop counted, because no audit of this execution added it. The fresh execution starts with a preflight, a `start` ledger and empty required audits, which is what makes the loop counts start at zero and the closing audits run again.

**The development record.** On a `same_branch` acceptance, the new execution's development ledger is a copy of the completed execution's; the archived one is unchanged. The copy keeps the checkpoints unchanged, each still stamped with the execution that recorded it. It also keeps the phase-owned assessments and assignments, `accepted`, `splits` and `revision`. It drops audit-owned assessments and assignments and `acceptedAudits`: those audits have finished. It drops what each evaluation recomputes: `repositoryResults`, `currentComplete`, `checkedAt`, `sourceUnavailable` and `lastReadError`. The authorization is the completed execution's, with `enabled`, `grants` and `revision`, minus `activationRecovery`. A checkpoint recorded by an earlier execution is valid when its `executionId` names a row in `continuation.executions`. Its audit owner is not looked up among this execution's audits, and neither is the `originOwner` of a split assignment on it. Only a replacement checkpoint can change it. Command evidence on such a checkpoint stands as recorded, since that session has ended. Its merge and GitHub evidence are read again. The final check judges an earlier checkpoint only as a prerequisite of this execution's checkpoints, or through an obligation assigned to a leaf this execution builds. Otherwise it stands as the earlier delivery accepted it, waivers included. Leaves the baseline carries as completed or skipped on a waiver count as closed, owing no evidence, as in every other scan of leaves. A `fresh_base` acceptance and a base-branch start keep an empty ledger.

**Loop limits, in either mode.** Allow writes the raised limit into the run's settings, and a continuation copies the run's settings as they stand, on the same branch and from a fresh base alike, so a raised limit carries into the continued execution, where the counts start at zero (LOOP-001): chose 3, used 3, allowed 2, and the continued run has a limit of 5. This keeps AC-LOOP-04 in Kiln Audit Loop Limits, under which the settings carry over unchanged. The finished run's settings show both limits, and a change there before Continue refreshes the offer, because the proposal binds the settings digest.

**Its delivery record.** The completed execution's archived row keeps the deliveries it had when archived. The new execution starts with no pull requests, merged branches or delivery history of its own; its final delivery finds each pull request open and updates it, or, if it has since merged or closed, opens a new one as any delivery does; the check holds that one. It opens one for any repository added since, and its pull request check records them and holds each description to the new delivery's work left (§What Was Left and For You). Duplicate URLs are removed within each execution's deliveries, as today; nothing is unique across executions. History shows the pull request under the earlier execution as an earlier delivery, and on the current page as this execution's, with no new label. `kiln status` reports only the current execution's pull requests, so nothing is counted twice. Once the pull request merges, the current execution's delivery history counts only the commits of the phases it built and marks the pull request as also containing other commits, the earlier execution's. An added repository's pull request holds only this execution's commits.

**A left-open leaf in accounting.** The baseline already holds a left-open leaf as open, with no completion row. The rule to lift is in accounting, in both modes: a leaf the completed execution left set aside, whether its ledger names it or it depends on one that does (its ledger read with the dependencies in its recorded plan), is judged as if added since delivery, not as unresolved earlier work. Open, it is new unfinished work. Closed by hand, it needs External completion evidence (on the same branch it blocks instead, above). Removed, it is dropped, not counted as lost completed work.

**The offer** appears under **Delivered, with work left** in place of **New phases found** whenever the delivery left phases open.

## Prompts

- `audit-session.txt`: the contract fields above. The item kinds are defined in the PRD's words, with what is never an item: a declared assumption, a request to confirm or review something, and anything the audit can settle itself. An action the requirements place after delivery goes in `afterDeliveryActions` and is never also an item; any other person action that no remaining work needs is an `other` item. The outcome guidance is rewritten around the kinds: `needs_you` when the audit's remaining work cannot go on without an item, when a critical finding would be caused or worsened by the step Kiln takes next (the prompt names that step for each outcome), or when the report would lead to delivery with a holding item open. A new `{{setAside}}` line names the phases Kiln has left open, says they do not count against a passing report, and says to relist as `other` an item whose waiting work is only those phases, and a `test_acceptance` item whose criterion one of those phases covers (§Items for a Person). For `phaseCriteria`, the prompt maps the skill's own status for each criterion an appended phase covers: `none` only when no code does any part of it (the delivery or test audit's Not implemented), and `partly` for every other gap (Partly implemented, or a test audit's criterion broken in a way bigger than the test work left, since broken code still does part of it). The released line asking for `needs_you` when the audit ended normally but lists something for a person is dropped: a critical finding that Kiln's next step would not cause or worsen is listed as `critical`, and the audit reports the outcome it reaches.
- `audit-loop-limits.txt`: the choice's new name.
- `audit-accept.txt`: the sentence names tests only; the other listed items follow, each with its kind, to be kept open. Its last line becomes: Report "passed" when every item in "needsYou" is of kind "critical" or "other", or it is empty, and "needs_you" when any item is of another kind, judging a relisted item by the kind it gives or, when it gives none, the kind listed above.
- A new `pull-request-work-left.txt` for the block in §What Was Left and For You: start each description with the block word for word, including its first and last lines, which are Kiln's markers rather than template comments and are kept; on any later edit, such as adding links or updating an already open pull request, keep the block first and unchanged, and replace any earlier block between the markers instead of adding a second. The pull request prompt says to update an already open pull request's description and, on a same-branch continuation with nothing left, to remove any earlier block, markers included.

## Interfaces (AC-BOT-01, AC-BOT-02)

**Command line.**

```
kiln settings <prd> [--delivery-audit-loops N] [--test-audit-loops N] [--when-loops-run-out deliver|ask]
kiln allow-more-loops <prd> --loops N --only-if-status-matches <token> --command-id ID
kiln accept-and-deliver <prd> --only-if-status-matches <token> --command-id ID
kiln continue-with-phases <prd> --proposal ID --only-if-status-matches <token> --command-id ID
kiln check-for-new-phases <prd>
```

`--when-loops-run-out` is the flag help and status name. The released `--after-last-test-audit-loop` stays accepted with the same `deliver|ask` values and sets the same one choice, which now covers both audits, as a run's saved choice does at upgrade (SET-001); help lists it as the older name. The settings and status JSON add `when_loops_run_out` (`deliver | stop_and_ask`), `when_loops_run_out_sentence` and `when_loops_run_out_chosen`, and keep emitting `after_last_test_audit_loop` (`deliver_unless_serious | stop_and_ask`), `after_last_test_audit_loop_sentence` and `after_last_test_audit_loop_chosen` with the same choice, so a bot written against protocol 1 reads the same answer it read before. The control journal's `settings` input accepts either key, never both. Dropping the older names is a breaking change for a later major version, not this one.

`continue-with-phases` is a new public action that reaches the engine path the page's Continue already uses, for either proposal mode, with that route's refusals (`proposal_changed`, `prerequisite_blocked` and the rest) and its receipt, keyed by command id and status token as the page sends them. It takes the proposal the status shows, as the page submits the one it displays. Early-merge authorization and retrying a blocked setup stay in the browser.

`kiln check-for-new-phases <prd>` runs the finished page's Check for new phases through `POST /api/control/v1/continuation/check`, which takes no inputs, returns the check and keeps no receipt, as `account --refresh` does. It needs a live controller, is listed among a finished run's controls, and is refused unless the run is finished and idle (`wrong_activity`, `busy`). `kiln status` stays a read and shows the last saved check. A flag on `kiln status` was not taken: a check saves its result and can supersede a pending approval, so it needs its own POST route either way, and a command named after the button is listed with its availability as AC-BOT-01 asks.

Against a controller that does not advertise `deliver_at_loop_limit` (§Interfaces, below the snapshot), the CLI refuses the new commands, the new flag and Accept at a delivery stop (`instance_incompatible`). The older flag works against either.

**Control journal.** `settings` takes `when_loops_run_out` or `after_last_test_audit_loop` with `via`, as it took the old field; saved receipts carrying the old field still validate. `accept-and-deliver` at a delivery stop records `via` in the `leftOpen` entry. New outcome `phases_left_open` and refusal `limit_held_by_loop_stop` are declared in `prompts/kiln-command-contracts.json`. That file's `settings` contract and `docs/kiln-command-line-and-bot-control.md` say "Raising a limit starts nothing by itself"; both now name the exception, a raised delivery limit while phases set aside by the setting are left open and no pull request session has started, which builds them at Kiln's next decision whether to start a loop (§The Loop Gate, LOOP-002).

**HTTP.** The existing settings, allow and accept routes carry the changes; Continue's route is unchanged. The one new route is `POST /api/control/v1/continuation/check`.

**Snapshot and `kiln status`.** The same objects in both, text and JSON, where `auditLoops` is `audit_loops`:

## Upgrade (AC-CHOICE-01)

Schema 24, in the record migration alone:

- `afterLastTest` becomes `whenLoopsRunOut` (`deliver_unless_serious` to `deliver`, `stop_and_ask` unchanged) with its source carried, so a run already going keeps its choice, which now covers both audits. A run begun before audit loop limits keeps `stop_and_ask` and its Kiln-applied source.
- The ledger gains empty `leftOpen` and `allowances`. An existing `allowed` epoch keeps the count it restarted. An Allow recorded before the upgrade as an `allowed` epoch still marks the first test audit after it as the loop it allowed, while no test loop has been counted since; Kiln reads whichever of that epoch and an allowance is later.
- A run stopped at a `loop_limit` stop stays stopped and is answered by its answers; at a delivery stop that now includes Accept. A stored `items_listed` stop on an accepted `passed` report held nothing, so it is cleared and the run carries on as its Check again would have.
- The ledger's `itemsListedStops` is dropped. Only the gate row for an `items_listed` stop on an accepted `passed` report read it, and that stop no longer happens.
- A run stopped on a test audit's `needs_you` report admitted before items had kinds is not re-admitted. An item with no kind, given none and with none in the ledger, counts as neither stopping nor holding, so with no test loop left the stop stays a loop stop with Allow and Accept. Its Accept sentence names every item that has no kind, as the released sentence did, and the Accept prompt lists those items as written. The Accept session's report, like any new report, gives every item a kind.

Schema-23 Kilns refuse schema 24 under the existing newer-schema rule.
