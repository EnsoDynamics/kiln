# Technical Design: Kiln Deliver When Audit Loops Run Out

**PRD:** [Kiln Deliver When Audit Loops Run Out](kiln-deliver-when-audit-loops-run-out-prd.md) · **Assumptions:** [none open](kiln-deliver-when-audit-loops-run-out-assumptions.md) · **Mockup:** [eight screens](mockups/kiln-deliver-when-audit-loops-run-out.html)

## Overview

The loop gate stops being a gate. A loop is now one run of an audit: Kiln counts each delivery audit and each test audit it allocates in the ledger Kiln Audit Loop Limits added, but nothing ever stops for a count. Every finding is built, and a kind whose runs reach its limit is **closed**, which routing reads as "no new audit of this kind". Closing happens inside the one routing function, `auditNext`, so the engine's next-step decision and the pull request step's audit currentness check agree on it. The loop stop, its page, Allow, Accept, the third setting and every acceptance sentence are removed.

Two smaller changes ride with it. Each item an audit lists for a person gains a **kind**, and the kind decides whether it stops the run, holds it short of the pull request, or goes on and is reported under **For you**. And `kiln status` and two new commands cover the finished page's continuation controls.

Everything here is Kiln's. No Enso Method skill changes (principles 1 and 2): the audits already list items for a person; Kiln asks for the kind in its own report contract, and decides by its own count of audit runs when to stop auditing.

## Existing Code

**Posture: Preserve** for everything in Kiln 1.3.0 this design does not name; **removed** for the loop stop machinery below, which this PRD retires.

- Reused: the loop ledger (`epochs`, `loops`, `appendLoop`, `countedLoops`), now counting audit runs rather than the work on findings (§Loops and the Ledger); activity loop rows; the version-2 report and its admission; the audit and pull request prompt templates; the continuation check and acceptance core; and the control journal with its receipts.
- Reused: `afterDeliveryActions`, with its projection widened from passed reports to every accepted report.
- Changed: the outstanding-items ledger (`personItems`) also reads the `needsYou` and `settled` of the valid report of an audit marked complete (§What each kind does), and the page's waiting count reads the same effective result. The admission test that pins a waiver with no report carrying items over stays valid; a new test covers a waiver with a valid report.
- Removed: the **Remaining human actions** card (`humanActions`), whose actions move to **For you**; the loop gate (`deliveryDecision` and its counting of leaves as loops); the `loop_limit` stop as something the gate records, `loopStop`, `testHold`, `testDecision`'s stop branch, `needsYouLoopStop`, `holds`, `listedItems`, `applyLoopControl`, `loopControl`, `launchAuditAtStop`, the `allow-more-loops` and `accept-and-deliver` actions and routes, `requestedLaunch` of kind `audit`, `itemsListedStops`, `acceptances` and `allowed` epochs; every acceptance sentence and the prompts that carried them (`audit-accept.txt`, `audit-allowed-loops.txt`, `audit-earlier-acceptances.txt`, `audit-loop-limits.txt`, `pull-request-loop-acceptance.txt`), and `sourceText`. A stored `loop_limit` stop is still read, so a saved record loads (§Upgrade).
- Kept: a `needs_you` report is never accepted, Reply and Take over at its stop work as today, and Mark complete is offered only where a check fails.

## Settings (AC-CHOICE-01, AC-CHOICE-02)

```
auditLoops:
  deliveryLimit: integer >= 1          — Max delivery audit loops; default 4
  testLimit: integer >= 1              — Max test audit loops; default 4
```

Each limit is the most runs of that audit a run makes (§Loops and the Ledger). `afterLastTest` and `afterLastTestSource` are gone (§Upgrade). No setting, help text or prompt carries a sentence accepting Weak rows. A continuation copies `Settings` as today.

**When a change applies.** Every routing decision reads the limits in force fresh (§Loops and the Ledger), so before `atPullRequest` is written a change applies at Kiln's next decision whether to run an audit of that kind. Once it is written, the change is still saved to `Settings`, but no decision in this execution reads it: it applies to a continuation accepted after the change, which copies `Settings`, and the run's settings panel and `kiln settings` say so.

**The floor.** A limit is refused below its kind's **floor**, as a field error on the page and `invalid_input` on the command line. The floor is the runs of that audit already made in this execution, the one under way included: the loops of that kind in the ledger, since a run is counted when its audit is allocated (§Loops and the Ledger). The message gives the floor and says so. Setting a limit to its floor while that audit runs makes that run the last; its findings are still built. Once `atPullRequest` is written, the floor of both kinds is 1: no decision in this execution reads `Settings` again, and a continuation starts with an empty ledger, so the field only has to be a whole number of 1 or more. The snapshot and `kiln status` give the floor, 1 included, so the page can set the field's minimum.

## Loops and the Ledger (AC-LAST-01, AC-LAST-02, AC-LAST-05)

The ledger keeps its container and changes what a loop records:

```
AuditLoopLedger:
  epochs                               — unchanged; only `start` epochs are written
  loops: AuditLoop[]
  atPullRequest?: { at, deliveryLimit, testLimit }   — the limits held for the rest of the execution (below)

AuditLoop:                             — one run of an audit
  kind: "delivery" | "test"
  number: integer                      — 1-based within its epoch
  startedAt: ISO-8601 UTC
  activityKey: string                  — the audit activity that is this run
```

`acceptances`, `itemsListedStops` and a loop's old fields (`limitAtStart`, `last`, `sourceAuditId`, `activityKeys`, `sessionId`, `firstAttempt`, `observed`) are gone. Nothing reads a loop's own limit or a last-loop flag: the status line and **Closing audits** compute "n of L" from the limits in force.

A kind is **closed** when its loops reach its limit in force (below): Kiln allocates no new audit of that kind. An audit already allocated still runs, resumes and is answered at its stops as today, and its findings are built. A kind with no loop is never closed, because every limit is at least 1.

`atPullRequest` is written once, when the run's first pull request session is launched, and is never rewritten. Kiln sets it from `Settings` before it builds that session's prompt, so the prompt and the block saved on the session record both read the frozen limits. It is saved in the same save of the run record that adds the new session to the pull request step, before the process starts. A session the billing check then holds, or that a stop or pause keeps from starting, counts as started: its relaunch reuses the record and the frozen limits. If Kiln stops before that save, nothing was recorded, and the next launch freezes the limits then. When the run completes without a pull request session, as Mark final delivery complete at a pull request stop does, and as a run does whose work is already merged or confirmed delivered early in every repository, `atPullRequest` is written in the write that completes it. An upgraded run already past that point gets it from the migration or the ledger rebuild (§Upgrade). When the pull request step's **Current completion audits** row sends the run back to the audits, as it does today when the pull request session's own commits leave an audit no longer current, those audits route on `atPullRequest`. A kind closed under it stays closed, so the row asks only for an audit of a kind with a loop left under it, and that audit counts as one of those loops as usual. A limit changed in this period applies only to a continuation (§Settings, "When a change applies").

**Limits in force.** `limitsInForce(record)` returns `atPullRequest` when present, otherwise the limits in `Settings`. Every read of a limit by a decision or a display of the run goes through it: closure, `{{nextSteps}}`, the status line's `position`, the snapshot's `used`, `limit` and `closed`, the hold stop's Check again, and **Closing audits**. Only the settings panel, `kiln settings`, the snapshot's `settings` and a continuation's copy read `Settings` itself.

**What counts as a loop.** A loop is counted in the write in which `allocateAudit` adds an audit activity Kiln will launch, when it is a delivery audit or a test audit that is not a continuation, so a crash cannot start an audit without counting it. That includes a delivery audit run again because a test audit changed implementation, the fresh test audit after it, and an audit the pull request step's **Current completion audits** row sends the run back to. These are not loops: a continuation (a session of test fixes), building the phases an audit appended, and an audit `completeAuditAtOnce` settles under a waived readiness problem, since no audit session runs. A Reply, Resume, Check again or relaunch after a restart continues the run already counted. So a run whose first delivery audit passes reads delivery 1 of 4.

**Findings are always built (AC-LAST-01).** No leaf and no session of test fixes waits on a loop count: Kiln builds every phase an audit appended and continues saved test work in as many sessions of test fixes as it takes, whatever the counts (§Routing After the Last Loop). The test work ends when a session reports anything but `continue_test`, and a session of test fixes that raised none of the rows it took may not report `continue_test` (§Report contract), so the work always ends.

**Nothing is recorded as done that isn't (AC-LAST-05).** Kiln marks nothing built and closes nothing itself: a criterion's state comes only from its sessions' commits, and each test row still missing, failing or Weak when the test work ends reaches **For you** as a `test` item (§Prompts). Kiln accepts no row.

**When a count starts.** As today: a `start` epoch per kind at the first Start, at a continuation's activation and at a base-branch Start from the Folder missing page; nothing else opens one, so a count never starts again during a run (AC-LAST-02).

## Routing After the Last Loop (AC-LAST-03, AC-CHOICE-02)

`AdmissionContext` gains `closed: { delivery: boolean; test: boolean }`, which the engine fills from the ledger and limits. `auditNext` applies it in two places and is otherwise unchanged:

- **Delivery closed.** Wherever `auditNext` would return `delivery_audit` because the latest delivery audit did not pass, is not current, or a test audit changed implementation, it goes on as if that delivery audit had passed and were current.
- **Test closed.** `test_audit` becomes `continue_test` while the latest settled test activity's effective result counts `continue_test`, because saved test work is always worked through, and `final_delivery` otherwise. `continue_test` is unchanged. So is `delivery_audit`: while a delivery loop is left, a delivery audit still runs on a test audit's phases or implementation changes (Method-Neutral Audits AC-NEUTRAL-06 as this PRD replaces it), and after it the closed test kind leads to the pull request.

Closure only ever removes a new audit of the closed kind; the other kind routes as it would. So the work of each kind's last loop is never audited again by that kind before the pull request, the cost the PRD's Business Context accepts. `auditStepAfterSettled`, the step after a waived readiness problem, applies the same closure. Because the closing is inside `auditNext`, the pull request step's **Current completion audits** row, which also asks `auditNext`, does not send a finished run back to an audit of a closed kind.

| Situation | `auditNext` with closure |
|---|---|
| Delivery audit loop 4 of 4 reports `completion_phases` | Its phases are built; delivery is closed, so the test audit |
| A test audit's phases built, delivery closed | No delivery audit; the test audit again while a test loop is left, otherwise the pull request |
| The last test audit's phases built, delivery open | The delivery audit, as a delivery loop; after it and its phases, the pull request |
| A `continue_test` report | A session of test fixes, whatever the counts, and again after each that reports `continue_test` |
| A `continue_test` report with `changedImplementation` | Delivery open: the delivery audit, then a fresh test audit as the next test loop when test is open, or a session of test fixes when it is closed. Delivery closed: a session of test fixes |
| A session of test fixes reports `passed` | The pull request; the delivery audit first when it changed implementation and delivery is open |
| A session of test fixes reports `completion_phases` | Its phases are built; then as after any test audit's phases |
| A limit raised after its kind's last loop | Once the activity under way ends, the kind is open again and `auditNext` asks what it would with that limit from the start: an audit of that kind when phases were built or work changed since its latest run (AC-CHOICE-02). With nothing unchecked, the raise changes nothing. After a delivery audit and its phases, the test audit runs only while a test loop is left |
| Either raised after the pull request session started | `atPullRequest` still closes it; the change waits for a continuation |

## Items for a Person (AC-ITEM-01 to AC-ITEM-03)

### Report contract

The report stays `schemaVersion` 2; each `needsYou` entry gains two fields, and the report one:

```
needsYou entry:
  id?, problem, action, criterion?     — unchanged
  kind: "critical_next_step" | "critical" | "blocker" | "business_question" | "test" | "other"
  waitsOn?: string                     — what waits on it
report:
  raised?: string[]                    — on a session of test fixes' `continue_test` report: the criteria whose rows it raised
```

`PersonItem` gains `kind` and `waitsOn`, kept across a relisting by `id` unless the relisting gives a new value, as `criterion` is. So a relisting needs only `id`, `problem` and `action`.

Admission refuses, naming the entry:

- an entry whose kind, as given or kept from the ledger, is missing;
- a `critical_next_step`, `blocker` or `business_question` item without `waitsOn`;
- a `critical_next_step` item no waiver covers under any outcome but `needs_you`;
- a `needs_you` report with no `critical_next_step`, `blocker` or `business_question` item that no waiver covers (§What each kind does): an audit whose items let the work go on reports the outcome it reached. The session corrects it and submits again, as with any refusal, so a waived item never stops the run again;
- a `continue_test` report from a session of test fixes whose `raised` is missing or empty: one that raised none of the rows it took ends the test work, reporting `passed` with each row left as a `test` item (AC-LAST-01).

Two released refusals are lifted: a `passed` report may list new items, and a test audit that changed only tests may list items. Every other item is admitted as it stands.

### What each kind does

| Kind | Effect | How Kiln applies it |
|---|---|---|
| `critical_next_step` | Stops | Arrives only on a `needs_you` report, which is the ordinary Needs you stop; once that audit is marked complete, the item is waived (below) and goes on |
| `blocker`, `business_question` | Holds | See below |
| `critical`, `test`, `other` | Goes on | Stays outstanding; later audits account for it by id as today; listed under **For you** at delivery |

**How a hold is measured.** As today, the audit says through its outcome whether the work it leaves needs the item: `completion_phases` or `continue_test` with a holding item listed means that work does not, so Kiln builds it; `needs_you` means it does. Kiln keeps no dependency model of its own, which would be a second judge beside the audit. Delivery always needs a holding item, so Kiln checks once more before delivery, because with closed kinds no audit may run between the last build and the pull request:

**The hold stop.** The hold check runs at every arrival at `final_delivery`, before anything that can complete the run (the pull request precheck on a pull request already open, and the pull request step's own check), so a holding item listed by an audit the run was sent back to stops the run rather than completing it. While an outstanding item no waiver covers (a **Nothing holds the run** waiver, or the waiver of an audit marked complete whose report listed it, below) is `blocker`, `business_question` or has no kind (from before kinds, §Upgrade), Kiln neither starts the pull request session nor completes the run. The stop is a launch-check stop on the pull request step, recorded and rechecked as the **Completion audit readiness** stop is (`selection` kind), with one failing row, **Nothing holds the run**. It is not a known-problem check, so no waiver matches it by its text. The row is built with one `other` item per holding item: `subject` and `against` are the item's ledger id (`item-<n>`), and `text` is its kind's words, problem, action and what waits on it. Because `against` names the item rather than the feature heads, a waiver still covers it after the pull request session commits and a send-back returns the run here. The row passes when a waiver covers every item. When a later arrival brings a holding item no waiver covers, the row fails again on that item alone: earlier waived items keep their **Waived** tag, and the new waiver saves only the uncovered items. Matching by ledger id is safe because ids are never reused within an execution, and a new execution starts with no waivers and an empty ledger. A relisting under the same id is the same need, whatever its new wording or kind, so its waiver keeps covering it and its **Waived** tag stays; the audit prompt has a need the item does not name listed as a new entry (§Prompts), which holds the run again.

An audit marked complete with a valid report counts as accepted (Completion Waivers AC-WAIVE-12), so `personItems` reads its `needsYou` and `settled` from the audit waiver's result, adding, relisting and settling items as an accepted report does. Its `settled` entries close items, shown under **Settled during the build** with that audit's name. "Marking an audit complete settles nothing" (Method-Neutral Audits AC-NEUTRAL-03) means the waiver itself settles nothing. Marking it complete is the person's answer at the stop AC-ITEM-01 describes: each item that report listed counts as waived by that audit waiver, in the hold check and in admission's uncovered-item rule alike, so it holds nothing and the **Nothing holds the run** row leaves it out, and it stays open under **For you** with that waiver's **Waived** tag. A later relisting under the same id stays covered. With no usable report, every outstanding item carries over to the next audit. An audit row on the page counts its items as waiting until a later audit has an effective result, accepted or waived with a valid report, not only an accepted one.

A pull request session can have run already, when its check sent the run back to the audits. Either way the stop is rechecked and waived without a session: whenever a failing row is **Nothing holds the run**, the offer is **Continue anyway** with effect `continued`, never Mark final delivery complete, so waiving it can never complete the run. The offer and the waiver's effect follow the row, not whether the step has run.

The offer keeps the shape of the **Continue in normal order** offer at a plan or readiness stop, which keeps its label, but its button reads **Continue anyway** and its words are its own. The stop's card heading is **Kiln needs you for one thing** (**for N things** with more), whichever step listed the items, as is the heading of an audit's stop for an item that stops or holds the run; the status line names the step (mockup screens 5 and 5b). Its heading is "You’ve provided what’s listed above, and want Kiln to deliver?" Its sentence is "Continue anyway. Kiln records each item above as waived, never as settled, and starts the pull request session. The items stay open and are listed under **For you**, each marked Waived." The sentence keeps its opening words, because the page and `kiln status` pick out the main paragraph by them. `kiln status` ends the preview with "Kiln would then start the pull request session, with each item under For you as still open and marked Waived.", not the line about a warning on each step. When every repository is already merged or its work confirmed delivered early (§What a Delivered Run Says), the sentence is "Continue anyway. Kiln records each item above as waived, never as settled, and completes the run, because the work is already delivered. The items stay open and are listed under **For you**, each marked Waived." and `kiln status` ends the preview with "Kiln would then complete the run, with each item under For you as still open and marked Waived." As on every Continue offer, the offer names no next activity. Waiving the row writes no `waiverWarning`; the **Waived** tags are the only mark it leaves.

- **Check again** reruns routing, on the limits in force, and the hold check, and clears the stop when nothing holds. Before `atPullRequest` is written, an audit runs only where a raised limit reopens a kind with work for it, such as phases built since its latest run, and that audit can then settle the item. Once it is written, a raised limit reopens nothing, and only an audit of a kind with a loop left under `atPullRequest` can settle the item. With both kinds closed and nothing to audit, no audit can settle it. Continue anyway is usable only after a Check again, as at the **Completion audit readiness** stop (Completion Waivers AC-WAIVE-02): a Check again with nothing able to settle the item keeps the stop, and the offer is then usable.
- **Continue anyway** is the way on without one: the person provides what each item asks outside Kiln, then waives the row with effect `continued`. Kiln records no settlement, because only an audit's report settles an item (Method-Neutral Audits AC-NEUTRAL-03). The waived items hold nothing again, the pull request session starts (or, with every repository already merged or delivered early, the run completes), and they are listed under **For you** as still open, each with its **Waived** tag (§For you; Completion Waivers AC-WAIVE-10). With a pull request already open, on the first arrival or a later one, the pull request session starts: the new **Waived** tags change the block, so the **Pull request description** row (§What a Delivered Run Says) fails until a session delivers it.
- Reply and Take over are not offered: the stop belongs to no session, even when an earlier pull request session ran.

The page is mockup screens 5b and 5c: screen 5 with the pull request step's lead, before and after a Check again.

The audit prompt names the step each outcome leads to (§Prompts), so an audit with nothing left to build and a holding item open reports `needs_you` itself; the hold stop catches the cases it cannot foresee: a blocker listed beside phases that turn out to be the last work, or a limit lowered after it reported.

### For you

**For you** is every item outstanding at delivery, `critical_next_step` and `critical` items first, then the rest in listing order, then the person actions the requirements place after delivery. Those are the actions in `afterDeliveryActions` on the latest accepted report of each kind, whatever its outcome (for a version-1 report, its `pendingHumanActions` beyond delivery with no result), one line each with no kind's words and repeats removed. Each item is one line, built by Kiln and copied word for word into each pull request's description, the finished page and `kiln status` (§What a Delivered Run Says): its kind's words, a colon, its problem, then its action. The words are **Critical finding** for `critical_next_step` and `critical`, **Blocker** for `blocker`, **Business question** for `business_question`, and **Test gap** for `test`. An `other` item, or one with no kind (§Upgrade), has no words: it opens with its problem, which carries whatever the audit called it. On the finished page the kind's words are bold. An item a waiver covers (§What each kind does) shows its **Waived** tag, in the existing Waived tag format (the step name, time, source and account), from the latest waiver of a **Nothing holds the run** item whose subject is the item's id, or of the audit waiver whose report listed it. The line leaves the tag out: the pull request description, the finished page and `kiln status` text each render it after the item's line, from its `waiver`, so the saved block (§What a Delivered Run Says) includes the tag's text. Settled items stay under **Settled during the build**, as today.

## What a Delivered Run Says (AC-LEFT-01, AC-LEFT-02)

**The pull request description.** `pull-request-person-items.txt` is rewritten to open each description with, in order and word for word:

1. `## For you`, when it lists anything (above);
2. `## Closing audits`: "Delivery audit: 4 of 4 loops. Test audit: 2 of 4 loops.", from the ledger and the limits in force, with no line quoting an acceptance;
3. **Settled during the build**, as today.

This is an instruction in the pull request prompt; Kiln does not read the description back. Each pull request of a multi-repository run gets the same block. Where a pull request is already open, whoever opened it, the rewritten `pull-request-person-items.txt` tells the session to edit its description (`gh pr edit`) so this block replaces any an earlier session wrote, keeping the rest.

**When an open pull request is delivered.** The block a pull request session is given is saved on its session record at launch, as `carried` is, and again at each resume (below). It is built only from saved facts: the ledger, the limits in force, saved waivers and the accepted reports' after-delivery actions. A pull request session **delivered its block** when its latest run ended on its own and finished its work: `endedAt` set; no `interruptedBy`, `spawnError` or `limitRefusal`; a `result` with `isError` false; and `exitCode` 0 for a Claude session or `codex.terminal.status` `completed` for a Codex one. While the run is not complete, `pullRequestCheck` adds one row, **Pull request description**, after waivers are applied, only when every other row passes, so a failing **Current completion audits** row still sends the run back to the audits on its own, and only when the check lists at least one open pull request: an open pull request from `runPullRequestChecks`, or an open review pull request from `evaluateRepositories`. When every repository is already merged, or all its work is confirmed delivered early, there is no description to write: the run completes as today with no pull request session (Multi-Repository Delivery AC-PRS-05, Development Deployments AC-DELIVER-04), and its **For you** and **Closing audits** are on the finished page and in `kiln status`. In a run with one repository merged and another with a pull request open, the session starts and edits only the open one's description. The row passes only when the latest pull request session in this execution that delivered its block was given the block Kiln would give now. Every path that can complete the run reads this check, the precheck on a pull request already open included, so each pull request's description carries this run's **For you** and **Closing audits**, even one opened outside Kiln (AC-LEFT-01, AC-ITEM-01, AC-ITEM-03). No waiver matches it: the row is added after waivers are applied, so a saved waiver never makes it pass on a check. When it fails, the row carries a single `other` item whose `subject` and `text` are fixed, with no timestamp, so comparing two check runs that fail it the same way finds no change.

When the row fails, at the routing decision or in the engine loop the pull request session starts. A pull request session that was interrupted resumes, or Kiln records the pull request check stop when it cannot resume; after one a usage limit refused, Kiln waits and resumes it, or stops, as today (`settleRefused`); after any other that ended on its own, Kiln records that stop (`not_resumable` when its resume never started). **Check again** at that stop, with only this row failing, clears the stop and a new pull request session starts. At such a stop **Mark final delivery complete** is usable on the stop's own check run, as at the preflight stop, because Check again there starts the session rather than keeping the stop. Its rerun, like Mark complete's rerun for **Current completion audits** (`routeAudits: false`), keeps the stop rather than starting the session. It compares the rerun with the offered run (AC-WAIVE-04) and saves a waiver with `effect: completed` holding the row's single `other` item. That waiver marks the row **Waived** only in the rows it completes the run with, in the same write, which records the open pull requests and, when no pull request session wrote it, `atPullRequest`. The description keeps whatever an earlier session or the person wrote, and Complete shows the row waived (AC-WAIVE-10). AC-STOPCHECK-02's line by Check again is left out at this stop. A false mismatch, such as a time zone change, only runs one extra session. Two behaviors change from Kiln 1.3.0: a pull request already open, such as one opened outside Kiln, no longer completes the run without a session, and a first pull request session interrupted with a pull request open resumes rather than completing on it. Every resume of a pull request session, Kiln's own (after an interruption, or at the end of a usage-limit wait) or a Resume the person presses, carries the block Kiln would give now after its carry-on line, introduced by "Use this block in place of the one in the first message:". The resume saves that block on the session record before its process starts, as the block the session was given. A session from before Kiln saved blocks, or one given an older block, therefore delivers the current block when its resumed run delivers.

**The finished page and `kiln status`.** A delivered run shows a **Closing audits** list with each kind's loops used and limit, and **For you**, beside the delivery facts shown today (AC-LEFT-02, mockup screen 3). On the Complete screen, **Closing audits** and then **For you** follow the pull request section, or the already-merged section when there is one, and come before Delivery history; the **Remaining human actions** card is gone. When **For you** lists a critical finding, it moves directly below the state header, above the plan check, development delivery and every other section (AC-ITEM-03, mockup screen 3b); **Closing audits** stays where it is. `kiln status` prints the loop line, then **For you**, or **For you** first when it lists a critical finding. Both read the ledger and the limits in force, and a completed run always has `atPullRequest`, so they keep showing what the run had at delivery after a later settings change, including a run completed with no pull request session.

## The Status Line (AC-STOP-05)

Superseded in part by: `docs/changes/kiln-after-delivery/kiln-after-delivery-technical-design.md`, §Closing-Audit Names (a session of test fixes names its loop and session on its row).

During the closing audits the status line names what is running, from a `position` the snapshot derives from the current or stopped activity and the ledger:

| The activity | `position` | Status line |
|---|---|---|
| An audit that is a loop | `{ audit, loop: N, limit }` | **Delivery audit loop 2 of 4** |
| A leaf, including one at or under phases an audit appended | none | **Building Phase 10**, as for any phase |
| A session of test fixes | `{ audit: "test", loop: N, limit, fixing: true }`, N the latest test loop | **Fixing tests from test audit loop 2 of 4** |
| A Needs you stop, the hold stop included | The latest loop counted, of either kind | **Test audit loop 4 of 4** |

`limit` is the limit in force. Nothing marks the last loop; the numbers show it. Each audit row in the activity list carries its loop label; phase rows and sessions of test fixes carry none (mockup screen 2).

## Removed Controls (AC-STOP-04)

Kiln never records a loop stop. The loop stop page, **Allow _N_ more loops** and **Accept what is left and deliver** are removed from the page. `kiln allow-more-loops` and `kiln accept-and-deliver` stay in the CLI only to refuse, exit code 2, `removed_command`: "Kiln no longer stops at a loop limit. Change the limits with kiln settings." The control journal refuses either action from an older script with the same code and reason. The `settings` input `after_last_test_audit_loop` and the flag `--after-last-test-audit-loop` are refused the same way, saying the setting was removed. The CLI refuses both commands and the flag before it reads any other flag or looks up the controller, so the refusal needs no `--command-id` and is the same whatever the controller's version.

## Interfaces (AC-BOT-01, AC-BOT-02)

Superseded in part by: `docs/changes/kiln-after-delivery/kiln-after-delivery-technical-design.md`, §Interfaces (`check-for-new-phases` reads GitHub first and counts as a person's press; `continue-with-phases` pushes first).

**Command line.**

```
kiln settings <prd> [--delivery-audit-loops N] [--test-audit-loops N]   (with the existing flags)
kiln check-for-new-phases <prd>
kiln continue-with-phases <prd> --proposal ID --only-if-status-matches <token> --command-id ID
```

- `kiln settings` refuses a limit below the floor (§Settings) and, once `atPullRequest` is written, says the change applies to a continuation.
- `check-for-new-phases` runs the finished page's check through a new `POST /api/control/v1/continuation/check`, which calls the same engine check as the page's `POST /api/continuation/check`, takes no inputs and keeps no receipt. It needs a live controller and is refused unless the run is finished and idle (`wrong_activity`, `busy`).
- `continue-with-phases` makes the internal `continuation-accept` action public under this name, with that action's refusals (`proposal_changed` and the rest) and its receipt, keyed by command ID and status token as the page sends them. A proposal that still needs **Authorize early merges** is refused with that reason; the authorization stays in the browser.

**Status and snapshot.** Both carry the same objects, text and JSON (`audit_loops` in JSON):

```
auditLoops:
  settings: { deliveryLimit, testLimit }
  delivery, test: { used, limit, closed, floor }
  frozen?: { at }                      — `atPullRequest` is written; changes apply to a continuation
  position?: { audit: "delivery" | "test", loop, limit, fixing?: true }   — §The Status Line
PersonItemView:
  id?: string                          — absent only on a new entry of an unaccepted needs_you report
  kind: <the six kinds> | null         — null: listed before kinds (§Upgrade)
  words: string | null                 — the kind's words (§For you); null for `other` and no kind
  problem, action: string
  waitsOn?, criterion?: string
  waiver?: WaiverRef                   — the Waived tag (§For you), as a check item carries it
items?: (PersonItemView & { effect: "stops" | "holds" | "goes_on" })[]
                                       — at a Needs you stop on an audit, and at the hold stop; a null kind holds
delivered?:                            — on a finished run
  loops: { delivery: { used, limit }, test: { used, limit } }
  forYou: { items: (PersonItemView & { id: string; line: string })[], afterDelivery: string[] }
                                       — in the order §For you gives; `line` and each action word for word
  pullRequests: { repository, number, url }[]
continuation?:                         — on a finished run, from the view the page reads
  check: { status, attemptedAt?, lastSuccessfulAt?, errors }
  proposal?: { id, readiness, phases, problems }
```

`kiln status` JSON shows each `waiver` as `waived: { waiver_id, activity, at, via, account, by }`, by the same projection as a check's items. The page bolds `words` at the start of `line`, and it moves **For you** to the top when an item's `kind` is `critical_next_step` or `critical`. `kiln status` text prints the position line, a stop's items with their kind and what waits, a finished run's loop line and **For you**, and the continuation offer. Its controls list gives `settings`, `check-for-new-phases`, `continue-with-phases` and the handoff, each with availability and reason.

**Compatibility.** The controller advertises a `loop_limits_move_on` feature and stops advertising `audit_loops`. The CLI refuses `check-for-new-phases`, `continue-with-phases` and the `kiln settings` flags `--delivery-audit-loops` and `--test-audit-loops` against a controller without it (`instance_incompatible`, "This controller does not support the new audit loop limits. Restart it with updated Kiln."), in place of today's `audit_loops` check. The other `kiln settings` flags reach an older controller as before. The removed commands and flag are refused whatever the controller's version (§Removed Controls). `kiln status` renders the new loop lines only when the controller advertises `loop_limits_move_on`. A run still under a 1.3.0 controller keeps that controller's own page until it is restarted with updated Kiln (§Upgrade). Released `audit_loops` fields that described the removed setting and stop (`after_last_test_audit_loop*`, `stop`) are removed rather than kept with a meaning they no longer have (§Delivery).

## Prompts

- `audit-session.txt`: the two entry fields and `raised`; the six kinds, in the PRD's words, with what is never an item (a declared assumption, a request to confirm or review, anything the audit can settle itself), and that a person action the requirements place after delivery goes in `afterDeliveryActions`, never in `needsYou`; a new `{{nextSteps}}` slot naming the step each outcome leads to (below). The outcome guidance becomes: `needs_you` when the work this report leaves cannot go on without an item, when a critical finding would be caused or worsened by that next step, or when nothing is left to build and a holding item not marked waived is open before the pull request, judged from the kinds `{{outstanding}}` shows. `{{outstanding}}` prints one line per item: `- <id> (<kind>; listed by <audit>[; criterion <id>][; waits on: <waitsOn>]): <problem> <action>`. `<kind>` is the kind's identifier, or "no kind: give one when you list it again" for an item from before kinds (§Upgrade). An item a waiver covers (§What each kind does) carries, after its action, the mark "waived at final delivery: settle it if it is done, otherwise list it again by its id; it holds nothing and is never a reason for `needs_you`. A need it does not name is a new entry with no id.", opening "waived when <audit> was marked complete" in place of "waived at final delivery" when an audit waiver covers it. The prompt says: "To list an item again, give its id, problem and action. Leave out kind and waitsOn to keep the ones shown. Give a new value only when the item itself has changed, such as a blocker that no longer holds anything. An item shown with no kind must be given one." The released line asking for `needs_you` whenever the audit ends normally but lists something is dropped, as is the rule that a test audit changing only tests lists nothing.

  `{{nextSteps}}` is a pure forecast, built as the prompt is built (and rebuilt the same way after a restart) from the ledger, the limits in force (§Loops and the Ledger), the audit's kind and whether it is a session of test fixes; no snapshot is read. For each outcome it names the step Kiln takes once that outcome's work is done, by the rules in §Routing After the Last Loop: the delivery audit, the test audit, a session of test fixes, or the pull request. It names steps, not loop numbers, and never tells a session it is the last loop. A line after which no test audit or session of test fixes follows, only the pull request (with any delivery audit still due first), adds "Kiln stops before the pull request while a blocker or business question not marked waived is open."; for a test audit or session of test fixes it also adds "List each test row still missing, failing or Weak as a `test` item with its criterion." `needs_you` always means Kiln stops at Needs you. A session of test fixes is also told: "If you raised none of the rows you took, do not report continue_test: report passed and list each row left as a `test` item. That ends the test work."

  A limit can change after the forecast is built. A raise only adds audits, which account for items by id. A lowered limit can make a forecast audit untrue, which changes no finding, and the hold stop catches a holding item it strands.
- `audit-loop-limits.txt` and the audit prompt's `{{loops}}` slot: deleted; a session is told nothing about loops beyond `{{nextSteps}}`.
- `pull-request-person-items.txt`: rewritten (§What a Delivered Run Says) and added to every pull request prompt, both `pull-request-session.txt` and `development-finalization.txt`, not only when there are items. `pull-request-loop-acceptance.txt`: deleted.
- `resume-carry-on-pull-request.txt` and `resume-carry-on-development-finalization.txt`: each is followed by the line "Use this block in place of the one in the first message:" and the block Kiln would give now (§What a Delivered Run Says).
- `audit-accept.txt`, `audit-allowed-loops.txt` and `audit-earlier-acceptances.txt`: deleted. No acceptance sentence reaches any session.

## Upgrade

No criterion asks for special handling of runs under way when Kiln is upgraded (PRD Out of Scope). This section is only what a build needs so that records saved by Kiln 1.3.0 and earlier load and display without error. Schema 24, in the record migration:

- **Settings.** `deliveryLimit` and `testLimit` are kept as recorded; `afterLastTest` and `afterLastTestSource` are dropped.
- **Ledger.** `acceptances`, `itemsListedStops` and every epoch but `start` are dropped, and `loops` is rebuilt by this design's count (§Loops and the Ledger, "What counts as a loop") from the current execution's audit activities in sequence order: one loop per delivery audit, and per test audit that is not a continuation, that has a session or is not yet settled. A started record with no ledger gets one the same way. The record holds everything the count needs, so the migration does it, and the engine's ledger rebuild is removed. A count above its limit just closes that kind; findings are still built.
- **`atPullRequest`.** A record whose pull request step already has a session, or that is complete, gets it with the record's limits, `at` from the `createdAt` of its `pr` activity or, with none, its `completedAt`.
- **`itemsUnread`.** Every audit activity that already has a `waivedResult` is marked `itemsUnread`: `personItems` reads nothing from its waiver, and its waiver covers no item, as in Kiln 1.3.0. Reading the waiver's report would renumber items that later audits already relisted or settled by id. One with no `acceptedResult` adds and settles nothing, and the page's waiting count does not end at it; its items stay out of **For you**, as they were left out of the 1.3.0 pull request description. One that was accepted before it was marked complete (Kiln 1.3.0 offered Mark complete on an accepted audit whose evidence or repository checks then failed) is read from its accepted report, as 1.3.0 read it, so later ids are unchanged.

In the engine:

- **A stored `loop_limit` stop** is shown as a Needs you stop with one line, "Kiln no longer stops at a loop limit. Check again to go on.", and Check again only. Its recheck, which Check again and `kiln run` both reach, always clears it, and routing goes on by this design.
- **Items with no kind**, listed before kinds, show with `kind: null` and count as holding at the hold stop, because Kiln cannot sort them; Continue anyway there waives them, and an audit that relists one must give a kind. A stored `needs_you` stop on an audit stays an ordinary Needs you stop: a Check again that submits its report again is checked under the current contract, so a report with no kinds is refused and shown as any refusal is.
- **A pull request session from Kiln 1.3.0** has no saved block; its resume carries and saves the current block (§What a Delivered Run Says).

Schema-23 Kilns refuse schema 24 under the existing newer-schema rule.

## Delivery

- **Expected build spend:** none. Proof uses scripted provider sessions, as the loop limits build did.
- **After the build:** `CHANGELOG.md` under Unreleased. `Changed`: a loop is one run of an audit, and the settings are **Max delivery audit loops** and **Max test audit loops**, both defaulting to 4; whatever an audit finds is built, and after a kind's last loop Kiln moves on; the status line names the loop; only some items stop the run, and the rest are listed under **For you**. `Removed`: the loop stop page, Allow and Accept, `kiln allow-more-loops`, `kiln accept-and-deliver`, **After the last test audit loop**, `--after-last-test-audit-loop`, the sentence accepting Weak test rows, and the `audit_loops` status fields for them. `Added`: `kiln check-for-new-phases`, `kiln continue-with-phases`. Removing commands and status fields is an incompatible change to the command line, so under the repository's release rules this release is a major version. Then the usual release steps.
