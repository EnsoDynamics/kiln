What we’re building

If any of these is wrong, say so before reading on. The rest of this review is detail within them.

  1. Once every phase is done, a Merge button on the finished page hands the pull request to the agent, which brings the base branch in, resolves conflicts, runs the project's checks, waits for the required ones on GitHub and merges. The merge may start the base branch's CI or deployment. Source
  2. Kiln shows the work as merged only once GitHub confirms it, and checks for new phases as soon as it does. Source · 2
  3. A finished run whose pull request hasn't merged yet says so in one line on the pull request card, instead of today's false “Plan needs reconciliation” alarm. Source
  4. Coming back to finished work gives one of two answers: nothing new, or the phases planned since and one Continue button that pushes their documents if needed and builds them. Today's block asking you to reconcile documents first goes. Source
  5. A finished run's page offers Exit Kiln, so closing Kiln no longer takes Ctrl+C. Source
  6. Closing-audit rows are renamed so an audit is told apart from the sessions fixing what it found. Source
  7. Every new button has a matching command, merging included, so a bot can do what a person clicks. Source

Not included

  • Exit Kiln while a build is still in progress. Ctrl+C stays the way to stop one.
  • Kiln closing itself after a merge.
  • Watching GitHub in the background. A pull request merged elsewhere is noticed when Kiln next checks, for example when you press Check now.
  • Deploying, or watching CI or a deployment, after the merge.
  • Removing the feature branch or worktree after the merge.

01 / SECTION

Merge from the finished page

Once every phase is done, the finished page's pull request card lists the delivery: the pull request Kiln opened in each repository the work changed. Merge with Claude Code (or Codex) on that card, the Merge button for short, starts the merge session, one more agent session that works on those pull requests.

Key acceptance criteria & mockups

  • Pressing Merge is the permission, for this delivery only. Nothing is remembered for later pull requests, other work or a later run. Source
  • The merge session waits on branch protection rather than overriding it: a missing required review or a failing required check stops it unmerged. It never force-pushes. Source
  • The merge session may fix failures the merge or the work itself causes, push the fix and merge, with no new review unless branch protection requires one. Source
  • The session merges by whichever method the repository allows (merge commit, squash or rebase), without asking you. Source
  • A pull request closed without merging removes the Merge button. Kiln never reopens or replaces it; reopening it on GitHub brings the button back, or lets a merge already under way resume. Source

Should one Merge button also cover a delivery with a pull request in several repositories?

Yes. A delivery with a pull request in each of several repositories gets one Merge button for all of them. One press lets one session merge each, in the order the pull requests' descriptions state.

If one can't be merged, the session stops there and leaves the later ones open.

Kiln doesn't check the stated order: a missing or wrong order is followed as written, just as if you merged them by hand from the same descriptions.

If you choose otherwise: The Merge button appears only when the delivery has exactly one open pull request. A delivery across several repositories keeps today's card: Open on GitHub for each and a note on the order, and you merge them yourself.

Why this is proposed

The request: “I rarely ever merge anything myself anymore … I'm not handling that myself.” Earlier, of merges during a run where one repository's work must go first, Kiln “exists so that we can minimize stopping points as much as possible and it can autonomously carry the entire thing through.” Kiln already gives one permission across all of a run's repositories for early merges: one “Allow early merges” checkbox covers every repository, and those merges follow the stated order too. Against: the example that prompted this was one pull request, and one press reaches several base branches. Rare either way: 2 of 16 Kiln runs recorded on one machine had more than one repository.

While the merge runs, and if it stops

While the merge session runs, the header reads Merging and the phase plan gains a Merge row after the final pull request.

Key acceptance criteria & mockups

  • A merge that stops before merging waits on Needs you. Your reply resumes the same session; you can't start a fresh merge session or mark it complete. Source

MERGE-001Confidence: 85%Impact: MediumUnanswered

Is watching enough while the merge session runs, with no messages, Pause now or takeover?

Yes. While it runs you can watch its output, but not message it, pause it or take it over, as with the session that opens the pull requests today.

To stop it, press Ctrl+C in Kiln's terminal: the session and any conflict fixes it hasn't pushed are kept, and the next kiln run shows it interrupted, with Resume.

This narrows the mockup agreed earlier on 21 Nov, which showed Pause now and takeover on the running merge.

If you choose otherwise: You can choose either alternative. Messages only: the running merge gets the message box a running phase has, a small change. Messages, Pause now and takeover: Pause now (Claude Code only) and takeover are new work, since Kiln can't yet return control to a merge session after either; a paused merge would get the Paused page.

Why this is proposed

The request handed the merge off whole: “Hey, go merge PR number 20 and solve anything that's needed … I'm not handling that myself.” Of replying to a running audit: “maybe we just don't have this at all… it would have to be more like it comes to a full stopping point.” A pull request is never left half-merged by Ctrl+C, since GitHub merges each in one step. Kiln already has watch-only stretches: Pause now isn't offered during the check Kiln runs before the first phase, the final delivery step, or for Codex sessions. Against: of phases and audits, “I also do want the ability to pause and take over the session … we don't want to lose that.” A merge waiting on checks or working through conflicts can run for minutes, and a merge into develop is harder to undo than a phase's commits.

03 / SECTION

Coming back to finished work

After a delivery merges, a later session may plan more phases for the same work, for example after stakeholder feedback. Those new phase documents may be committed only in your main checkout, not yet pushed to the base branch.

Key acceptance criteria & mockups

  • A finished phase is never rebuilt or offered again, whatever later happens to its document. Changing that work takes a new phase. Source
  • Kiln reads new phases only from committed documents. Uncommitted edits in your main checkout are never read, committed or pushed; the page lists them as not read. Source
  • Continue has an agent push the new phase documents from your main checkout to the base branch, then starts the build with no second press. Today you push them first. Source

PLAN-001Confidence: 80%Impact: LowUnanswered

Should Kiln say nothing when a finished phase's document is edited later?

Yes. Kiln says nothing about later edits to a finished phase's document. Kiln is being built this way until you answer.

This reverses one quiet line naming the edited phase, accepted earlier on 21 Nov on the assumption such edits are rare. They aren't: across three repositories Kiln has run on, 59 of 327 finished phase documents were edited after closing, none adding work. The line would show on nearly 1 finished phase in 5, with nothing on the page able to act on it.

If you choose otherwise: Each time Kiln checks for new phases, its answer gains one line per edited finished phase: “Phase 2's document was edited after Kiln finished it. Kiln doesn't rebuild finished phases. To change that work, add a new phase.” To do that, Kiln keeps a copy of each finished phase's document as it finished.

Why this is proposed

The ruling answered an offer of one quiet line “in that rare case… say if you'd rather Kiln stay silent about it” with “Okay, I think we're aligned on all this now.” Of the 59 edits, 56 were record-keeping, such as notes added after the phase closed; the other 3 recorded a later decision in place, and none needed new work. The same day, the old reconciliation block was called “friction around dotting i's and crossing t's on the paperwork”; a line nobody can act on, shown that often, is a smaller form of the same friction.

Exit Kiln

Exit Kiln is a button on a finished run's page. It stops Kiln in its terminal and leaves the pull requests and worktrees as they are.

Key acceptance criteria & mockups

  • While a merge session runs, Exit Kiln is unavailable until it ends. Ctrl+C still stops everything, the running session included. Source

05 / SECTION

Closing-audit rows

After the last phase, Kiln runs closing audits: a delivery audit checks that everything promised was built, and a test audit checks that the tests prove it. Each run of an audit is a loop, up to a set limit, and further sessions fix the test gaps an audit finds.

Key acceptance criteria & mockups

  • Only a run of an audit counts toward its loop limit. Sessions fixing what it found don't, and read Fixing tests. Source
