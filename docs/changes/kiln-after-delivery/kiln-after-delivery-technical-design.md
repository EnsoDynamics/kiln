# Technical Design: Kiln After Delivery

**PRD:** [Kiln After Delivery](kiln-after-delivery-prd.md) · **Assumptions:** [SCOPE-001, MERGE-001 and PLAN-001 open](kiln-after-delivery-assumptions.md) · **Mockup:** [eight states](mockups/kiln-after-delivery.html)

## Overview

A finished run gains two activities that run after delivery, and a way out. **Merge** is one more agent session that brings each base branch into its feature branch, runs the project's checks, waits for GitHub's required checks and merges the delivery's pull requests. **Push the plan** is one more session that pushes newly planned phase documents from the person's main checkout before Continue builds them. While either is open the finished run is reopened, so the engine's existing loop gives it billing, usage-limit recovery, Needs you, Ctrl+C and restart recovery. Kiln itself never merges or pushes. It decides that either is done only by reading GitHub or the remote base branch.

The check for new phases on a finished run is rebuilt around three questions, asked in order: is the delivery still waiting to merge (answered from GitHub, never from commit ancestry), which one copy of the plan to read, and which phases in that copy are unfinished. Comparing finished phases with what they finished as, and comparing the two copies of the plan with each other, are removed, and with them every "Plan needs reconciliation" result for a finished run.

**Exit Kiln** ends the process cleanly from the page, and every closing-audit name comes from one function.

Everything here is Kiln's. No Enso Method skill changes (principles 1 and 2): a person can already ask an agent to merge a pull request or push documents by hand, and Kiln writes nothing into the repository that the skills do not.

## Existing Code

**Posture: Preserve** for everything this design does not name; **removed** for the finished-run comparisons below, which this PRD retires.

- Reused: the engine loop and its session launch, resume and settle path with their gates; the control journal and its receipts; the Needs you page; the GitHub read that proves an early merge (the merged time, the merge commit, and the base containing it); the completed baseline, the Git-object plan reader, external-completion accounting, the readiness evaluator, the proposal, the acceptance and activation; the loop ledger; the way a reset ends the run from a page action.
- Changed: what counts as a finished run that the loop leaves alone (§After-Delivery Activities); the finished-run check (§The Plan Check); what proves a finished phase's work is in the base (§The Plan Check, step 4); what counts as closed for the phases an execution Continue created carries as finished (§The Plan Check, step 3); how the early-merge evaluator treats a merged review pull request on a finished run (§The Merge Session); every place that builds an audit's name.
- Removed, for a finished run only: deciding "waiting to merge" from commit ancestry and the PRD folder's tree; the completed-scope comparison, the `source_conflict` problem, the list of documents that differ between copies and the `unresolved_earlier_work` class; reading the main checkout's files from disk (the proposal's `sharedDigest`, the `shared_documents` input observation and the end-of-check comparison of the disk digest); the "Waiting for the delivery to merge" panel and the "Plan needs reconciliation" heading, header and terminal sentence.
- Kept: plan reconciliation of a run still in progress, apart from those carried phases, including its "Plan needs reconciliation" notice, which is not rendered on a finished run. The pull request session still may not merge. Early merges keep their own grants, evidence and `kiln delivery` interface, which the merge session is not given.

## Architecture

No new service, store, timer or background watcher. The foreground engine and its command journal remain the only owner of every change. GitHub is read through the existing `gh` helper with its timeouts.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| How a session runs once the run is finished | An open after-delivery activity makes the run not currently complete | A finished run is inert today: the loop, startup recovery, stops, waits and billing approval all return early on it, and AC-MERGE-05 and AC-MERGE-06 need every one of them. One predicate reopens the run; a run with early merges already reopens a finished record the same way |
| Who merges and pushes | The session, with `gh` and `git`. The engine only reads | AC-MERGE-03 needs conflicts resolved and failures fixed, which only a session can do. Early merges already work this way. GitHub applies branch protection to the session's own merge, so Kiln holds nothing that could go around it |
| What proves a merge | The `merged` reading (§The Delivery Reading) | AC-MERGE-04 forbids taking the session's word, and "by any merge method" (AC-WAIT-01) rules out looking for the delivered commits in the base |
| What "waiting to merge" is read from | The state on GitHub of the run's pull request in the PRD's repository | The same; ancestry and comparing copies are what produced the false alarm |
| Which copy of the plan is read | Exactly one, chosen by AC-BACK-03's table, from committed Git objects | Uncommitted edits can then never be read, and two copies are never compared |
| What a missing main checkout does | AC-BACK-03's last row (§The Plan Check, step 2) | Kiln keeps no other copy of the repository: every remote read, the run worktrees' Git data and both Continue sessions depend on that checkout, so a plan read some other way could not be built from |
| What makes a phase finished | The run's completion record (§The Plan Check, step 3) | AC-BACK-01: a finished phase stays finished whatever happens to its document (PLAN-001) |
| What Kiln says about an edited finished phase | Nothing; no copy of a finished phase's document is kept or compared | AC-BACK-01 asks for one line per edited finished phase; PLAN-001, open with stakeholders, proposes silence, since such edits are common and none added work (evidence in the assumption). The line is built only if the original ruling stands (§Open Questions) |
| Where the push sits | A step of accepting Continue, owned by the same acceptance | AC-BACK-05: one press pushes, checks again and starts the build |
| How Kiln knows the stated merge order | One fixed line in each description, written by the pull request session and parsed by Kiln | AC-MERGE-01's note must name the order, and prose cannot be read reliably. Kiln still does not check the order |
| When GitHub is read | Only on the occasions in §The Delivery Reading | Watching GitHub in the background is out of scope |

## After-Delivery Activities (AC-MERGE-05, AC-MERGE-06)

Both sessions are activities of the finished execution, keyed and typed so nothing takes them for a plan phase, an audit or the pull request session.

| | Merge | Push the plan |
|---|---|---|
| Activity key | `merge` | `plan-push-<operationId>`, one per press (below) |
| Activity kind | `merge` | `plan_push` |
| Session kind | `merge` | `plan_push` |
| Stop kind when it ends undone | `merge_check` | `plan_push_check` |
| Runs in | The run's session folder | The person's main checkout |
| Done when | The delivery reading shows every pull request merged | §Continue and the Push Session, "Done" |
| Closes | At Done | At the plan check's decision after Done ("Ending") |
| Row | **Merge**, id `M`, after the final pull request row | **Push the plan**, id `P`, before the first added phase |
| Header while it runs | **Merging** | **Pushing the plan** |

**Opening.** An activity opens when its journal action is accepted (§Interfaces), recorded with its receipt before anything launches. One is open at a time, and none opens while a session runs or a check is in progress.

**While open.** The run is not currently complete, so the loop serves it. `completedAt`, the pull request facts, the delivered summary and the phases-done count do not change, and the open activity is the loop's next activity ahead of anything else. The plan reader, the done check, the pull request check, the audits, the preflight and the completion step never run for these keys. Each activity is settled only by the reading one of its own occasions takes: its session's end; a stop's Check again, Resume or Send and resume; the resume after a usage-limit wait; and `kiln run`, Resume or `kiln continue` at the restart review. A delivery reading on any other occasion (opening or reloading the page, Check now, Check for new phases, `kiln check-for-new-phases`) while a merge activity is open only saves the pull request states the card shows. It never closes the activity, whatever it reads, whether a session is running, starting, stopped, waiting or held. The run counts as complete again when the activity closes. The PRD's time totals count the activities' sessions like any other (Kiln PRD Time Totals AC-TOTAL-02 and AC-TOTAL-03): while an activity is open the totals advance, and when it closes they are fixed at the close, not at `completedAt`. The snapshot ends Complete's timing, and the span the totals cover, at the later of `completedAt` and the latest after-delivery activity's `closedAt` (§Data Models and Upgrade). The archive row a Continue acceptance writes saves running time up to that acceptance, not up to `completedAt`, so the push session stays in the next execution's total.

**Gates.** The session starts through the ordinary launch path, so it uses the run's agent, model and effort and passes the same gates as any session: agent readiness, billing (an approval can be given again while the activity is open), each read in the folders the activity is given (below), keep-awake, and a usage-limit refusal that becomes a wait and then a resume. The folder check and its Folder missing page stay off for a finished run, because that page's Start sets up a fresh execution. Each activity checks its own folder instead, at the press and before every launch or resume:

| Activity | Its folder is ready when | When it is not |
|---|---|---|
| Merge | Each pull request still to merge has its run worktree, on the feature branch. At the press the worktree also has no uncommitted work and no merge in progress (`MERGE_HEAD`). Kiln brings in the objects of the pull request's head, the `headSha` the press's fresh reading saved (GitHub's `headRefOid`), from the main checkout, writing no ref, as the plan check already does for the remote base. The worktree's head must then be at, ahead of or behind that head. Behind is the usual case after GitHub's Update branch or a suggestion committed on GitHub, and the session fast-forwards it first. A worktree that has diverged from it, with commits on both sides as after Update with rebase, is refused. The activity records the worktree's head at the press. A fetch or ancestry read that fails refuses the press and names the failure; it is never read as behind or diverged. At Resume, Send and resume, the resume after a usage-limit wait and the resume at `kiln run`, its head need only descend from the head recorded at the press: uncommitted work or a merge in progress is left as it is for the resumed session, as for every other session Kiln resumes | The press, or Resume at the stop, is refused naming the repository and folder. A diverged worktree is refused saying that it and pull request #{n} each have commits the other lacks. Check again still reads GitHub, so a merge finished on GitHub by hand is still shown |
| Push the plan | The main checkout is found (§The Plan Check, step 2) and is on the base branch; at the press its tip is the commit the offer was read from, and on a resume its tip descends from that commit | The press, or Resume, is refused saying which |

Each activity's session is given only the folders its check requires. A merge session starts in the run's session folder, and its workspace (Codex's writable roots and assigned worktrees, Claude Code's added directories) is that folder plus the run worktree of each pull request the latest delivery reading does not show `merged`. The set is taken again at every launch and resume, and the agent readiness read and the Codex launch-settings check use the same set. A repository whose pull request has merged, whether early, by hand or earlier in this session, is left out, so removing its worktree never stops the session. A Codex resume keeps its recorded start folder, which this rule never changes, and is given the roots of that moment, as a session that gains a worktree partway through already is. A push session is given the main checkout alone, never the run's session folder, which a person may remove once the delivery merges. It starts there, a Codex session has it as its one writable root, and the billing read, the agent readiness read and the Codex launch-settings check all use it alone: at the press, before each launch or resume, and when a billing hold is checked again. So the billing read sees the main checkout's own local settings, which Git ignores and a worktree lacks. Network access is already granted to every Codex session.

**No live controls.** As for the pull request session, no live attempt is created, and messages, takeover, Pause after this activity and Pause now are unavailable with the reason the page prints (for the merge session, MERGE-001). Pause after is never counted as offered for these keys, so while either session runs the reset line takes Kiln Run Restart's third `reset.reason` row (A session is still running. Reset becomes available when it ends.), and while Kiln's own work for it runs, such as a reading or the push's re-check, the fifth, as for final delivery.

**Ending.** When the session ends, the engine takes the activity's reading. Done closes the merge activity. Closing at the session's end saves the summary (§The Delivery Reading). Not done after a usage-limit refusal is a wait. Otherwise it is a Needs you stop carrying the session's last message word for word and one check row per pull request (or one for the plan). A stop, wait or close of either activity leaves the early-merge ledger's completion result as it was, so closing the activity returns the run to complete without evaluating delivery again. For the push activity, Done does not close it. It records `doneAt` and moves the activity to `accepting` until the re-check's decision. A match closes it in the same record save that adds the acceptance row. Any other result closes it as that result is shown.

**At the stop.** Only `reply`, `resume` and `check-again` are offered, with Exit Kiln. Each first repeats the reading; when the work is done the activity is done without resuming (the push activity moves to `accepting`), with the receipt outcome `already_done`. A reading that cannot read a pull request not already `merged` decides nothing: nothing resumes, no reply is sent, and the stop stays and names the failure, as for the push session. The same holds when the resume after a usage-limit wait or `kiln run` first repeats the reading: the session is not resumed and the merge stop shows the failure. Resume works again once GitHub can be read. `carry-on`, `start-again`, `verify-and-advance`, Mark complete and the fresh-session prompt are never offered for these keys, because nothing starts a second merge or push session. When the conversation cannot be reopened, the stop says so and leaves two ways on: finish the work outside Kiln, then Check again.

A pull request closed on GitHub is not done, so it never closes the merge activity: the stop's check row shows it closed, and Merge with {agent} is not offered again (once per delivery, below). Reopening it on GitHub and pressing Resume carries on the same session, whose resume prompt carries the fresh reading; merging every pull request on GitHub, then Check again, closes the activity as Merged.

**Ctrl+C and restart.** Ctrl+C interrupts the session as it does any other. The next `kiln run` takes the reading first, and when the work is done the activity is done: the merge activity closes, and the push activity moves to `accepting`. Otherwise it holds the same session at the restart review (Kiln v1 AC-CLI-01): nothing launches, resumes or waits until Resume. The page stays the finished page, never the Paused overview. The activity's row reads **Interrupted**, and the pull request card shows **Resume** where it shows the running session. Resume, and `kiln continue` while the review shows, release the review: they take the reading again and then resume the session or restart its usage wait. `kiln run <path> --resume` skips the review. None of these marks a preflight while an after-delivery activity is open. An open activity is handled before anything else `kiln run` does for a finished run, including the early-merge delivery evaluation. An `accepting` push activity has no session to hold: `kiln run` goes straight to its plan check (§Continue and the Push Session).

**Keys, and once per delivery.** A push activity's key is `plan-push-<operationId>`, where `<operationId>` is the receipt id of the press that opened the push. `activityKeyKind` gains `merge` (exact match) and the `plan-push-` prefix. Every press opens a new key, so a push never reuses an earlier push's facts or sessions. An execution has at most one merge activity and may have several push activities, at most one of them open. Once the merge activity exists, Merge with {agent} is never offered again for that execution.

## The Delivery Reading (AC-MERGE-04, AC-MERGE-07, AC-WAIT-01)

One engine operation reads each of the delivery's pull requests from GitHub and saves the result. The delivery's pull requests are the ones the run recorded at completion; repositories recorded as already merged then are shown as today.

| Read as | When |
|---|---|
| `open` | GitHub shows it open. `conflicts` is set only when GitHub says definitively that it cannot be merged cleanly: `mergeable` reads `CONFLICTING` or `mergeStateStatus` reads `DIRTY`. An `open` reading saves the pull request's current head (`headRefOid`) as `headSha` |
| `merged` | GitHub shows it merged into the recorded base, with a merge time and merge commit, and the base branch contains that merge commit |
| `closed` | GitHub shows it closed and not merged |

While GitHub has not yet worked out whether an open pull request merges cleanly (`UNKNOWN`), `conflicts` stays unset, the card shows no mark, and Kiln does not read again for it; the next occasion picks it up. A `merged` reading is final and is not read again. A read that fails keeps the previous reading, records the failure and its time, and never infers a state. Nothing resumes a merge session on a reading with a failed read (§After-Delivery Activities). While a pull request's state is unknown, the merge is not offered and the card says GitHub could not be read, with the recorded failure.

The reading also parses the merge order line from each description (§Prompts) into a position, where one is given. The note names that order when every description has the line. When none has it, the note says the session follows any order the descriptions state, which covers pull requests opened before this change, whose order is in prose.

The reading is `gh pr view <number> --repo github.com/<owner>/<name> --json number,state,mergedAt,mergeCommit,headRefOid,baseRefName,mergeable,mergeStateStatus,body`, and for a merged pull request `gh api repos/<owner>/<name>/compare/<base>...<merge commit>`, whose `status` reads `behind` or `identical` exactly when the base contains the merge commit. A merged pull request whose `baseRefName` is not the recorded base is a failed read, never `merged`. `gh` runs from each repository's main checkout, never from a run worktree, which a person may remove once the work has merged. A repository whose main checkout is not found (§The Plan Check, step 2) is not read, and its read fails with that step's text. One reading runs at a time; an occasion that arrives while one is in flight waits for its result instead of starting another.

**Occasions.** `kiln run` on a finished run, before the terminal's line; opening or reloading the page, which is the view's one request when it mounts (`POST /api/continuation/check` without the press flag), while a reconnect of the event stream and a snapshot read take no reading; Check now, Check for new phases and `kiln check-for-new-phases`; the Merge press, before the activity opens; the end of a merge session; Check again, Resume or Send and resume at its stop; Resume or `kiln continue` at the restart review; and the resume after a usage-limit wait. There is no timer.

**What follows from it.**

- **The offer** is AC-MERGE-07's table over the saved states, so the page and `kiln status` agree.
- **Merged**: when every pull request reads `merged`, the run is shown as Merged with each merge time and merge commit. While a merge activity is open, only one of its own occasions closes it (§After-Delivery Activities, "While open"); a reading on any other occasion shows each pull request merged on the card and the header stays Merging. The closing summary is saved only when a merge session's own end closes the activity: the reading taken at that end shows every pull request `merged`, and the run that just ended has a final message (`result.text`, non-empty once trimmed), with no usage-limit refusal, interruption or error result. That message is saved word for word in `merge.summary`, whatever it says, since the reading, not the message, decides Merged. The summary is taken from the run that just ended, never from an earlier run, so a resumed session's summary is the final message of its last run and an earlier stop's message is never shown. An activity closed by Check again, by Resume's first reading, or by `kiln run` saves no summary, and neither does a delivery the person merged before any session ran. Without a summary, the Merged card leaves the summary block out and shows each merge time and merge commit only.
- **Waiting** (AC-WAIT-01): the delivery waits while the pull request in the PRD's repository is not `merged`, unless it reads `closed` and the person has pressed Check now since. That press is recorded only for a reading a person asked for by the button or the command, never for a page load or `kiln run`, and it stops counting if the pull request is later read as open. A delivery with no pull request in the PRD's repository never waits.
- **The check follows the reading.** On the page, button and `kiln run` occasions the plan check runs straight after the reading when the delivery is not waiting and no activity is open. When a merge activity closes with every pull request merged, the check runs unasked (AC-WAIT-03). On the page occasion this is today's check on page load (AC-FIND-01 in Kiln Continue Added Phases, which AC-WAIT-03 leaves in force), so a phase added after the merge appears on reload with no press. Once every pull request reads `merged` the occasion reads nothing from GitHub and only the check runs. Concurrent occasions from several tabs join the reading and the check already in flight.

## The Merge Session (AC-MERGE-01, AC-MERGE-02, AC-MERGE-03, AC-MERGE-08)

**The press.** The `merge` action takes a fresh delivery reading, then:

| The reading | The action |
|---|---|
| Every pull request `merged` | Completes as `already_merged`; no session starts, and the run shows Merged |
| Any `closed`, or any state unknown | Refused with that reason; nothing opens |
| Otherwise | Opens the merge activity for the pull requests that read `open` |

**Permission.** The accepted receipt for this execution is the whole permission. Nothing is written to settings, to the early-merge authorization or to a preference, and a continuation's fresh execution starts with no after-delivery state (AC-MERGE-02).

**The prompt** is a new template, `merge-session.txt`, filled with the pull requests to merge in order (stated positions first, then recorded order), each with its repository, number, feature branch, base branch and worktree. It carries AC-MERGE-03's two columns as written, and these fixed points:

- Before anything else, bring each worktree up to its pull request's head with a fast-forward only (`git pull --ff-only origin <feature>`). If it cannot fast-forward, end there without merging the pull requests after it, and name it.
- Merge the base branch into the feature branch; never rebase, amend or force-push.
- Merge with `gh pr merge --match-head-commit`, pinned to the head it last pushed, or, when it pushed nothing, the head it fast-forwarded to, by the first of merge commit, squash or rebase that the repository allows. Never use an administrator override, and never delete the branch.
- Wait for a pull request's required checks for at most 30 minutes after its last push. A check still failing after its fixes, or not reported by then, ends the session there.
- Read each description before merging, and follow any merge order it states, whether as the `Merge order` line or in prose. Kiln does not check the order.
- A session that cannot merge a pull request ends without merging the ones after it. Its last message names what is outstanding: a conflict to decide, a missing required review, or a required check failing or never reported.
- Never reopen, recreate or replace a pull request. Before waiting on a pull request's checks and before merging it, read its state; one closed on GitHub ends the session there, without merging the ones after it, and the last message names it as closed (AC-MERGE-07).
- Before ending with a conflict to decide, abort the unfinished merge (`git merge --abort`) and name the conflicting files and what needs deciding. Commits already made stay.
- A session that merged everything ends with a short summary of what it did, which becomes the Merged card's summary (§The Delivery Reading).

Merge commit first keeps the delivered commits in the base's history where the repository allows it. Thirty minutes covers ordinary CI and gives "never wait without end" a number. Both are constants in the template.

A resumed session gets `resume-carry-on-merge.txt`, the same rules with the current delivery reading. It opens by telling the session to read each worktree's state first: a merge of the base left in progress by an interruption is the session's to finish, or to abort and redo, never to commit half-resolved.

**Under early merges.** A run with early merges allowed delivers its remaining review pull requests the same way: they are the delivery's pull requests, and the merge session uses this prompt, not the early-merge authority block. `kiln run` on such a finished run evaluates delivery again, and today that evaluation requires an open review pull request holding the feature head, so a review pull request that has merged, by the merge session or by the person, would turn the merged run into a Needs you stop. On a finished run the evaluator therefore counts a repository as delivered when the delivery reading shows its review pull request `merged` (§The Delivery Reading), whoever merged it and however its branch was updated beforehand. For that repository it reads nothing from the run worktree: its branch, uncommitted work, pushed head and ancestry are not checked, and the worktree may be missing or part-way through a merge an interrupted merge session left. It does not look for the feature head the run recorded, since Update branch with rebase rewrites it. Early-merge checkpoints keep their own rules unchanged: each checkpoint's pull request must still merge at its prepared head, and its deployment and verification evidence is still judged. A run still in progress keeps today's rule, an open review pull request holding the current pushed head.

**The statement of what Kiln may do** (AC-MERGE-08) gains its allowed lines wherever it is built: before Start, in the folder setup panel, and in the settings while Kiln works. The wording is mockup state 8's: the allowed list adds "Merge the delivery's pull requests only when you press Merge with {agent} on the finished page", and the line that forbids drops "merge" and reads "Never deploy or touch other branches". Where early merges are allowed, the early-merge lines stay and the merge line is added. In the PRD's repository only, the allowed list also adds "Push this PRD's documents to {base} only when you press Continue on the finished page" after the merge line; with early merges on, this line is still added, because the push is not an early merge. The settings statement, which only a run in several repositories shows (a run in one repository states nothing there), reads "…It merges the delivery's pull requests only when you press Merge with {agent} on the finished page, in the PRD's repository pushes this PRD's documents to its base only when you press Continue there, and never deploys or touches other branches." The README's sentence about what Kiln does by default changes the same way.

## The Plan Check on a Finished Run (AC-WAIT-01 to AC-WAIT-03, AC-BACK-01, AC-BACK-03, AC-BACK-04)

The check runs in this order and stops at the first step that answers.

**1. Waiting.** While the delivery waits (§The Delivery Reading) the result is `awaiting_merge` and no plan is read, whatever the base branch or the main checkout holds. When GitHub cannot be read and the pull request is not already known to be merged, the result is a failed check giving the reading's failure, which for a main checkout that is not found is step 2's text.

**2. One source.** The main checkout must be found first. It is found when the path saved in the record is a folder, Git's top level there is that same path, and its origin is the run's GitHub repository. A fresh clone of the same repository at that path is found and read like the original. Anything else is not found, a plain folder that now sits inside another repository included, and the result is `failed` with the text "Kiln could not find the main checkout at <path>: <what was there>. Put it back at that path, then check for new phases again.", where what was there is nothing, a folder that is not a Git repository, a folder inside the repository at <top level>, or a clone of <other repository>. Continue is unavailable as AC-BACK-03's last row says. Kiln never clones the repository, fetches into a run worktree or reads the plan through GitHub's API in its place.

With the checkout found, the remote base branch is always read. The main checkout's committed plan is read only when the checkout is on the base branch and its tip holds commits the remote base lacks.

| The main checkout | Source |
|---|---|
| On the base branch, and its committed plan has unfinished phases whose ids the remote plan lacks | The main checkout's tip commit |
| On the base branch otherwise | The remote base |
| On another branch | The remote base, with the branch name recorded as the reason the checkout was not read |

Both copies are read from Git objects at one commit each. This PRD's documents are every file under the PRD's folder, together with every file the plan read covers, linked documents included. Uncommitted changes to them, untracked files included, are listed by name from the main checkout's status (`git status --porcelain=v1 -z --untracked-files=all` limited to those paths, both names for a rename) and are never read. The list is made whichever source was read, the checkout on another branch included, so a phase document written but not committed is named as not read. The two copies are never compared with each other and never combined. The check's final guard against a moving source compares commits, not files: the remote base's revision as today and, for an offer read from the main checkout, its branch and tip commit. An uncommitted edit made during or after a check never fails the check and never supersedes a granted early merge.

**3. What is finished.** The run's completion record is the set of phase ids in the completions of the run's retained plan baseline, together with every phase of the finished execution whose facts show it done (Mark complete included) or skipped on a waiver. Each of these is mapped to a plan id by plan reading's judgement against the execution's recorded plan: the plan its last in-progress read saved, which is also the plan its done checks judged. The plan read now is never used, so a finished phase that later gained phases beneath it keeps its own id, and its new children are not taken for it. Only phase facts count, never final delivery, an audit or a preflight. The baseline already carries every earlier execution's finished phases, every phase closed before a start and accepted then, and every phase accepted as completed outside Kiln when Continue activated, so the record covers the whole history of the PRD, not only the last execution. Split parents are never in it. The external-completion accounting ties a session to a Closed leaf against the same recorded plan. A record from before baselines existed builds the set from its phase facts, as today.

Each leaf of the plan read is classed by one table.

| The leaf | Class |
|---|---|
| Its id is in the run's completion record | Finished. It is carried and never compared, whatever its document now says |
| Not in the record, and Closed in its document | Completed outside the run, by the existing external-completion accounting |
| Not in the record, and not Closed | Unfinished: counted and offered, wherever it sits, beneath a finished phase included |

A finished id that the plan read no longer has, or now has as a split parent, stays finished and is not reported. Split parents are never leaves, so they never count. When Continue activates a fresh execution, its retained baseline carries this same completion record, not only the candidate's completions, together with the phases accepted then as completed outside Kiln, and the fresh execution's record names that baseline in `continuationBaselineId`; every id in it is carried as closed, so a finished phase whose Closed line was later removed is not built again.

The fresh execution keeps these ids as its carried-finished set: the completions with no waiver in the baseline Continue activated it with, beside the waived ones it already carries. Phases this execution completes, and phases accepted as completed outside Kiln during it, are never in the set, so their final delivery checks run and a later reopen of one stops the plan read as today. An execution created by a folder start has no carried-finished set. Wherever the execution asks whether a leaf is closed, a carried-finished id counts as closed whatever its document says: the next phase, the remaining count, the completed-scope comparison of each plan read (so a Closed line removed during the execution is not a reopened phase) and the delivery pass. That pass skips it as an accepted completion, so its Closed-line and delivery checks never run, and it is never launched. Its row shows done, never waived.

**4. Readiness** runs as today when there are unfinished phases, with two changes to what proves a finished phase's work is in the base:

- A merge Kiln confirmed counts. For each finished phase that the finished execution completed, in each repository whose delivery pull request reads `merged`, the phase's work is in the base when the base revision read contains that pull request's merge commit. A merge commit missing from the object store after the base fetch is not in the base. Readiness does not look for the phase's own commits. "By any merge method" (AC-WAIT-01) also covers how the branch was updated beforehand. So a merge commit, a squash, a rebase merge, Update branch by merge or by rebase, and a fresh clone made after the branch was deleted all leave Continue available. Phases carried from earlier executions, and repositories with no delivery pull request, keep today's test: the phase's commit is in the base, or its retained integration is.
- When the delivery's pull request was closed without merging and its work is not in the base, the readiness line says so in plain words, naming the pull request and that reopening and merging it brings Continue back. Continue stays unavailable. This is the guard for Check now pressed on a closed pull request: Kiln never builds added phases on a base that lacks the delivery.

**The result.**

| Status | When | The page |
|---|---|---|
| `awaiting_merge` | Step 1 | The pull request card's one line (AC-WAIT-02); no panel |
| `unchanged` | No unfinished phase | **No new phases found**, with the check time |
| `available` | Unfinished phases, and ready | The offer (AC-BACK-04) |
| `blocked` | Unfinished phases, and readiness not met | The offer with its readiness results; Continue unavailable |
| `failed` | A required read failed, the main checkout is not found, or a plan is invalid | **Could not check for new phases**, as today, with the reason |

Phases completed outside the run are still listed with their evidence, but they no longer change the status when nothing is unfinished. A phase closed by hand without external completion evidence is not unfinished and is never offered, but it is listed as closed outside Kiln and not verified, and, as today, it blocks Continue whenever there are unfinished phases; when nothing is unfinished the result is **No new phases found** with that listing. No result carries an internal problem code or a list of differing documents.

**Where the phases came from** (AC-BACK-04). For the remote base, the result names the most recent commit that added one of the unfinished phases' documents, with its date and subject. For the main checkout, it says what AC-BACK-04 says.

## Continue and the Push Session (AC-BACK-05)

An offer read from the main checkout is ready on the same readiness results as any other, although its documents are not in the remote base yet. Its proposal records that source and the commits the checkout's base branch holds beyond the remote, each marked as touching only this PRD's documents or not. This PRD's documents are as §The Plan Check defines them, taken from the plan read at the checkout's tip.

Accepting such an offer, from the page or with `kiln continue-with-phases`, does not create the acceptance yet. It opens a new push activity under its own key (§After-Delivery Activities, "Keys"), bound to the offer's ordered unfinished phases with each phase's own scope digest (`phaseScopeDigest`), and the receipt completes as `plan_push_started`.

**The prompt**, `plan-push-session.txt`, gives the main checkout, the base branch and the listed commits, and these fixed points:

- If a listed commit touches anything but this PRD's documents, push nothing and end, naming those commits.
- If the remote base has moved, merge it into the local base branch. If the same documents changed in a way that needs a decision, abort the merge and end, naming the documents and what needs deciding.
- Never stash, commit, change or discard uncommitted work. If Git refuses because of it, abort and end, saying so.
- Push with a plain `git push`, never forced. If it is refused, end with the refusal word for word.
- A reply may say to push the other commits too, or how to combine the documents. No reply permits a forced push or touching uncommitted work.

Aborting the merge before ending means a session that stops never leaves the person's checkout part-way through one. An interrupted session can, and `resume-carry-on-plan-push.txt` tells the resumed session to finish or abort a merge in progress before anything else.

**Done** is read from the remote base, on the activity's own occasions (§After-Delivery Activities, "While open"). It is done when either holds: the remote base's plan has a phase with every offered id, whatever its document now says, or the remote base contains the main checkout's base-branch tip (`refs/heads/<base>`) as it stands at that reading. The first covers a push that rewrote the commits, such as a squash-merged pull request or a push of this PRD's documents alone. The second covers a reply that dropped or renumbered an offered phase, and a person who withdrew the plan by resetting the local base. Neither holds at the press: the offer was read from the main checkout only because the remote plan lacked one of its ids and the tip held commits the remote lacked. Both read the revision `remoteBase` fetched, never `origin/<base>`, which that fetch does not update. A remote plan that cannot be read makes the first clause false and leaves the second to decide. A remote that cannot be reached decides nothing: nothing resumes, and the push stop shows the failure. The engine then runs the plan check again. When the new offer's ordered unfinished phases match the offered ones by id and phase scope digest and it is ready, the engine accepts it itself, as an automatic journal instruction linked to the original receipt, and Continue goes on as today: setup, the preflight, the build. Otherwise the result is shown as found and nothing starts: a refreshed offer for a fresh choice (AC-OFFER-03 in Kiln Continue Added Phases), a blocked offer, **No new phases found**, or **Could not check for new phases** (AC-FIND-04 in Kiln Continue Added Phases).

An `accepting` activity is open, so `kiln run` after Ctrl+C or a crash handles it first, as any open activity. It does not repeat the Done reading. It repeats the plan check and accepts on a match, as the live path does. The automatic instruction gets a fresh command id for each attempt. Its reconcile rule reads the record: an acceptance row linked to the push operation means completed; no row means `failed/not_applied`, and nothing was applied. So an interrupted attempt never leaves an indeterminate receipt that blocks dispatch.

**An early-merge grant does not survive the push.** A target grant given before the press (AC-CONTINUE-09 in Kiln Continue Added Phases) is bound to the offer's `scopeDigest`, which includes each repository's base revision. The push moves the PRD repository's base. So the re-check marks that pending authority superseded, as any change to the base does, and the refreshed offer is blocked until the grant is given again. This is AC-OFFER-03's fresh choice. Kiln shows the refreshed offer with **Authorize early merges** again and explains that pushing the plan moved the base branch, so the earlier permission no longer applies. Nothing starts until the person grants and presses Continue. Kiln never carries a grant to the new offer or re-binds it, even when the only change is Kiln's own push. An offer missing its grant is not ready, so it is never accepted automatically.

**Activation and the row.** The push's facts and session stay in the finished execution, where the session ran, and are archived with it. The fresh execution starts with none of them, and nothing is moved or rewritten.

The finished page shows a **Push the plan** row while a push is open, and while the acceptance it led to is being prepared. The fresh execution shows a Done **Push the plan** row before its first added phase when its acceptance carries `planPushKey` (§Data Models and Upgrade), reading that push's facts from the archived execution; its session links pass that execution's id. A push that reached Done but that no activation followed shows no row; its facts stay in the history.

## Exit Kiln (AC-EXIT-01, AC-EXIT-02)

`exit` is a journal action, available on a finished run whenever no session process is running and Kiln is not starting one: no journalled command is applying, no accepted continuation is being set up and no push activity is `accepting`. That includes the Merged page, a merge or push stop, an after-delivery activity held at the restart review, the Waiting screen of a merge or push wait, and a plan check or delivery reading in progress, unless a journalled command or an `accepting` push activity is waiting on it. While a session runs or starts, Exit is unavailable, and its reason says Exit Kiln returns when the session ends, or once Kiln has started it, and that Ctrl+C stops everything. While a push activity is `accepting`, the reason says Exit Kiln returns once Kiln has started the build or shown what it found. A plan check or reading in progress is abandoned. The ordinary stop path aborts it, as Ctrl+C does today, and the record keeps the last completed check. The next `kiln run` checks again.

In order: the receipt completes and is flushed; the caller gets its answer; every open page receives an `exited` event with the time, how Kiln was exited and the command that opens the PRD again; then, after the short delay a reset already uses, the run ends through the ordinary stop path with exit code 0. That path releases keep-awake and helper processes, closes the server, releases the instance lock and prints the last line, which says Kiln was exited from the page (or from the command line) and gives the same command.

A page that receives `exited` shows the Kiln has exited state from the event and stops reconnecting, so it never shows the disconnected banner. Exit writes nothing but its receipt (AC-EXIT-02). An abandoned check saves nothing to the record. Files a part-way check may already have written, content-addressed baseline or proposal files and a pending approval marked superseded, are what Ctrl+C at the same moment leaves today, and the next check writes them again; they stay within AC-EXIT-02.

## Closing-Audit Names (AC-AUDIT-01)

One function, in a module the page can import, gives every audit activity its row title, the line beneath it and a sentence form for prose.

| Activity | Title | Line | In a sentence |
|---|---|---|---|
| A delivery audit | Delivery audit | Loop _n_ of _limit_ | delivery audit loop _n_ |
| A test audit | Test audit | Loop _n_ of _limit_ | test audit loop _n_ |
| A session of test fixes | Fixing tests | From test audit loop _n_ · session _k_ | fixing tests from test audit loop _n_, session _k_ |

_n_ is the loop the ledger counted for the audit. A session of test fixes takes the loop of the test audit that started its chain, and _k_ is its place in that chain, counted from 1. _limit_ is the limit in force. An audit the ledger did not count as a loop shows its title alone, and a phase an audit added keeps its phase title.

The function replaces every place a person reads an audit's name: the phase-plan row and the session page's heading; the terminal's audit lines, including the line that starts an audit; the live-control label, the pause label and the pause sentences built from it; the paused-partway page's eyebrow and the pause panel's activity name; the "was marked complete" check row; the `kiln status` progress rows, title and line both, and the waiver labels; and the "listed by" and "settled by" names in the session page and the pull request description. The audit prompt's own round and continuation numbers are not a person's reading and stay.

## Interfaces (AC-BOT-01, AC-BOT-02)

**Command line.**

```
kiln merge <prd> --only-if-status-matches <token> --command-id ID
kiln exit <prd> --only-if-status-matches <token> --command-id ID
kiln check-for-new-phases <prd>
kiln continue-with-phases <prd> --proposal ID --only-if-status-matches <token> --command-id ID
```

- `merge` and `exit` join the journalled actions, with a command ID for retries and a status token for targeting, as every control that changes work has. The status token covers the after-delivery state, so a press made on a stale reading is refused. `kiln merge --help` carries the button's note (AC-MERGE-01).
- `check-for-new-phases` takes the delivery reading and then the check, as Check now does, and counts as a person's press. It still keeps no receipt.
- `continue-with-phases` is unchanged in form. On an offer read from the main checkout it starts the push first, and its receipt says so.
- `kiln status` lists `merge` and `exit` among the controls (AC-BOT-01); `exit`'s availability is §Exit Kiln's.
- The controller advertises an `after_delivery` feature. The command line refuses `merge` and `exit` against a controller without it, as it does for other newer commands.

**Local routes.** `POST /api/merge` and `POST /api/exit` submit the two actions from the page. `POST /api/continuation/check` and its control-API twin take the reading before the check; the page's load sends `{}`, and the Check now and Check for new phases buttons send `{ "press": true }` to mark a person's press (the control-API twin always counts as one), which counts only for the closed pull request rule (§The Delivery Reading, "Waiting"). The event stream gains the `exited` event.

**Snapshot and status** carry the same object, as `after_delivery` in JSON:

```
afterDelivery?:                    — on a finished run
  pullRequests: { repository, number, state: "open" | "merged" | "closed",
                  conflicts?: true, order?: { position, of },
                  mergedAt?, mergeCommit?, readAt }[]
  readError?: { at, problem }
  waiting: boolean
  merge?:    { state: "running" | "stopped" | "waiting" | "interrupted" | "done", sessionId?, startedAt?, doneAt?, summary? }
  planPush?: { key, state: "running" | "stopped" | "waiting" | "interrupted" | "accepting" | "done", sessionId?, proposalId }
                                   — the latest push
continuation.check.result          — gains:
  source: { kind: "remote_base" | "main_checkout", branch, revision }
  notRead?: { reason: "other_branch", branch }
  uncommitted: string[]            — this PRD's documents with uncommitted changes, not read
  origin?: { kind: "commit", revision, committedAt, subject } | { kind: "unpushed" }
  followsPush?: string             — the latest push whose re-check produced an offer of this scope
```

Audit rows carry the title and line of §Closing-Audit Names, and a session of test fixes carries `fixing: { loop, session }`. The numeric `round` and `continuation_index` stay in JSON as identifiers. `kiln status` text prints the states of AC-BOT-02 in the page's words. In `kiln status` JSON the check is `continuation`, with `check`, `summary` (the terminal's sentence for the answer), `waiting` (the pull request the card names, while the delivery waits), `answer` (`source`, `notRead`, `uncommitted`, `origin` and the unfinished `phases`) and `proposal`; `after_delivery` is the saved reading without `headSha`. `interrupted` is an activity held at the restart review (§After-Delivery Activities), and wins over `waiting` while the review holds; `kiln status` prints it as "merging, interrupted" (or "pushing the plan, interrupted") and lists `continue` as the control that resumes it. `accepting` is a push activity past Done whose plan check has not yet decided (§Continue and the Push Session); its row and header are §Display Contract's.

## Display Contract

**Header of a finished run**, first match:

| The run | Header |
|---|---|
| A merge or push session stopped, or held for billing | **Needs you** |
| A merge or push session interrupted and held for Resume | **Merging** (**Pushing the plan**), with the fact "Interrupted · Resume to carry on" |
| A merge or push session waiting for usage | **Waiting for usage**, as today |
| The merge session is running or starting | **Merging** |
| The push session is running or starting | **Pushing the plan** |
| A push activity is `accepting` | The plan check in progress, as today's running check |
| The check found unfinished phases | **New phases found** |
| A check that is not waiting is running or failed | As today |
| Every pull request merged | **Merged** |
| Otherwise | As today: **PR ready for review** and its variants |

While the delivery waits, the check never changes the header.

**Screens.** A finished run with an open activity picks its screen from the activity's state, first match. At a stop or billing hold it shows the existing Needs you page, with copy for each activity (state 4). Held at the restart review, it shows the finished page, whether the session was interrupted while running or while waiting. While waiting for usage it shows the existing Waiting screen, which names the activity as its row does and adds Exit Kiln (Kiln Usage Limit Recovery AC-LIMIT-04). Running, or being started, it shows the finished page, with the session in the pull request card (states 2 and 5). A push activity `accepting` shows the finished page with the plan check in progress and its row reading **Pushed**. Disconnected, the page keeps the last screen it showed, as today. No other screen is added. At a merge stop, a pull request read `closed` says “{repository} #{number} was closed on GitHub without merging. Reopen it there, then press Resume.” in its check row and in place of the line under the last message that says the pull request is unchanged. The card's line about a closed pull request shows only while no merge activity exists; while the merge session runs, that pull request's row reads Closed without merging and nothing more. The pull request card carries the merge button and note, the conflict mark, the per-request states and the one line about new phases with **Merged it yourself? Check now**, which reads **Check now** while that pull request is closed (state 1). Once Merged, Exit Kiln is the card's main button (state 3). Exit Kiln is enabled, or disabled with its reason, as §Exit Kiln says (state 2). The check's panel shows only the two answers (state 5). The terminal says the card's sentence while the delivery waits. The mockup is the reference for all wording.

## Data Models and Upgrade

The record gains one object at schema 25, and the field `continuationBaselineId` below:

```
afterDelivery?:
  pullRequests: { repository, number, state, headSha?, mergedAt?, mergeCommit?, conflicts?, order?, readAt }[]
  readError?: { at, problem }
  checkedWhileClosedAt?: string
  merge?:    { operationId, requestedAt, via: "browser" | "command_line", pullRequests: { repository, number }[],
              pressHeads: { repository, sha }[], doneAt?, closedAt?, summary? }
  planPushes?: { operationId, requestedAt, via, proposalId, offered: { id, phaseScopeDigest }[], doneAt?, closedAt?,
                 refreshedScope? }[]
```

`planPushes` gains one entry per Continue press that opens a push, and entries are never removed; an entry only gains `doneAt`, `closedAt` and `refreshedScope`. Its activity key is derived from `operationId` (§After-Delivery Activities, "Keys"). The open push is the entry without `closedAt`, and there is at most one. An entry with `doneAt` and no `closedAt` is `accepting` (§After-Delivery Activities, "Ending"); `closedAt` is written in the same save as the acceptance row on a match, or with the result shown otherwise. The snapshot's `planPush` describes the latest entry. The merge's `closedAt` is written in the same save as its `doneAt`, so both kinds give the latest after-delivery activity's `closedAt` that ends Complete's timing (§After-Delivery Activities, "While open").

A continuation acceptance gains `planPushKey?`. The automatic acceptance sets it to its push's key. When a push closes after Done and its re-check found an offer, the same save records that offer's `scopeDigest` on the push's entry as `refreshedScope`. A check result carries `followsPush: <key>` while its offer's `scopeDigest` equals the latest push's `refreshedScope`, whatever started the check: Check now, a page load, `kiln run`, or the check that a grant or an acceptance runs itself. A person's acceptance copies `followsPush` from the check it runs itself. A grant leaves the `scopeDigest` unchanged, so accepting after granting early merges still carries the key. Any change to the offer's scope drops it: the base moved again, the phases changed, or the settings changed. A push whose re-check found no offer records nothing, so a build accepted after a later check shows no row.

Sessions, stops and waits of the two activities live in the record's phase facts under their keys, as for any activity. The session kind, stop kind and activity kind unions gain the values in §After-Delivery Activities. A proposal gains `source: { kind: "remote_base" | "main_checkout", branch, revision }` and, for the main checkout, its commit list, as optional fields, and loses `sharedDigest`. For the main checkout, `branch` and `revision` are the base branch and the tip commit the offer was read from, which the push activity's folder check holds the checkout to. The input observation `shared_documents` is removed. Stored proposals that carry `sharedDigest` still read and verify, since their id is the hash of the stored body. A pending grant made before the upgrade is superseded by the first new check, because the proposal's `scopeDigest` changes, and is given again.

The carried-finished set (§The Plan Check, step 3) is derived from the retained baseline named by the record's new optional `continuationBaselineId`: its completions that carry no `waiverId`. Continue's activation sets the field to the baseline it writes. A folder start never sets it, and no plan read changes it. An execution activated before the upgrade has no field and no carried-finished set, as today. Since the field is optional, the migration adds nothing. A saved check result made under the old rules is dropped, so no stale "Plan needs reconciliation" or waiting panel can render before the first new check. Saved baselines, proposals and acceptances stay readable. Kilns at schema 24 refuse schema 25 under the existing newer-schema rule. All new times are UTC ISO 8601.
