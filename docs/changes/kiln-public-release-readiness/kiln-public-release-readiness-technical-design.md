# Technical Design: Kiln public release readiness

**PRD:** [kiln-public-release-readiness-prd.md](kiln-public-release-readiness-prd.md)
**Assumptions:** [kiln-public-release-readiness-assumptions.md](kiln-public-release-readiness-assumptions.md)

## Overview

Most of this change is content and configuration: package metadata, repository files, help layout, release notes, documentation and a few test fixes. The one architectural change is how Kiln decides whether it can use an agent feature. Today three features are gated on an exact version (billing inventory on Claude Code 2.1.307 with Agent SDK 0.3.310, live control on Claude Code 2.1.311, PowerShell for Codex on Windows on 7.5.2) and the Codex compaction readers reject any new field. This design replaces every exact gate with two things:

1. **A minimum version**, held in one module, checked by the start checks (Node.js, Git) and by each agent's readiness (Claude Code, Codex), and accepted for every version above it.
2. **Contract recognition at runtime.** Each feature checks the specific information it reads. When that information is missing or changed, the feature is marked unavailable with a compatibility notice naming the feature and agent version, and the rest of the run carries on. Information Kiln doesn't read is ignored.

Proof that billing and live control work on newer Claude Code comes from recorded contract fixtures captured on the newest Claude Code during implementation, replayed through the real adapters, plus mutation tests that show each recognition check turns the feature off rather than failing the run. No release-time test run on the newest agents is required (AC-AGENT-06 retired).

## Existing Code

- **Posture: Preserve.** Kiln is published from `develop` to real users' projects; billing, live control and Codex evidence behavior are constraints except where this PRD changes them.
- **Reused:** the billing route rule (subscription only with complete inventory, `claude.ai` authentication and the first-party provider), the passive settings worker and its bounded process, the live gate, checkpoint hook and replayed-message receipts, `supportedCodexVersion`, the command contract reference (`prompts/kiln-command-contracts.json`), `scripts/release.mjs` `checkRelease`, and the CI `full` scope.
- **Kept:** the checkpoint hook fails closed whenever a takeover is held; a billing reading Kiln does not fully recognise shows **Claude Code settings**, never **Claude subscription** (AC-BILL-02); delivery command evidence from Codex history that Kiln can't read completely is refused, as today.
- **Kept:** recorded fixtures named for the version that produced them (for example `claude-2.1.311-message-contract.json`) stay as historical evidence and are not renamed.

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Where minimums live | One module of agent tooling minimums (Claude Code 2.1.311, Codex 0.162.1, Node.js 22.15, Git 2.29, PowerShell 7.5.2) with one version-comparison function. `CODEX_MIN_VERSION` moves into it. | AC-AGENT-05 needs start checks, the README and every gate to state the same numbers. One source makes the README test and the standing guard below possible. |
| Standing guard against new exact pins | A unit test scans every file in `src/`, `scripts/` and `prompts/`, except tests (`*.test.*`), `src/test-support/`, `test/fixtures/` and the minimums module, and fails on any version literal it finds. A version literal is three dot-separated whole numbers, each dot optionally escaped with a backslash, that are not part of a longer dotted number. So `2.1.311` and `/^2\.1\.311/` count, and `127.0.0.1` in either form does not. In TypeScript and JavaScript files the test reads only string, template and regular expression literals, taken from the syntax tree built by the `typescript` development dependency. Comments are therefore never scanned, and a note recording which version a behaviour was observed on stays. Other files (the command contracts, prompt texts, PowerShell) are scanned as whole text, because they state requirements to people and agents. A short named exemption list inside the test pairs a file with the exact literal it allows, with a reason for each:<br>- the saved audit profile `codex-0.162.1-static-v1` that older records carry (`src/session/codex-evidence.ts`);<br>- Kiln's own version `1.0.0`, in `kiln_version` (`src/control/server.ts`) and in the `clientInfo` of the three Codex app-server clients (`codex-metadata-rpc.ts`, `codex-history-rpc.ts`, `codex-work-rpc.ts`);<br>- the proof peers' own identities: `0.1.0` in `scripts/proof-run/codex-rpc.mjs`, and the probe server's `1.0.0` in `scripts/proof-run/codex-launch-probe-proof.mjs`.<br>An exempt literal in any other file, or any other version in an exempt file, still fails. | AC-AGENT-01 applies to every future feature. A test catches the regression at the commit that introduces it; a review note would not. Today's live gate is a regular expression, so a plain text search would miss the very pin this change removes. The command contracts are what `kiln <command> --help` and `kiln --help --json` print, so an exact version there states a requirement that AC-AGENT-03 removes. Without the comment, saved-identifier and self-version rules, the guard would fail on provenance notes, force a change to saved data, or treat Kiln's own version as an agent's. |
| Version comparison | A tool's version is the first `major.minor.patch` in its `--version` output, compared numerically with the minimum. Build metadata (`+…`) and text after the version (`(Claude Code)`, `(Apple Git-154)`, Git for Windows' `.windows.1`) are ignored. A prerelease (`-…`, such as Codex `0.167.0-alpha.4`) is supported when its `major.minor.patch` is above the minimum, and below minimum when it equals or is under it, because a prerelease comes before its release. Output Kiln can't parse, or a `--version` that fails, is **unrecognised**, never below minimum. Per feature:<br>- **Start checks and agent readiness:** below minimum is a start problem for Node.js or Git and a readiness blocker for Claude Code or Codex (Start checks for versions row); unrecognised is neither.<br>- **Codex sessions and metadata:** below minimum leaves Codex unselectable with a blocker naming the minimum and how to update. Unrecognised blocks nothing: the launch profile records the version as Codex reported it, and Codex's own protocol reads decide.<br>- **Codex command evidence:** below minimum refuses delivery command evidence; unrecognised proceeds.<br>- **Billing:** the settings worker doesn't run, so billing shows **Claude Code settings** (AC-BILL-02).<br>- **Live control:** **Message Claude** and **Pause & take over** aren't offered for that attempt. A `live_messages` and a `takeover` notice give `agentVersion` as reported, or `unrecognised`.<br>- **PowerShell (Codex on Windows):** see its row.<br>The Codex requirement text and the README drop "stable".<br>Replaces in part: `docs/prds/kiln-codex-support/kiln-codex-support-technical-design.md`, §Codex process and version contract ("Reject older, prerelease or unparseable versions": prereleases above the minimum and unrecognised versions are now accepted) | AC-AGENT-01 forbids refusing a version above the minimum. Codex publishes alpha builds above it every few days, and people run them. `--version` output is itself agent information (AC-AGENT-07). Nothing Codex runs needs the version beyond the minimum, and its sign-in, model and account reads are checked already. Billing and live control keep the conservative side because their fallbacks are designed (AC-BILL-02, AC-AGENT-04). |
| Start checks for versions | `kiln run`'s start checks add Node.js (from the running process) and Git; either below its minimum is a start problem naming the minimum. An agent's minimum is part of that agent's readiness: Claude Code or Codex below its minimum is a readiness blocker for that agent, shown on Documents found when it is selected and checked again before every session launches, naming the minimum and the update command. An agent that isn't selected isn't read, so an outdated one blocks nothing. An agent that isn't installed is not a start problem. An unrecognised version, of an agent or of Git, is not a start problem; each feature then applies the Version comparison row. | AC-AGENT-05, within AC-AGENT-03 of `docs/prds/kiln-codex-support/kiln-codex-support-prd.md` (readiness follows the selection), which this PRD doesn't replace. Start checks run before the agent is chosen and are skipped for a feature already underway (AC-START-02 in `docs/prds/kiln-v1/kiln-v1-prd.md`), so they can't see which agent will run. Readiness is checked at every launch, including after a resume, so no session starts on an outdated agent. |
| Billing gate | The settings worker runs whenever Claude Code reports a parseable version at or above the minimum and the installed Agent SDK provides the settings resolver. The CLI and SDK version numbers no longer decide anything else. The worker's passivity (it starts no Claude process and runs no hook, credential helper or `policyHelper`) rests on the SDK's documented contract for its settings resolver, which the passive boundary test's canaries check (Proving section).<br>Replaces in part: `docs/changes/kiln-billing-safeguards/kiln-billing-safeguards-technical-design.md`, §Passive inspection without a model request (the qualified 2.1.307 / 0.3.310 contract, and not calling the resolver for an unknown contract) | AC-AGENT-02 and PUB-003. The existing route rule already demands complete, recognised inventory plus a recognised subscription from `claude auth status --json`, which is Claude Code's own view of the effective credential. The pin also held passivity to one inspected SDK; AC-AGENT-01 forbids pinning the SDK, so the documented contract and the canary tests carry that guarantee instead. |
| Billing recognition | Inventory is complete only when the resolver result has the expected shape (a source list and an effective settings object), every source tier is one Kiln knows, and every billing field Kiln reads has the expected type. Unknown fields are ignored. Any failure records a diagnostic and leaves inventory incomplete, which yields **Claude Code settings**. | This is the existing extraction rule. It is stated here because it is now the only gate. |
| Billing contract identifier | `BILLING_CONTRACT` becomes a revision of Kiln's detection rules (`claude-settings-v4`), with no agent or SDK version in it. The billing fingerprint no longer includes the Claude Code or Agent SDK version either. An update of either alone keeps an existing approval. A change in anything the fingerprint still covers (route, provider, sources, credentials, helpers, payer, launch profile), or a reading whose inventory is incomplete, still voids it.<br>Replaces in part: `docs/changes/kiln-billing-safeguards/kiln-billing-safeguards-technical-design.md`, §Context identity and invalidation (the detection-contract version no longer names an agent or SDK version, and a CLI or SDK version change no longer invalidates approval; a detection-contract change still does) | The contract identifier and the fingerprint together decide whether an approval still applies. With an agent or SDK version in either, each automatic Claude Code update would void a metered approval and hold an unattended run at Needs you, which AC-AGENT-01 forbids. AC-BILL-05 names provider, credential source, payer and credential as what needs new approval, not a version. An update that changes the billing context Kiln can see changes those fields. An update that stops Kiln recognising the settings leaves the inventory incomplete, which changes the fingerprint and voids the approval as today. Moving from v3 voids existing metered approvals once, and people re-approve on their next run. |
| Live control eligibility | Offered on macOS for Claude Code at or above the minimum. The attempt records the actual version as its profile (`claude-code-<version>/darwin`) for diagnostics; the profile is never compared for equality. The live command contracts' `limits` text and the unavailable reason name no version.<br>Replaces in part: `docs/changes/kiln-live-session-control/kiln-live-session-control-technical-design.md`, §Literal input and admission (live input only on an explicitly validated profile) and §Phase 1 implementation facts (takeover only on Claude Code 2.1.311/macOS) | AC-AGENT-03. Literal handling of a live message on versions above the minimum is an accepted risk (PUB-004). |
| Live message recognition | Each attempt's message contract starts **unproven**. An **echo** is a `user` event with `isReplay: true`, the attempt's provider session ID and the UUID of a message Kiln sent. An echo matches when its text (`message.content` as a string, or an array of only `text` blocks joined with nothing) equals the sent text, or, for the last message of a batch Claude Code merged, equals the batch's sent texts in sending order joined with a newline, where every earlier message of the batch already has its own matching echo in this attempt and none of them has yet been named as consumed. **Consumption** is a sent UUID in `user_message_uuid` or `user_message_uuids` on an `assistant` or `result` event. The contract becomes **recognised** when a sent message has a matching echo and is later consumed. It becomes **unrecognised** when any of these happens:<br>- an echo for a sent UUID does not match;<br>- an `assistant` event, or a `result` with `is_error: false`, names a sent UUID as consumed with no echo for that UUID earlier in the attempt;<br>- an `assistant` or `result` event carries a `user_message_uuid` that is not a string, or a `user_message_uuids` that is not an array of strings.<br>Consumption that is never reported changes nothing on its own. The receipt stays **Sent to session — not confirmed read** and becomes **Delivery uncertain** when the attempt ends, as today. Unrecognised turns messaging off for the rest of the attempt, and the message concerned shows the existing **Delivery uncertain** receipt. | These are the exact fields messaging depends on. The literal `text_not_typed` flag can't be observed directly; verbatim echo is the observable proof that the text arrived. A version could still expand a leading slash command or file reference while echoing the text verbatim; that is the accepted risk in PUB-004. The newest-version live proof confirms today's newest Claude Code still takes the fixture's slash command and file reference literally. Claude Code echoes each prompt before the first reply that names it, so consumption with no earlier echo means the echo is gone. It merges prompts queued for the same turn into the last one's UUID: each earlier member is echoed alone, and the last is echoed with the joined text. An error result is exempt because a turn cut off before its first reply can name its prompt without echoing it. A missing UUID is normal: older versions, failed deliveries and turns Kiln didn't send carry none. Observed on 2.1.311 (recorded fixture and saved runs) and read from the 2.1.317 binary; the ordering for a prompt folded in mid-turn and the error-result exemption are not yet observed, and either could only cause a false **unrecognised**, which the newest-version live proof would show. |
| Takeover hook recognition | The checkpoint hook needs `session_id`, `hook_event_name`, `tool_use_id` and `tool_name` (on `PreToolUse`), and needs `PostToolBatch` to fire after admitted tools resolve. When no takeover is held and the input is in a form Kiln doesn't recognise, the hook records the contract as unrecognised in the gate and lets the tool proceed. While a takeover is held, any failure still denies. The hook records the tool-use ids of every `PostToolBatch` (`tool_calls[].tool_use_id`) in the gate, whether or not a takeover is held. On the live stream the engine marks the contract unrecognised in two cases. First, a `tool_result` whose `is_error` is not `true` names a tool call the gate never admitted; results from calls that never ran, such as invalid input, unknown tools, denials and interruptions, are always errors and don't count. Second, in the main conversation (`parent_tool_use_id` null), an `assistant` event starts a new model response (a new `message.id`) in the same turn (no `result` since), after a response whose tool calls the gate admitted, and no recorded `PostToolBatch` names any of those calls. Unrecognised turns takeover off for the rest of the attempt. A takeover already accepted keeps its hold: the gate stays held and keeps denying new tools, nothing interrupts or ends the attempt, and the pausing reason says the safe checkpoint can't be used and Kiln is waiting for the attempt to end. Once the contract is unrecognised, an operation the hook can't settle is settled by its tool result in the stream, so it never keeps the attempt's input open; release still requires the attempt and its tracked processes to have exited. | Today an unrecognised hook input fails the hook, and with `onFailure: block` that blocks every tool and stalls the run. AC-AGENT-04 requires the run to keep working. Failing closed while held keeps the existing safety guarantee. AC-TAKE-01, 02 and 05 still hold: an accepted takeover lasts until hand-back and is never cancelled or forced to make up for a missing checkpoint. Without stream settlement, an operation admitted before recognition failed would hold the drain open and the attempt would never end, with or without a takeover. Claude Code waits for `PreToolUse` before a tool runs and for `PostToolBatch` before the next model request, so both gate writes come before the stream evidence that checks them. The check uses a new response rather than any assistant event because tools start while their response is still streaming: a result can arrive between two events of the same response. It resets at `result` because interrupted, deferred and hook-stopped turns end without `PostToolBatch` and without another model request. Observed on 2.1.311 to 2.1.316 in saved runs; the `PostToolBatch` input shape is from the SDK declaration, and a different shape could only cause a false **unrecognised**, which the newest-version live proof would show. |
| Live launch arguments | If Claude Code exits before its first event and its error output names one of the live control arguments (`--replay-user-messages` or `--settings`), Kiln records the message and hook contracts as unrecognised for that Claude Code version, each with its notice, and relaunches the same attempt once without them. Any other exit before the first event stays the launch failure it is today. | A removed flag is a changed contract for one feature, not a reason to fail the phase. Limiting the relaunch to an error naming a live argument keeps it from masking sign-in, permission or other launch failures. The relaunch is recorded and reported, not silent. |
| Codex compaction | Both compaction readers, the thread's own compaction and a fork's copy of an ancestor's, require the fields they read and check their values as today, and ignore any other fields.<br>Replaces in part: `docs/prds/kiln-codex-support/kiln-codex-support-technical-design.md`, §Authoritative evidence (an unknown compaction schema remains inconclusive; now only a missing or changed field Kiln reads does) | AC-AGENT-07. The snapshot never substitutes for original execution records, so an unread field can't hide evidence. Codex has already added fields to this record (`guardian_history` in 0.144) and dropped bookkeeping from fork copies (0.166). |
| Codex audit envelopes | Codex command evidence keeps its list of raw record types. An unknown record type still leaves the evidence inconclusive and now also writes a `codex_history` compatibility notice. | Receipts must rest on a history Kiln can read in full, so an unknown record type is information it needs (AC-AGENT-07), unlike an unknown field inside a record it reads. Codex 0.166.0 histories still use only known record types. |
| Codex tool inputs | Codex command evidence, the receipts final delivery reads, recognises `exec_command`'s parameters `cmd`, `workdir`, `shell`, `login`, `tty`, `yield_time_ms`, `max_output_tokens`, `sandbox_permissions`, `justification`, `prefix_rule` and, when Codex's `exec_permission_approvals` feature adds it, `additional_permissions`. A call with any other parameter gets no command receipt and writes a `codex_history` notice whose detail names the parameter and says that command has no receipt; the feature stays on for every other call. `view_image` and `wait` inputs keep their checks on the parameters Kiln reads and ignore any others, so a new parameter in either never withholds a receipt, including for later calls in the same exec cell. The proof capture's evidence policy reads the same recognised parameter list. | A receipt states which command ran, where, and how it ended. An unknown `exec_command` parameter can change where or how it ran, as an environment selection would, so it is information the receipt needs (AC-AGENT-07, AC-AGENT-04). `additional_permissions` only widens the sandbox, less than the already accepted `require_escalated`, and receipts never rely on the sandbox. `view_image` only reads an image and `wait` only polls or stops a cell; neither yields a receipt. Codex 0.166.0's default `exec_command` declaration lists exactly the ten parameters above; its schema adds `additional_permissions` under that feature, `environment_id` on `view_image`, and `terminate` on `wait`. |
| PowerShell (Codex on Windows) | Every Codex process Kiln starts on Windows runs under a PowerShell Job Object supervisor. Before each Codex launch on Windows, Kiln reads the `pwsh` version and applies the Version comparison row against 7.5.2. A version below the minimum, or a missing `pwsh`, refuses the launch as a Codex readiness blocker in the existing **Agent selection and readiness** check, worded as in Version problem wording. An unrecognised version proceeds, and the existing Job Object startup check decides. The launch profile records the version as reported. The PowerShell reader, which only full-history proof capture and its tests use, accepts the same minimum. An AST node or alias inventory it doesn't recognise leaves that evidence inconclusive, as a parse failure does today. Its integration tests run on any `pwsh` at or above the minimum. Neither writes a compatibility notice.<br>Replaces in part: `docs/prds/kiln-codex-support/kiln-codex-support-technical-design.md`, §Authoritative evidence, "Native PowerShell reader" (the pinned `pwsh` 7.5.2 and the launch profile's exact version check) | AC-AGENT-01 and AC-AGENT-05; the PRD Terms count PowerShell as agent tooling. A PowerShell problem stops Codex before any session exists, so it is a readiness blocker like Codex's own minimum, not a notice for a run underway. Delivery receipts match PowerShell commands by their recorded argv and never parse them, so no running feature depends on PowerShell recognition. The supervised startup check already proves an unrecognised `pwsh` works. |
| Compatibility notices | A recognition failure in any feature above writes a notice to the PRD record. The record holds at most one notice per feature: a later failure replaces it, and the feature's next successful recognition removes it. Billing writes none; it follows AC-BILL-02. PowerShell writes none; it is a readiness blocker (its row). A notice reads `<feature> unavailable with <agent> <version>: <detail>`, with the features named **Message Claude**, **Pause & take over** and **Codex command evidence**. It shows in three places:<br>- **Live controls, while the attempt runs:** an unrecognised message contract makes `input` unavailable with the notice as its reason. An unrecognised hook contract makes takeover (the live view's `available`) unavailable with the notice as its reason, except while a takeover is held, when the hold's reason stands (Takeover hook recognition row); `input` is unaffected. These replace the "validated Claude Code 2.1.311/macOS profile" and "this Claude CLI/profile" reasons. Below the minimum or off macOS, the reason names the requirement without a version (Live control eligibility row). Status `controls` carry the same reasons.<br>- **Browser view, every screen:** the snapshot carries the record's notices. The page shows them in one existing-style `command-notice` panel headed **Agent compatibility**, one line per notice, with no dismiss. It stays until the record drops the notice.<br>- **`kiln status`:** the targeted result, and so each inventory `runs` entry, gains `compatibility: [{ feature, agent, agent_version, detail, attempt_id, observed_at }]`, empty when there are none: the record's notice fields in the result's snake_case, with `agent` from `agentId`. It is read from the saved record, so it is present with the controller stopped. Text mode shows it through the existing field listing; the progress block is unchanged. `status` `result_fields` in `prompts/kiln-command-contracts.json` adds `compatibility`. | AC-AGENT-04 requires the feature and agent version to be visible in both places. One per feature keeps the list bounded and stops a notice from an earlier Claude Code or Codex outliving the version that caused it. The live reasons last only as long as the attempt, and Codex command evidence has no screen of its own, so the record-level panel is what keeps every notice visible. |
| Kiln's own dependencies | Runtime dependencies use caret ranges (`acorn` moves from `8.19.0` to `^8.19.0`). The `@anthropic-ai/claude-code` development dependency is pinned to the minimum, 2.1.311, for the passive boundary test, which also accepts a path to another Claude Code so implementation can run it on the newest one. | AC-AGENT-01 allows a test to pin a dependency to replay a contract, provided that isn't the only proof for newer versions. |
| Proof scripts | Proof and exploration scripts accept any version at or above the minimum and record the actual version in their output and in any fixture they write. | AC-AGENT-01 names proof tools. |
| Text help | Each command contract gains a `group`. Top-level text help prints a one-line description, the start line (`run`) and the status line (`status`), then each remaining group under its task heading in a fixed order, with the group's command names on one line. Purposes, availability and flags stay in `kiln <command> --help`. Every command in the `kiln-sessions` group is collapsed into one line giving the count of its runnable helpers (contracts whose `side_effect` is not `group`). A closing sentence points bots at `kiln --help --json`. The `guidance` paragraph moves out of text help and stays in the JSON. A test fails if the output exceeds 40 lines or any line exceeds 80 characters.<br>Replaces in part: `docs/prds/kiln-bot-control/kiln-bot-control-technical-design.md`, §Discovering commands (`kiln --help` showing the whole command tree, and the bot guidance surfaced in text help) | AC-HELP-01 and 02. Text help and JSON help keep one source. JSON help gains the field and loses nothing. Contract purposes run up to 156 characters, so one purpose per line wraps past 40 rows on an 80-column screen. The names under a task heading fit with room to spare and need no second description to keep in step with the purpose. |
| `--version` | Handled first in command routing, before inspection commands, printing the version from Kiln's own `package.json`. | AC-HELP-03: no controller, Git or sign-in may be needed. Routing is where the command tests already reach. |
| Usage errors | A `kiln run` usage error (no path, more than one path or an unknown flag, a path that isn't one PRD, `--resume` before anything has started) prints its one-line reason, when it has one, then `Usage: kiln run <PRD-path> [--resume]` from the `run` contract and `Use kiln run --help for details.` The shared multi-command usage block is removed, along with the `kiln run` entry point's own help, no-argument and unknown-command answers, which `kiln --help` and the command contracts already give. | Source maps | The production build (`tsconfig.build.json`) and the view build emit no source maps. Development type-checking keeps them. | AC-PKG-02. |
| Clean builds | `npm run build` removes `dist/` first with a cross-platform Node step. | AC-PKG-03. Windows CI packs too, so the step can't be a shell `rm`. |

| Run that stops before publishing | The release pull request into `main` is that run. ## Interfaces

### Agent tooling minimums

```
AgentToolingMinimums:
  claudeCode: "2.1.311"
  codex: "0.162.1"
  node: "22.15.0"
  git: "2.29.0"
  powershell: "7.5.2"        # Codex on Windows only

compareToMinimum(tool, versionOutput) -> { state: "supported" | "below_minimum" | "unrecognised", version?: string }
```

Each tool's `--version` output format (for example `2.1.317 (Claude Code)`, `codex-cli 0.166.0`, `git version 2.39.5 (Apple Git-154)`) is parsed by the module.

### Version problem wording

```
Git 2.25.1 is older than Kiln supports. Install Git 2.29 or later.
Claude Code 2.1.300 is older than Kiln supports. Install Claude Code 2.1.311 or later: claude update
Codex 0.160.0 is older than Kiln supports. Install Codex 0.162.1 or later: codex update
PowerShell 7.4.6 is older than Kiln supports. Install PowerShell 7.5.2 or later.
Codex on Windows needs PowerShell 7.5.2 or later. Install it before starting work.
```

Node.js and Git take one line each in the existing start-failure list. An agent's line is one of that agent's readiness blockers, which Documents found shows and every launch checks. An update command is named only where versions below the minimum provide it; otherwise the line ends at "or later". PowerShell's lines are Codex readiness blockers on Windows, reported by the check before each Codex launch.

### Top-level text help (shape, at most 40 lines of at most 80 characters)

```
Kiln runs an Enso Method phase plan with Claude Code or Codex.

Start:        kiln run <PRD-path>
See work:     kiln status

Answer a stopped phase
  <command names in this group, comma separated>
Pause and take over
  <command names in this group, comma separated>
Look closer
  <command names in this group, comma separated>

Used by Kiln's sessions: <count> helper commands (kiln <command> --help for each).
Bots and scripts: kiln --help --json lists every command with full metadata.
```

Command contract addition: `group: "start" | "answer" | "live" | "inspect" | "kiln-sessions"`. `start` holds `run` and `status`, printed as the two opening lines. The text help renderer holds the order and heading of the other groups: answer, live, inspect. The implementer assigns the people-facing commands to groups by task. A test checks that every contract has a group.

## Data Models

```
CompatibilityNotice:                     # PRD record, compatibility[]; at most one per feature
  feature: "live_messages" | "takeover" | "codex_history"
  agentId: "claude_code" | "codex"
  agentVersion: string                   # as reported by the agent, or "unrecognised"

  observedAt: string

SessionRun.live (existing):

  messageContract: "unproven" | "recognised" | "unrecognised"      # new
  hookContract: "unproven" | "recognised" | "unrecognised"         # new

  contract?: { state: "unrecognised"; detail: string; at: string }  # written by the checkpoint hook

```

These fields are additive and optional. Records without them read as before. The implementer decides whether that warrants a `SCHEMA_VERSION` increase under the record's existing migration rules.

## Integration Points

- **Claude Code CLI:** `--version`, `auth status --json`, stream-json output with `--replay-user-messages`, and hooks supplied through `--settings`. Every field read from these is checked by its feature as above.
- **Claude Agent SDK:** the settings resolver, in the existing disposable worker. Users' installs resolve the newest matching 0.3.x, not Kiln's lockfile, so the shape check is what protects newer SDKs.
- **Codex CLI:** `--version` and retained rollout history (compaction, record types and tool inputs).
- **GitHub:** repository description, website and topics; branch deletion; `.github` issue forms and pull request template; Actions release workflow.
- **`enso-method-website` repository:** the Kiln page source (`scripts/kiln-page.mjs`) states the same minimums and platform support (AC-SYNC-01, 02). Deploying it stays out of scope.
- **npm:** package metadata only. Publication stays out of scope.

## Open Questions

If it fails, the minimum becomes the oldest version on which both billing and live control pass, and AC-AGENT-05 and the README change with it.

If they show the resolver starting Claude Code or running a hook, helper or `policyHelper`, billing on that SDK needs a design change before release.
