# Technical Design: Kiln Pause Now

**PRD:** [Kiln Pause Now](kiln-pause-now-prd.md) · **Assumptions:** [Kiln Pause Now assumptions](kiln-pause-now-assumptions.md) · **UI contract:** [mockup](mockups/kiln-pause-now.html) · **Builds on:** [Control a live Kiln session technical design](../kiln-live-session-control/kiln-live-session-control-technical-design.md)

## Overview

Pause now is the existing safe takeover, renamed and re-presented. The hold, its provider gate, its release and its hand-back stay as they are; no existing identifier, route, journal action, bot command or status value changes. Three things are new underneath the wording:

1. **The stop becomes a durable gate fact**, written the first time the gate acts on a hold (a refused operation, a yielded batch, or sealed input). With the attempt's end, it is the boundary Cancel is checked against.
2. **Cancel pause and keep going** is a browser-only live instruction that withdraws a takeover hold before the stop, in the same critical section the gate uses.
3. **One engine projection, the Pause now state** (`pausing` or `paused`), drives the header, the phase plan row, the pause panel, the paused page, `kiln run`'s terminal lines and `kiln status` wording, so no surface re-derives it from hold internals.

## Existing Code

**Posture: Preserve.** Everything this design touches is published and in use.

- Reused unchanged: the `take-over` journal action, `POST /api/live/take-over`, the bot `take_over` action and `kiln take-over`; the attempt gate and checkpoint hook; release reconciliation; terminal ownership admission; `POST /api/resume` with its takeover `note` and the existing already-complete advance; the carry-on path for a conversation that can't be reopened; the end-of-activity pause and its cancel.
- Reused, with an added field: the gate state, the takeover hold, the live snapshot.
- Behavior to keep that the code alone doesn't make obvious: a hold reaches the running session only through the gate's three responses (deny, yield, seal) and through refusing new live input. Nothing is sent, signalled or interrupted. This is what makes Cancel before the stop safe (PAUSE-005), and nothing in this build may add another effect of a hold on the session.
- The delivery-recovery hold (an uncertain message) shares the takeover record but is not Pause now: it keeps its own page, wording and behavior throughout.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| What Pause now is | The existing `take-over` instruction, under the new name everywhere a person reads it. Machine-read names (`take-over`, `take_over`, `takeover_requested`, `effects.takeover`, compatibility feature `takeover`) stay. | AC-PAUSE-02 says it does exactly what takeover does today. Bot control's JSON contract promises stable state and error identifiers (AC-CLI-01 in `docs/prds/kiln-bot-control/kiln-bot-control-prd.md`), and bots already tell a takeover apart by its takeover fields, so a new status value or a renamed identifier would break scripts and tell them nothing new (PAUSE-006). |
| Where the stop is recorded | In the attempt gate, inside its critical section, by whichever of the three gate responses first acts on the current hold. | The gate is the only place that can tell "nothing sent yet" from "Claude was told to stop", and it already serializes hook decisions with hold admission. Recording it anywhere else would race the hook. |
| How Cancel is admitted | Under the controller admission boundary and the gate critical section, in one synchronous step as take-over admission writes its hold: refused once the stop is recorded or the attempt's process has ended, otherwise the gate's hold is removed first, then the saved takeover hold. | One lock decides between Cancel and the gate's stop, so a cancel and a deny can't both win, and the operation-ID check (§Cancel) keeps a reading that started before Cancel from acting on its result. The engine consumes a hold as soon as the attempt's process ends (it records the activity's stop and treats the exit as the takeover's), so the running check must sit in the same step as both writes. Removing the gate's hold first means a crash between the two writes leaves a hold that no hook honors, which startup finishes removing (§Cancel). |
| Cancel with an uncertain message on the attempt | The hold returns to the delivery-recovery hold that uncertainty creates, re-derived from the receipts; otherwise the saved hold is removed. | "As if Pause now had not been pressed" (AC-PAUSE-04): a Pause now pressed from the uncertain-message recovery replaces that recovery's hold today, so withdrawing it must give it back. |
| When "Paused" begins | A `releasedAt` time set on the hold the first time release is observed, or the first time the attempt has ended and its conversation can't be reopened. It is never cleared while the hold lasts. | Reconciliation keeps running after release and turns the hold back to pending when, for example, the person opens Claude on the conversation. Today that flips the page back to "Pausing". The person is paused from the release on; a later failed observation is an obstacle on the paused page, not a return to pausing. |
| Which page an immediate pause lands on | A held Pause now (any takeover hold that is not delivery recovery, once its attempt has ended) gets its own screen. The existing recovery page keeps ordinary stops and delivery-recovery holds. | The paused page shares little with the recovery page: no checks section, two peer columns, Pausing and Paused states, and a different header. A branch inside the recovery page would multiply its conditions. The feature state stays `needs_you` underneath, so Resume, advance, carry-on and reset keep their existing admission. For the same reason the paused activity is still an unresolved stop after a controller restart, so `kiln run` reopens on its paused page with Resume, never on Start (AC-CLI-01 in `docs/prds/kiln-v1/kiln-v1-prd.md`: unresolved stops retain Needs you). |
| Naming the command | The gate records each operation's label at admission, with the tool and its main input stored separately: the input chosen by the session output's existing main-input rule (the tool line's own output unchanged), capped at 200 characters with an ellipsis. The hook reads `tool_input` for the label only: a missing or unexpected `tool_input` gives the bare tool name and never makes the hook contract unrecognised. The hold records which operations were in flight when Pause now was accepted, captured in the same critical section that writes the hold, and `lastCommand` is derived from that list when projecting. No settle time is recorded. | AC-PAUSE-03 and AC-PAUSE-05 name the running and last command. The hook already receives the tool input at admission, and the gate survives a controller restart; scanning saved events for it would be a second reader of the same fact. Storing tool and input apart lets the running row and the paused sentence render them differently. Under a hold the hook admits no new operation, so the in-flight list is exactly what can finish after the press, and once released all of it has finished. The hook contract requires only the fields it decides on (AC-AGENT-07 in Kiln public release readiness), and a display label decides nothing. |
| Retaining a take-over instruction ID in the browser | Kept only while the answer is uncertain, then forgotten. | Today it is kept after success, so a Pause now pressed again after a Cancel would replay the old instruction and get its old receipt without a new hold. |
| Cancel on the command line | None (PAUSE-002). The journal action is browser-only as `message-review` is: left out of `kiln status`'s `controls` and refused on the bot command route, and not added to the bot contract, help or capability features. | The approved scope. Every journal action otherwise appears in `kiln status`'s `controls` with a `kiln <action>` invocation and is accepted on the bot route, which would publish a command and a status value the PRD rules out. |

## The Stop and Cancel

Replaces in part: `docs/changes/kiln-live-session-control/kiln-live-session-control-technical-design.md`, §Safe Checkpoint and Release (a pending takeover hold can be withdrawn before its stop).

Replaces in part: `docs/changes/kiln-public-release-readiness/kiln-public-release-readiness-technical-design.md`, §Design Decisions, Takeover hook recognition row (an accepted takeover can be withdrawn before its stop; the hook reads `tool_input` for a label without making it part of the recognised contract).

**The stop.** The gate state gains `stop?: { at, by: "deny" | "yield" | "seal", operationId }`, bound to the hold's operation ID. It is written once, in the same critical section that returns the response: the checkpoint hook's first refusal under the hold (a `PreToolUse` deny, or the failure it returns for hook input it doesn't recognise while held, both `deny`) or `PostToolBatch` yield, or the session adapter's drain sealing input under the hold. Later responses leave it as written. A gate without a hold never records a stop. The field is additive; gate schema 2 readers that predate it ignore it, and nothing older can hold a Pause now this build creates. It is the one record of the stop: the existing `checkpoint` time, written on a yield and read nowhere, stays as it is.

**The attempt's end is also the stop.** An attempt can end under a hold before the gate acts on it: input sealed before Pause now was pressed, or the process ending on its own. Once the process has exited, the engine treats the exit as the takeover's and records the activity's stop, so Cancel is refused from then on, as after a gate stop. An attempt without a gate (a legacy attempt waiting for natural exit) has only this one: Cancel is offered until it ends.

**Cancel.** A `cancel-take-over` journal instruction carries `{ instructionId, target }` and the take-over hold's instruction ID. Its receipt is written before any effect. It is a live control like `take-over`: admitted on the exact live target rather than the status token, available wherever take-over admission accepts the attempt (including one recovered after `kiln run` restarts, whose hook still answers to the gate), and blocked only by another pending instruction. Admission requires a takeover hold (not delivery recovery) whose target and instruction match, no recorded stop for that hold, and the target attempt's process still running. Cancel is also offered while a compatibility notice holds the pause (AC-AGENT-04 in Kiln public release readiness): the hook's fail-closed refusal of the first new operation under the hold is the stop, so Cancel is refused from then on, and before it a cancel simply returns the attempt to running under its notice. Then, in order:

1. Inside the gate critical section, in one synchronous step with step 2, recheck the stop and that the attempt is still running, and remove the gate's hold. Either check failing refuses the cancel with code `already_paused` and the PRD's wording. An attempt without a gate has no gate hold: step 1 is the same synchronous check that its process still runs.
2. Replace the saved hold: with the delivery-recovery hold re-derived from unresolved uncertain receipts on the attempt, or with nothing.
3. Project the change. Live input availability, the pause panel and `kiln status` return to their unpaused state because they read the hold. The reconciliation timer keeps running, as it does after every other hold ends, and does nothing while there is no hold.

Cancel does not wait for a reading in flight. Reconciliation applies its results (the activity's stop, the "stopped" terminal event, `releasedAt` and `obstacle`) only while the saved hold's operation ID still equals the one it started with. A delivery-recovery hold that Cancel restores carries its uncertain receipt's ID, so it never matches.

The take-over receipt stays `takeover_requested`; the cancel receipt records `takeover_withdrawn`. A separately requested end-of-activity pause is a different record and is untouched. A later Pause now is a new instruction and a new hold.

**Restart.** Startup reconciles an unsettled cancel receipt before admitting other live actions: if the gate no longer holds its take-over, finish step 2 and settle it `takeover_withdrawn`; if the gate still holds it, settle it `not_applied` and the pause continues. With no gate, settle `takeover_withdrawn` if the saved hold no longer holds the take-over (step 2 already ran); otherwise finish step 2 and settle `takeover_withdrawn` if the attempt is still running, else `not_applied`. Settled take-over receipts are not re-reconciled, so a withdrawn hold is never recreated.

**Sleep while pausing (PAUSE-003).** The design adds nothing for sleep. No timer, signal or deadline in the hold moves it forward: the stop happens only when the gate next acts, which needs the session to run. The lid-close run under §Delivery confirms the assumption on real hardware.

## The Pause Now State

Replaces in part: `docs/changes/kiln-live-session-control/kiln-live-session-control-technical-design.md`, §Snapshot and browser (the pause panel's heading, choices and narrow-screen order, and the requested and completed takeover wording, for a hold that is not delivery recovery).

The engine projects one state for the activity under a takeover hold that is not delivery recovery:

```
PauseNowView:
  phase: "pausing" | "paused"
  activityKey, label            — the running header's name for the activity at that time (AC-PAUSE-03): "phase 2b", "delivery audit · round 2"
  requestedAt
  releasedAt?                   — present exactly when phase is "paused"
  stopped: boolean              — the gate recorded the stop or the attempt ended (Cancel withheld from here on)
  running: { tool, input? }[]   — labels of top-level operations still running, oldest first
  background?: { pid?, command? }[] — processes Claude started that the pause is still waiting on, after the stop or once Claude's turn has ended
  lastCommand?: { tool, input? } — label of the newest-admitted top-level operation in flight at the press and not backgrounded
  lastSaid?: string             — the last thing the agent said before the stop
  waitingSeconds?               — today's 30-second waiting figure (AC-TAKE-05)
  obstacle?: { code, reason }   — anything other than ordinary waiting for the attempt or its evidence
  cancel: { available, reason? }
```

`phase` is `paused` from `releasedAt` on, otherwise `pausing`. While a Resume or carry-on launched from the paused page is starting (the hold still saved until the new run reports in), no `pauseNow` is projected: the activity shows as starting, with today's "The new session is starting.", and reconciliation readings in that window write no `obstacle` or `hold.reason`, since the new session's own `claude --resume` is not a terminal in use. A launch that ends before reporting in returns to the paused page, `releasedAt` unchanged.

A running command takes the command row whether or not the stop has happened, because in a parallel batch a deny can record the stop while another command still runs. When `obstacle` is present, the obstacle row (its reason, as a warning) replaces the situation row and its lid sentence. Otherwise a non-empty `running` gives the command row; otherwise a non-empty `background` gives the background-process row, one line per entry, oldest first; otherwise, once `stopped`, the "Claude has stopped" row; otherwise the before-its-next-command row, since before the stop Kiln is waiting on Claude's next command. A background line reads "{command} (process {pid})", the command alone when there is no `pid`, or "process {pid}" alone when there is no `command`. From 30 seconds after the last observed activity, the waiting line shows below whichever row applies.

A top-level operation is *backgrounded* when its own tool result arrives while a non-ambient task it started (`tasks[*].toolId`) is still unsettled: the "running in background" result of a background Bash. The gate marks it once, in the critical section that sees the result, and never clears the mark. Agent and Task calls are never marked, because their settlement already waits for the subagent, and a foreground Bash's task ends before its result. `background` holds two kinds of entry:

1. Each backgrounded operation whose task is still unsettled, with its label's input as `command` and no `pid` (the gate keeps none for a task), while Claude's process runs and either `stopped` is set or Claude's turn has ended: the gate's `turnEndedAt` is set, every live input it tracks is answered, and every unsettled top-level operation is backgrounded. The gate records `turnEndedAt` when it observes a `result` for the target conversation and clears it on any later `assistant` event or newly admitted input, so a turn Claude starts on its own (a background task's completion notice) clears it too. The field is additive, as `stop` is, and is rebuilt when reconciliation replays events. Tracked live inputs alone can't show the end of a turn, because the first prompt and turns Claude starts itself are not among them. Before the stop this is the case where the stop never comes on its own: the hook only acts on Claude's next call, Claude makes none until the task ends, and the session's drain keeps input open for pending background work. Cancel stays offered there. After Claude's process exits, kind-1 entries are dropped: no task notification can arrive, and kind 2 shows anything still alive, while the release keeps waiting on the unsettled task under the "Claude has stopped" row, as today.
2. From the reading in which Claude's own process has exited and Kiln's last observation of it has finished, each tracked process still alive under its recorded start identity, with `command` when its command line is readable. Before then, the gate's `tracked` list holds Claude's own MCP servers, hooks and shells, which are not what release is waiting on.

The process lookup runs as its own first step of the one-second reconciliation reading (`reconcileTakeoverOnce`), before the release checks, because those stop at the first unmet condition. It checks each tracked identity with the start-identity reader the release check uses, then reads the live processes' command lines in one `ps -ww` call, each capped at 200 characters with an ellipsis like an operation's input. No signal is ever sent. The result is kept in memory, keyed by the hold's operation ID, applied only while the saved hold's operation ID still matches, and never saved: it is derived each second from the durable `tracked` list. The snapshot and the bot JSON's `pauseNow` both read it. After a controller restart it is empty until the first reading, which startup schedules at once, and the "Claude has stopped" row shows meanwhile.

Every reading, before and after `releasedAt`, sets or clears `obstacle` on the saved hold under the same operation-ID fence, except while a launch from the paused page is starting (above). A reading that fails with an error other than `takeover_pending` records `{ code, reason }`: the ownership error's code, or `state_unavailable` for any other error. A concrete error takes precedence over the checkpoint-unavailable text, so a checkpoint problem never hides `terminal_in_use`. Otherwise, before `releasedAt`, a safe stop Kiln can't establish records `{ code: "control_unavailable", reason }`: a hook contract that became unrecognised under the hold (with the checkpoint-unavailable text as its reason, reworded under §Wording), or an attempt with no gate, recovered from an earlier Kiln, whose process is still running. Nothing can stop such an attempt, so its row has no lid sentence, and once its process ends `stopped` is set and the "Claude has stopped" row applies. A reading that releases, that finds the conversation can't be reopened (the carry-on cards cover that), or that fails only with `takeover_pending` clears `obstacle`. Ordinary waiting (the attempt still running, a background process still alive, completed-operation evidence pending) is never an obstacle. `hold.reason` follows the same precedence, and the pausing panel never shows it. An obstacle shows on the paused page without changing its header.

With no hold, the panel is the idle pair from AC-PAUSE-01: heading **Pause**, **Now** then **After {activity}** in reading order, so Now comes first on narrow screens. In the After choice, {next activity} is "phase {id}" when the running activity is a phase and another leaf follows it: the first row after the current one in the snapshot's plan order whose state is `planned` and which has no `splitInto`. When the running activity is an audit or the last open leaf, it reads "the next activity", as today's panel and the Paused page's "Paused before the next activity." do, because what follows depends on the audit's result or the configured audits. Every surface reads this projection:

| Surface | `pausing` | `paused` |
|---|---|---|
| Header (running overview, session page, held page) | New header kind: **Pausing {activity}**, amber outline with the progress arc, beside the phases done | The existing Paused look: **Paused in {activity}**, phases done, "Paused {time} · {how long ago}" from `releasedAt` |
| Phase plan row | Keeps its running pill; never Needs you | **Paused** |
| Pause panel | The pausing wording per AC-PAUSE-03, chosen from `running`, `background`, `stopped`, `waitingSeconds` and `obstacle`; Cancel per `cancel`; no Pause after is offered while pausing, though the engine still admits `request-pause` (`kiln pause`), and a pending end-of-activity pause stays below with its own cancel | Not shown, except a pending end-of-activity pause with its cancel |
| `kiln run` terminal lines | Nothing printed for the stop or the process's exit. At restart, the summary says "pausing in {activity}" where it says "needs you", and the ● line reads "{Activity} is pausing. Kiln finishes the pause on its own." | The activity's phase line, printed once when `releasedAt` is first set: "{time}  {key}  {name}  paused · at {address}", not amber and without "waiting for you". At restart, the summary says "paused in {activity}" where it says "needs you", and the ● line reads "Paused in {activity}. Press Resume {activity} to go on.", as "Paused before phase 3. Press Start phase 3 to go on." does today. A delivery-recovery hold keeps today's three lines. |
| `kiln status` text | "Pausing — …": the panel row's bold title, then its running commands or background process lines joined with "; "; for an obstacle, "Pausing — " and the obstacle's reason; no lid sentence or waiting line | "Paused" where it says "Paused for terminal takeover" |

`running` lists top-level operations (those without an `agentId`) that are unsettled and not backgrounded, oldest first. An Agent or Task call stands for its subagent's work, and each parallel top-level call gets its own row. The pausing panel's running row renders `Tool(input)` as the mockup does (`Bash(npm test -- src/refunds)`), or `Tool` with no input.

`lastCommand` is derived when projecting, not stored: the label of the newest-admitted top-level operation in the hold's in-flight list, captured in the same gate critical section that writes the hold, leaving out operations since marked backgrounded. Under a hold the hook admits no new operation, so that list is exactly what can finish after the press, and once released all of it has finished. With no top-level operation in the list, `lastCommand` is absent. The paused card's sentence uses `lastCommand` when set, naming a Bash command by its input alone and any other tool as `Tool(input)` ("Kiln stopped after {lastCommand} finished. Nothing is running."), otherwise the before-its-next-command sentence. For an attempt with no gate the card says "The session ended on its own. Nothing is running.", since it may have run many commands after the press.

`lastSaid` is the newest top-level Claude output line (source `claude`) whose arrival time is at or before the gate's `stop.at`; when the attempt ended without a gate stop, it is the newest such line in that attempt's run. It is omitted when the conversation has none. It is never the run's result text and never an earlier run's message: a turn the gate yields ends with an empty result, and text after the stop comes only from a later turn Claude starts on its own (a background task's completion notice), which is Claude answering the checkpoint. The card shows it as a quotation, shortened with an ellipsis. The eyebrow and the two columns follow AC-PAUSE-05 and AC-PAUSE-06 and the mockup.

## The Paused Page

Replaces in part: `docs/changes/kiln-run-restart/kiln-run-restart-technical-design.md`, §A Held Phase That Can't Be Reopened (for a Pause now hold, the page's header is the Paused header and the page shows no checks).

Replaces in part: `docs/changes/kiln-completion-waivers/kiln-completion-waivers-technical-design.md`, §Display Contract (the hand-back page bullet does not apply to a Pause now hold's page).

The held screen shows, in order of precedence (each replaces what follows it while it applies):

1. Uncertain messages to acknowledge (AC-MSG-05), as today.
2. While pausing: the pausing panel. No terminal command and no resume controls.
3. When the conversation can't be reopened (the hold carries its reopen check): the existing carry-on and fresh-terminal cards, under the Paused header.
4. Otherwise the two columns. **Resume {activity}** calls the existing takeover resume, with `note` when the Note for Claude box has text. The terminal column shows the existing released command and fresh-session disclosure.

Both columns, the command and Copy stay visible from `releasedAt` on, whatever the hold's current state: the snapshot's resume command for a held Pause now is gated on `releasedAt`. An obstacle shows inside the paused page. `terminal_in_use` is a neutral line in the terminal column: "Claude is open on this conversation; exit it, then press Resume." Every other obstacle code is a warning. Resume stays pressable; its refusal keeps its existing code, and the page shows the refusal's reason beside the button. The paused page never renders the recovery page's check error. `kiln status` and session inspection keep `terminal_readiness.ready: false` with the reason while the obstacle lasts.

Resume's answers keep their existing handling: a Resume refusal's reason is shown beside the button; `already_complete` shows the existing advance choice and keeps the note unsent; an advance that then fails its checks shows the existing checks section with Check again and Mark complete. Nothing else adds a checks section to this page (PAUSE-004). Below the columns: a pending end-of-activity pause with its cancel, the full session output link, and the billing, development delivery and reset panels, as today.

The private execution schema does not change version.

## Wording

Replaces in part: `docs/changes/kiln-public-release-readiness/kiln-public-release-readiness-technical-design.md`, §Design Decisions, Compatibility notices row (the `takeover` feature's display name is **Pause now**).

Every place a person reads the action's name says **Pause now**: the pause panel, the unavailable reasons (Codex, preflight, final delivery, message submission pending, unsupported Claude Code, disconnected), compatibility notices (the `takeover` feature's display name), `kiln status` and its help, the bot command contract's descriptive text, the reset explanation, the uncertain-message recovery, the final-delivery notes on the running and session pages, and the README. The Folder missing page's takeover wording stays (Out of Scope).

Strings outside the panel change with it:

- **The checkpoint text Claude reads** (`prompts/takeover-checkpoint.txt`, the deny and stop reason the hook returns): its first and third sentences change and the yield instructions stay word for word. "Kiln paused this activity. Finish no further substantive work. The completed operation and this conversation are saved; the person will resume the unfinished phase or audit work through Kiln or continue it in a terminal. Yield at this completed-operation boundary."
- **Reasons a pausing hold records**: the checkpoint-unavailable text drops "Wait before opening Claude.", the placeholder reasons written at acceptance and after a restart drop their terminal wording, and a gate-less attempt's reason reads "Input connection lost. Pause now waits for this session to end on its own; no forced interruption." in place of "Takeover waits for safe release".
- **Message Claude's unavailable reason while a Pause now hold lasts**, today "Pausing or paused for terminal takeover.", names Pause now: "Pause now is pausing or has paused this activity." The delivery-recovery hold keeps its own reason.

The build's check is a search for "take over" and "takeover" in user-facing strings, each hit either renamed or listed as an intended keeper.

## Integration Points

- **Claude Code hooks:** the existing `PreToolUse` and `PostToolBatch` hooks write the stop and the operation label. No new hook event, no new provider capability.
- **Session adapter drain:** writes the stop when it seals input under a hold.
- **Journal:** one new browser-only action, `cancel-take-over`, reconciled at startup like other live actions.
