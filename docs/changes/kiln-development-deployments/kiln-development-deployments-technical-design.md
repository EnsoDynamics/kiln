**Document-wide supersession:** [Kiln completion checks](../kiln-completion-checks/kiln-completion-checks-technical-design.md) supersedes workspace-confinement auditing, outside-change warnings, related repair prompts and acceptance controls, and persistent phase-verification success notices wherever they appear below. Independent Git, required receipt authentication, launch permission, conversation availability and runtime ownership/cleanup requirements remain in force.

**PRD:** [Kiln development deployments](kiln-development-deployments-prd.md) · **Assumptions:** [AUTH-001 and AUTH-002 settled](kiln-development-deployments-assumptions.md)

## Overview

Superseded in part by: `docs/changes/kiln-completion-checks/kiln-completion-checks-technical-design.md`, §Completion and recovery and §Interfaces and saved records (workspace auditing, confirmation controls and phase success banner only; independent receipt authentication remains).

Add execution-scoped development authorization, a small delivery ledger and a shared evidence-based completion check to Kiln. Sessions continue to own engineering and deployment through each project's documented workflow. Kiln owns the permission snapshot, records intent before delivery, reconciles external facts and explains unresolved results. No new service, database, deployment scheduler or provider credentials are introduced.

## Existing Code

**Posture: Preserve**, the default. Restricted executions retain their existing delivery contract.

- Reuse the foreground engine, instance lock, atomic private JSON store and local authenticated HTTP/SSE interface.
- Extend the per-repository records and checks; keep assigned worktrees and feature branches.
- Reuse Claude transcripts and Codex authoritative conversation-tree evidence; retain each provider's workspace audit and recovery rules.
- Extend external prompt templates, snapshot-driven Svelte screens and terminal events.
- Preserve pause, usage recovery, model/account provenance, historical output and separate Follow-up/running/waiting displays.
- Keep the published Enso Method skills unchanged; Kiln's instructions supply the additional execution contract.

## Authorization and Persistence

Superseded in part by: `docs/changes/kiln-billing-safeguards/kiln-billing-safeguards-technical-design.md`, §Persistent Data and Upgrade (Claude billing safeguards and additive private billing state only).

### Target identity and PRD-scoped choices

New authorization targets are `{ repository: "github.com/owner/repo", baseBranch }`. Normalize GitHub identity case-insensitively and preserve the exact Git branch. Delivery checkpoints retain a separate `{ repository, baseBranch, environment }` identity: the agent reads the actual environment from the versioned project workflow and binds evidence to it. Authorization never asks the person to name or classify that environment.

Before Start, **Allow early merges** is off. Checking it covers every participating repository at its currently configured base branch. Compact read-only cards show **May merge into <repository> / <branch>**; there are no individual selection boxes. The view sends the enabled option without requiring target rows. At Start, after the repository and branch checks pass, Kiln constructs the complete target set from that checked repository list and saves it with the execution grants before workspace/session dispatch. A changed configured base before Start is reflected in the summary and saved target set. A new repository added after Start does not expand that saved authority. Required checks still apply, and the repository’s existing CI/CD may run before the PRD finishes.

Requirements and application code need not share a repository. The checkbox covers all listed repository branches, including a documents-only product repository when listed; storing a PRD there alone grants nothing. Existing started executions keep their exact grants. Nonempty candidates from older unstarted records retain their complete scope, including repository subsets and multiple environments for one branch, unless the person selects the current option anew. Their read-only summary shows only that earlier scope and explains how to select all participating repositories. Toggling off and back on sends an empty candidate set, which Start expands into all configured branch targets. Invalid or mismatched legacy candidates still fail validation instead of granting a different target.

Early-merge choices belong only to the current PRD execution (AC-PERMIT-03, corrected by Doug on 2026-10-30). New PRDs start with `enabled: false` and `targets: []`, including PRDs in the same requirements repository and checkout. The interface has no remember/reuse controls; the API and snapshot expose no cross-PRD preferences. Remove the preference storage module and its reads, writes and locking. Obsolete `development-deployment-preferences.json` files are inert and are never read or written.

When loading existing PRD records, discard the retired `rememberForPrdRepository`, `useSavedTargetsForThisPrd` and `preferenceRevision` metadata. Preserve the current PRD’s effective enabled/target choices, execution grants and delivery history. This compatible normalization keeps the current schema version; retired metadata is omitted on the next normal record write. It never imports choices from another PRD.

### Execution grants

Superseded in part by: [Kiln Continue Added Phases — pending target grants](../kiln-continue-added-phases/kiln-continue-added-phases-technical-design.md#target-grants-before-acceptance), Phase 3b (reserve fresh-execution authority before Continue, adopt its exact grants at activation, and retain replay/supersession through private schema 18; active grants remain separate from resume).

At Start, save an `executionId` and a copy of the effective target grants in the same atomic PRD-record write as the start intent, before setup or session dispatch. A retry after partial setup retains the execution and its grants; any permitted change to an uncreated repository's base invalidates that target and requires reconfirmation before proceeding. Once a session has started, the grant set changes only through the explicit Needs you grant action.

Needs you exposes **Allow early merges** with the same repository cards and disclosure. **Authorize early merges** grants the displayed branch directly; no extra checkbox or environment entry is present. Branches already covered by a branch grant show **Authorized for this run**. A retained environment-limited grant is labeled with its existing scope and may be explicitly broadened using the same branch action. The person submits the exact target and current authorization revision; atomically persist `enabled: true`, the selected branch target and an incremented authorization revision before acknowledging the grant. An identical repeated grant is idempotent, including after restart. The button records authorization but does not silently resume; existing Resume/Check again controls decide continuation. This applies only to the current execution (AUTH-002). A normal settings write, Resume note or repository addition cannot create a grant. Prompts tell agents to request this control when uncovered work is necessary.

First-grant activation retains `developmentAuthorization.activationRecovery: { stoppedPhaseId, phaseIds[], repositoryNames[] }`. Capture completed leaves through the stopped leaf, in plan order, and the already assigned repositories in the same atomic grant write. If the stop occurred before its first provider session, clearing the original blocker launches that stopped leaf/finalization session under the saved recovery scope. The stopped conversation may recover the first unresolved captured leaf; it cannot skip an earlier unresolved obligation or assess future work. A finalization conversation may prepare a criterion-required historical checkpoint within that scope; the final review remainder remains ineligible for merging. Delivery status supplies each recovery leaf's current digest and evidence check. Keep the original stop while these checks are unresolved, rather than creating a new historical phase-completion event. A schema 1–4 execution receives an execution identity on migration when it already started, while its authority remains disabled.

The local API is the existing trusted machine-user boundary, not a new claim that a browser click can be cryptographically distinguished from the user's local agent. Agents receive instructions never to grant themselves permission; the deployment command has no grant operation. Keep provider protections, client-request refusals and branch protections unchanged.

Checkpoint head, target and required evidence form an immutable identity once an operation is prepared. A changed head becomes a new checkpoint; an interrupted attempt retains its identity. References remain after failure so a later pass cannot erase an unfinished obligation. A corrected head may explicitly replace an unsuccessful checkpoint: retain the old attempt and its failures, link `supersededBy` to the replacement, and carry forward its target, criterion obligations and unsatisfied dependencies. Accept the transfer only when Git proves the replacement retains the earlier source work; conflicting targets, a cycle or uncertain coverage remains unresolved. The old obligation is satisfied only when the replacement satisfies it, never when replacement is merely proposed. Confirmed merges remain delivery history even when their failed deployment or verification is completed by a later covering checkpoint. Requirements identify pre-merge checks/reviews and deployment/verification evidence from the project's documented workflow, with repository-relative source paths and revision. Evidence is stored under the execution's private state directory, never in project repositories, and follows the existing owner-managed execution retention without automatic pruning. Older Kiln readers refuse schema 9; rollback must retain a compatible reader or restore an owner-held pre-upgrade record, never lower the schema number. Invalid/unreadable records stop with the offending record named; no empty-history fallback.

## Session Contract and Delivery Interface

### One authority statement everywhere

Superseded in part by: `docs/changes/kiln-completion-audits/kiln-completion-audits-technical-design.md`, §Provider Sessions and Development Delivery (audit task identity and owner scope accompany current authority in resumed and manual recovery; note/workspace-repair precedence remains).

Generate one authorization block from the execution record for initial phases, subsequent sessions, every Kiln-launched resume cause, finalization and fresh-session recovery. It identifies execution, assigned workspaces/feature branch and exact approved targets, the unchanged restricted repositories, and AC-DEV-02/04's boundaries. Explicitly replace the earlier no-PR/no-merge/no-deploy sentence only for the named scope; do not append a grant beside an unconditional prohibition. Resumes of older conversations say this block replaces their earlier delivery restriction for these targets, while preserving all other instructions. User notes remain first, then workspace repair guidance, then the effective authority and remaining task. For a person reopening an existing conversation in a terminal, show only the provider resume command, without displaying or requiring a recovery prompt. This also applies after a grant changes; changed instructions can be discussed directly in the resumed conversation. Retain current-authority prompt generation for Kiln-managed resumes, programmatic handoff information and fresh-session recovery.

Sessions may open/merge a checkpoint only to satisfy an identified PRD criterion needing development delivery. Closing a phase or finishing the PRD is not a trigger. Required pre-merge checks and reviews must pass for the checkpoint head, including human approvals when the project requires them. No administrator override, force push, separate release workflow or checkout switch is allowed. The approved branch’s configured CI/CD is covered without inspecting its production classification. Use ordinary protected GitHub merge operations with the expected head pinned; if that head changes, reassess and recheck before merging. An approval auto-review rejection remains a rejection.

In enabled executions, a session records a delivery assessment for its judged leaf before completion: either required checkpoints with criterion references, or no development delivery required with a short reason. The assessment binds to a deterministic digest of that leaf, governing PRD and design, excluding only mechanical completion metadata (`Closed` lines and acceptance-checkbox ticks); other leaf files are not inputs. Closing work therefore does not invalidate its own assessment or earlier assessments. Requirement wording and technical contracts remain digest inputs. A changed digest requires a new assessment before completion; unchanged obligations may reuse their existing checkpoints and evidence rather than repeat deployment. Retain obligations across document edits. When a phase splits, its session explicitly assigns every inherited required merge and evidence requirement to current descendant leaves using the split assignments. Preserve checkpoint, requirement, dependency and evidence identities and original phase/criterion references; shared evidence may satisfy several assignments, but assignment is not evidence. Each descendant records its own assessment. Apply the same assignment contract whenever a descendant splits again. A missing assessment is unresolved, not “no delivery.” Kiln validates references and evidence mechanically; identifying which business criteria need a deployment remains the engineering session's responsibility, as identifying implementation/test scope already does. Kiln makes no model call to judge completion.

### Small local command/API surface

Superseded in part by: [Kiln Continue Added Phases — pending target grants](../kiln-continue-added-phases/kiln-continue-added-phases-technical-design.md#target-grants-before-acceptance), Phase 3b (reserve fresh-execution authority before Continue, adopt its exact grants at activation, and retain replay/supersession through private schema 18; active grants remain separate from resume).

Add `kiln delivery` as a client of the running execution's engine, using the same workspace-to-instance discovery as `kiln add-repository`. It records and reads facts; the agent still runs `gh`, deployment and test commands. All mutating requests carry `executionId` and expected ledger revision. Reject a stale revision or wrong execution with 409. No generic remote command runner is added.

| Interface | Request and result |
|---|---|
| `POST /api/settings` | Adds the before-Start candidate settings above; changes after Start refused. No cross-PRD preference fields are accepted |
| `POST /api/development-authorization` | Needs you only: `{ executionId, authorizationRevision, target: { repository, baseBranch } }`; returns effective authorization; malformed/empty input 400, stale/wrong state 409, repository/base mismatch 422 |
| `POST /api/delivery/assessment` | `{ executionId, revision, phaseId, documentsDigest, required, criteria, reason, checkpoints, split?: { phaseId, documentsDigest, assignments } }`; atomically records assessment and any split assignments against the current ledger revision and split documents; missing authorization can be recorded as a named blocker |
| `POST /api/delivery/prepare` | `{ executionId, revision, checkpointId, operation }`; reconcile first, check grant/identity/dependencies and the operation's required evidence, then persist intent before returning `{ operationId, disposition: proceed \| already_observed \| unresolved, facts }` |
| `POST /api/delivery/evidence` | `{ executionId, revision, checkpointId, operationId, references[] }`; references are candidate evidence, never trusted success booleans; returns reconciled facts |
| `GET /api/delivery` | Effective authorization, ledger revision, assessments, checkpoint facts and unresolved work |

Assessment validation checks plan/target references and, for a split, complete inherited-obligation coverage, actual descendant leaves, original criteria accounting and prerequisite order. Missing, stale or inconsistent assignments block progression rather than assigning everything to the first child.

CLI subcommands `assess`, `prepare`, `evidence` accept their structured payload as a JSON file; `status` reads the ledger. The command prints the authoritative result and exits nonzero on a refusal/unresolved preparation. Assessment and preparation normally cover only the current session’s judged leaf and assigned repositories; explicit manual recovery uses the stopped leaf. Activation recovery additionally permits that same recovery session to assess and prepare obligations for engine-identified unresolved previously completed leaves, in plan/dependency order. This exception covers no future leaves, new repositories or unapproved targets; all identity, evidence, workspace and authorization guards remain. Preparation is refused while a check/resume is in progress. Existing engine serialization covers state changes; no second execution coordinator is introduced. For merge preparation, the required evidence includes current check results and reviews for the exact head plus any documented pre-merge test results; missing or stale evidence refuses `proceed`. Queue admission may precede queue-specific checks, which GitHub runs on its derived queue revision containing the pinned checkpoint; that admission is pending and cannot satisfy a merge obligation. GitHub enforces its protections again when the agent submits the head-pinned merge. Evidence submission is idempotent by operation/source identity. The browser grant route is not part of this CLI.

An operation already prepared with an unknown outcome never returns another `proceed` merely because the client retries. After interruption the engine first queries the external source or authoritative provider tool history. Only evidence that the operation was not accepted permits another attempt. If the source offers no way to distinguish not-started from accepted, Needs you names that ambiguity; Resume does not clear it. Provider IDs discovered after a crash can be adopted only when repository, target, revision and time/correlation identify a unique matching operation.

All routes retain loopback, Host, Origin and token checks. Each remote read uses the existing bounded helper timeout; the complete reconciliation has a 120-second deadline, including pagination. Exhausting the deadline leaves the unfinished sources unresolved and preserves observed facts; a truncated result never counts as an empty set or a pass. Malformed provider data is unresolved with its source named. A failed private-state write prevents dispatch authorization.

## Evidence and Completion

### Merge, deployment and verification are separate

GitHub and Git facts establish delivery. Read the exact PR number once known; discover interrupted creations using repository, same-repository head branch, base and recorded head SHA across open/merged/closed results, with pagination. An open PR or closed-unmerged PR is never a merge. Capture `headRefOid`, `baseRefName`, `mergedAt`, `mergeCommit` and PR state; check the approved base's actual remote history contains the merge result. The PR's merged head must match the prepared checkpoint. Unexpected new commits or a foreign repository cannot be adopted. Preserve the original source head even when squash/rebase changed commit IDs. A successful merge command that only enabled auto-merge or entered a merge queue remains pending until the PR is actually merged. The merge result is the target merge commit, squash commit or last rebased commit as GitHub reports; it is not necessarily the original feature head. A merge method that cannot be established is recorded as unknown without guessing, while the verified source/result pair remains the coverage proof.

For deployment and verification, accept either of these concrete evidence forms:

- A GitHub workflow run/job, deployment/status or check-run reference, reread through `gh api --hostname github.com` as structured provider data. Resolve the run's actual commit/artifact, destination environment, attempt and result, not just its workflow name or green conclusion. The project's documented workflow mapping must establish which deployment job targets the workflow environment and which tests provide the required verification. A general successful CI run is insufficient.
- A command/tool result from the recorded session's authoritative provider history, with call identity, executed command/arguments, working directory, call/result timestamps, terminal tool outcome and retained output. The provider evidence projection retains those facts and distinguishes a terminal tool-error flag from a numeric process exit code. Use the provider's actual terminal-success signal; never synthesize an exit code or completion timestamp. The documented verification command and its output must identify the workflow environment and the deployed revision/artifact; a pasted log, agent-written JSON or final success prose is insufficient. A missing result, hidden child call or uncertain target/revision remains unresolved. This supports documented project workflows without adding a provider framework.

Each requirement has a stable `id`, `purpose: pre_merge | deployment | verification | current_artifact`, versioned workflow/document source, expected target and revision/artifact binding, plus one of these bounded matching contracts:

| Evidence source | Mechanically checked contract |
|---|---|
| GitHub object | Repository and object kind/ID; workflow path and exact attempt when applicable; required job/check identities; terminal success; deployment environment and revision/artifact link. Read every required job/check, not only the run conclusion. Resolve dynamic destinations or artifact inputs from provider records or a structured status result; workflow names alone supply neither. Skipped/cancelled/pending jobs do not satisfy a required result |
| Recorded command result | Exact documented invocation and working directory, with target/artifact arguments where the command takes them; matching call/result identity and terminal success. A required test result may be the terminal outcome of the exact documented test command. Target/artifact facts not already bound by that invocation or referenced status evidence come from typed JSON output using declared JSON Pointer paths and exact expected scalar values, or from the GitHub object that the command returns. No regex over prose, executable extraction expression or agent-supplied success value is accepted |

This is a fixed evidence matcher, not a plugin or command-execution system. Requirements name source paths/revisions and the expected fields before delivery; opaque output or an unsupported shape is a named evidence gap at Needs you. Command results must come from executing the documented operation or probe, not an `echo`/wrapper that merely prints a claimed result. A successful deploy submission proves acceptance only; completion requires the documented deployment/status evidence. Local verification is allowed; house deployment operations continue through GitHub Actions. Bind deployment to the confirmed target merge result (or a demonstrably containing later revision), and bind verification to the actual deployed immutable artifact; source-head equality alone fails squash/rebase deployments.

Store candidate references and independently resolved facts separately. Normalize both forms to the evidence record, retaining enough raw evidence for the person to inspect the reason. Verification must cover the checkpoint's deployed artifact and every required check, and occur after that deployment. For dependent repositories, bind verification to the prerequisite checkpoints/artifacts too. A failure in a prerequisite blocks dependent verification, without deleting other successful repository deliveries.

A deployment is historical evidence, not a claim that a shared environment stays unchanged forever. Before unfinished dependent verification, reread the environment's current artifact; if it has changed, obtain evidence for the intended work on that artifact or carry out the documented deployment again under a newly prepared operation. An unknown current artifact cannot satisfy the dependency. Already completed verification retains its original time and artifact.

## Continuing the Assigned Branch

Keep the same local feature branch and worktree. After a confirmed merge, the session fetches the approved base without changing another checkout and merges that base into its assigned feature branch, then pushes normally. This makes the delivered base an ancestor for the next PR even after squash/rebase, while retaining original feature commits. Record the synchronization operation and both tips. Do not reset, rebase away accumulated work, delete a branch or force-push. Conflicts are resolved only within the assigned worktree through the normal engineering checks; uncertain or unrelated conflict resolution returns to Needs you.

If GitHub deleted the remote feature branch, the local branch remains the work record. Once synchronization and local identity are checked, the session recreates only that same remote branch with a normal push. A remote name now pointing at unrelated work is a blocker. Until push is confirmed, Pushed still fails. Kiln itself does not mutate Git beyond its established workspace setup.

For remaining-work comparison use the synchronized approved base and current feature head, plus the ledger's covered head/result pairs. Do not use only the original `baseCommit` or assume source-head ancestry in the target proves squash delivery. An empty content delta after synchronization is fully delivered only when ledger coverage accounts for the original source work; synchronization-only commits do not require an empty final PR. Any new content, including phase-document closures, needs its own coverage or a review PR. If a meaningful new commit's delivery cannot be distinguished from coincidentally equal trees, keep it unresolved rather than dropping it.

Before a second checkpoint, reuse only a suitable open PR whose exact current head/base match. A merged PR stays history; create a new PR for remaining changes when needed. Avoid repeated already-delivered content in its diff. Cross-links include earlier merged PRs and present review PRs; the recorded `dependsOn` order comes from the technical design/requirements, and sessions perform needed deployments in that order.

## Phase 1 Interface Details

Initially authorized executions use the schema-5 delivery ledger and the before-Start settings/Start routes. The development-authorization route and activation of existing restricted executions belong to Phase 2 and are not supplied by Phase 1. Cross-PRD preferences were subsequently removed under AC-PERMIT-03.

The authority block pins the running Node executable and Kiln CLI entry point: provider login shells can otherwise select an older globally installed command. Instance discovery reads the private address hint and authenticates the running server with the execution token; the delivery client does not require process inspection inside the provider sandbox. Every mutation validates the complete resulting schema before the atomic save, and rolls back its in-memory transaction on refusal or write failure. Start likewise saves execution identity and target grants before workspace/session dispatch and restores its pre-Start state if that write fails.

Command matcher arguments support `{{sourceRevision}}`, `{{mergeRevision}}` and `{{environment}}`. Typed JSON fields use JSON Pointer keys and exact scalar expectations; `$sourceRevision`, `$mergeRevision`, `$environment`, and `$dependency:<checkpoint-id>` bind values to independently established identities. Pre-merge tests must bind their tested source head through an argument or field, so an old bare test result cannot be relabeled. A current-artifact probe may report `$currentRevision`, an immutable revision read from the environment, including a changed artifact. Such a probe establishes current state and never satisfies deployment/verification by itself. Print/evaluation/extraction wrappers and compound shell syntax are not evidence operations. The versioned source declares each exact invocation and matcher before delivery.

GitHub workflow verification declares exact run attempt, required job names and the actual deployment job. The successful deployment's job URL must match that job in the run for the same artifact/environment; a green workflow with a skipped required job is insufficient. Verification must begin after deployment. A historical successful deployment remains historical proof when a later deployment makes it inactive. Current-artifact probes separately require the latest environment deployment and current successful status. Retained evidence history preserves the original deployment/job association and verification timestamp across subsequent restorations.

Preparation includes optional `operation.requirementIds` to bound split obligations and `operation.restorationFor` to identify an active dependent checkpoint whose verification remains unfinished. A restoration can redeploy only the earlier approved checkpoint's intended artifact after a fresh authoritative probe proves the environment changed. It inherits the dependent verification's active scope, so a later phase can restore a prerequisite without reopening unrelated earlier work. Command probes must postdate the last successful restoration, preventing replay; GitHub probes reread current environment state. Unknown restoration outcomes are reconciled before another intent. Remotely accepted GitHub restorations can be recovered from unique matching SHA/environment deployments created after the saved intent. No deployment is authorized merely to finish a final review remainder.

Assessment supports `split` and atomic `splits[]`, each with phase ID, document digest and assignments (`checkpointId`, `requirementId`, `originPhaseId`, `criteria[]`, `leafIds[]`). Every inherited obligation retains original criterion coverage, nested assignments agree, merge precedes its deployment/verification, and prerequisite completion is assigned no later than dependent delivery. A corrected checkpoint preserves source ancestry, target, checks/review, matchers, criterion obligations and prerequisites; proposing a replacement alone never clears the original obligation.

The single reconciliation deadline also bounds authoritative provider-history reads. Definite latest failures remain blocking alongside historical successful evidence. Delivery status exposes recorded command identities; evidence submissions carry references, never agent-provided outcomes. Read-only prerequisite probe references use `operationId: current-artifact` after preparation requests them. Confirmed operation failure permits a new retained attempt; unknown acceptance does not.
