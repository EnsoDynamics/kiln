Kiln Model Modes

Changes to how Kiln picks models, each from a gap found while using the recommended model for each phase.

Kiln builds a requirements document, which its screens call a PRD, one phase at a time. Today Model defaults gives each phase the model for its tier, every change there applies at once to every requirements document on the computer, and a fallback switch moves work to your other agent only when an account nears its usage limit.

What we’re building

If any of these is wrong, say so before reading on. The rest of this review is detail within them.

  1. You can run a whole requirements document on one model, chosen once on Model defaults for every requirements document, or on Documents found for just one. The recommended model for each phase stays the default. Source · 2
  2. A third fallback setting, For everything, keeps a run off an account you want to spare, while each phase still gets the fallback that fits its tier. Source
  3. The preflight and the pull request session get a row of their own on Model defaults, at medium effort, lighter than the audits. Source
  4. A change on Model defaults takes effect only when you press Save, for every requirements document on the computer or for this one only, and lasts until you undo it. Source
  5. Model defaults gets a clear way back to the requirements document you opened it from, and leaving never drops an unsaved change without telling you. Source
  6. Settings you saved before the upgrade keep their meaning. Source
  7. Whatever the page can save can also be saved from a terminal, and Kiln’s public guide explains all of it. Source · 2

Not included

  • Switching an agent off by name. For everything spares an account when every first choice is on it.
  • A setting that ends on its own, such as one that lasts until a usage limit resets. A change meant for a few days is saved for one requirements document instead.
  • A fallback for the one model.
  • A third agent, or more than one fallback for a row.
  • Changing the models Kiln ships for the three tiers and the audits.

01 / SECTION

One model for everything, or a model for each phase

Model defaults, opened from Documents found or a run’s settings, sets how Kiln picks models. Besides phases and audits, Kiln runs the preflight, the pull request session, a merge session that merges the pull request after delivery, and a push session that pushes the plan when you press Continue.

Key acceptance criteria & mockups

  • One model covers everything that hasn’t started, every phase whatever its tier, both audits, the preflight, and the pull request, merge and push sessions. Source
  • Until you pick, the one model is Claude Code · Opus · high, or Codex · GPT Sol · high on a computer without Claude Code. Source
  • Any choice you changed for one requirements document, on a phase, an audit, the preflight or the pull request, overrides the one model. Every phase still shows its tier. Source

02 / SECTION

The fallback for everything, to spare an account

Each row of Model defaults has a first choice and a fallback on your other agent. Use the fallback decides when Kiln launches a phase, audit or session on its fallback instead of its first choice.

Key acceptance criteria & mockups

  • Use the fallback has three options, “Never”, “When the first choice’s usage reaches” a threshold, and “For everything, until you change this”. Never is selected until you save another. Source
  • For everything launches each phase, audit and session on its fallback without checking usage, and never on the first choice. Source
  • At a usage limit the run waits for the fallback’s account. If it can’t be used otherwise, such as an agent not signed in, the run stops or Start stays unavailable. Source
  • One model ignores the fallback setting, even For everything, so picking it on a requirements document meant to spare an account runs everything on the one model. At a usage limit the run waits. Source

03 / SECTION

A lighter row for the preflight and the pull request

The preflight checks access before the first phase, and the pull request session opens the pull request at the end. Both run today on the Audits row at Opus high. Their new row starts at Claude Code · Opus · medium, with Codex · GPT Sol · medium as its fallback.

Key acceptance criteria & mockups

  • To change the new row for one requirements document, press Change beside the preflight or the pull request in the plan, before it starts. Source
  • If you had changed the Audits row for every requirements document, the new row starts from your Audits choices after the upgrade, not Kiln’s. Source
  • An Audits choice you had changed for one requirements document stays on its preflight and its pull request, merge and push sessions that haven’t started. Source

04 / SECTION

Save on purpose, for every requirements document or for this one

A requirements document’s own settings are a copy of everything on Model defaults, kept for that one document. The save bar offers Every PRD on this computer, which changes your defaults, and This PRD only, which gives the document its own settings.

Key acceptance criteria & mockups

  • Every PRD on this computer is selected to start, except on the page of a requirements document with its own settings, where This PRD only is. Source
  • A change saved for every requirements document doesn’t reach the others that have their own settings. Source
  • Use my defaults here ends a requirements document’s own settings at once, without a Save, unless the page has unsaved changes. Then the save bar says to save or discard them first. Source

05 / SECTION

One model for one requirements document, from Documents found

Documents found is where you check a requirements document before Start, and the run’s settings are where you adjust it while it runs. Both show the same two choices, with One model for this PRD in place of one model for everything.

Key acceptance criteria & mockups

  • A choice made there takes effect at once, without a Save, and changes nothing for other requirements documents or your defaults. Source
  • In a run underway, the choice reaches every phase, audit and session that hasn’t started. Source

SAVE-003Confidence: 90%Impact: MediumNo reply needed

Does a change saved for one requirements document still apply after Kiln stops, restarts or is upgraded?

Yes. They stay through Ctrl+C, a restart or an upgrade, until you choose Use my defaults here or reset Kiln for the document, which clears everything Kiln holds for it. Ending at a restart would quietly put the remaining phases back on the account you meant to spare.

Details and optional reply

Kiln keeps them outside the repository, so there is nothing to commit.

If you choose otherwise: Its own settings would end when Kiln stops. After a restart the requirements document would follow your defaults again, so a run picked up afterwards would go back to the account you meant to spare.

On 26 November you asked whether a change for one requirements document could just live in memory and be lost on Ctrl+C, partly so that no file would need a gitignore. Kiln keeps a folder for each requirements document outside every repository, so no such file arises. The case you raised lasts days. Of the 20 runs Kiln has recorded on this computer, 12 spanned more than a day, and each of Kiln’s 12 releases from 4 to 21 November meant a restart to upgrade. If they stay when you wanted them gone, Documents found says the document has its own settings, and one click ends them.

When you save for every requirements document from the page of one that has its own settings, does only what you changed go to every document?

Yes. Say Customer returns has its own settings, including the fallback for everything. From its page you change the demanding phases’ model and save for every requirements document. Every document gets the new model, and only Customer returns keeps the fallback for everything.

Details and optional reply

Only what you changed goes into your defaults and into this document’s own settings. The rest of its own settings stays its own, so you can’t make one document’s settings everyone’s defaults in one go from its page. Restore Kiln’s defaults, saved for every document, still restores all of your defaults.

If you choose otherwise: Saving for every requirements document would make the whole page, as shown, your defaults, and the document would lose its own settings and follow those defaults.

On 26 November you asked that a change meant for a few days not be permanent. Saving the whole page would make one document’s temporary settings, such as the fallback for everything, every document’s default. Kiln already treats one document’s changes this way. A phase’s model changed with Change outlasts any change to your defaults, and your defaults record only the settings you actually changed.

When a choice on Documents found makes a requirements document’s settings the same as your defaults again, does it go back to following them?

Yes, when nothing else differs. The notice that it has its own settings goes, and later changes to your defaults reach it. If your defaults changed while it was on One model, it keeps its own settings until Use my defaults here.

Details and optional reply

That gap matters when the change was the fallback for everything. A document on One model at the time keeps its old settings when switched back, so it runs on the account you meant to spare, though Documents found does say it has its own settings.

Picking One model on Documents found or in the run’s settings gives the document its own settings at once. If they differ in anything else, such as the fallback for everything saved earlier for this document only, they stay, and only the choice you made changes.

If you choose otherwise: Switching back to Recommended would keep the document’s own settings, by then a copy of your defaults, so later changes to your defaults would not reach it until Use my defaults here.

You wanted a change for a few days not to be permanent, and the screens as simple and intuitive as possible (26 November). Keeping its own settings would show the notice just after you picked the default. Against it, on 26 November you agreed that choices on Documents found apply as that document’s own settings until you return it to the defaults, and picking Recommended there is itself that return. Kiln’s undo for one phase’s model works the same way.

When a Kiln update changes the model Kiln recommends for a row you never changed, does a requirements document with its own settings get the new model too?

Yes, as in every document that follows your defaults, while what you saved never changes. The risk is a release that swaps a row’s models between Claude Code and Codex, which under the fallback for everything would launch that row on the account you meant to spare.

Details and optional reply

Its own settings keep only what you set, meaning what you saved for the document and what you had set in your defaults when it got them. Any other row follows Kiln’s current recommendation, and the changelog announces any change to it.

The suggested one model works the same way. Until you pick one, it is Claude Code · Opus · high, or a Codex model on a computer without Claude Code, so installing Claude Code later switches it, in a document with its own settings too.

For example, Customer returns has its own settings, with a model you chose for its demanding phases. A Kiln update recommends a newer model for mechanical phases, a row you never changed. Its mechanical phases start on the new model, as every other document’s do, and its demanding phases keep the one you chose.

If you choose otherwise: A requirements document’s own settings would freeze Kiln’s recommended models as they were when it got them, until Use my defaults here.

You treated the recommended models as Kiln’s to keep current, saying most people won’t need to override the tier table (22 November), and you wanted a document’s own settings to be temporary (26 November). Your defaults already keep only what you set, so a release can ship a new recommended model without overwriting anyone’s choice. Against it, on 26 November you agreed that a document with its own settings keeps a copy of the whole page and that later changes to your defaults don’t reach it. Read literally, that copy would freeze Kiln’s recommended models too, though the changes it kept out were yours, and they stay out.
