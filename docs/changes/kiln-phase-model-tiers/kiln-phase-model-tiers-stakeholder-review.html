Kiln Phase Model Tiers

The model choice moves from one setting for a whole requirements document to one for each phase, with an optional way round usage limits.

Kiln builds a requirements document, which its screens call a PRD, one phase at a time on Claude Code or Codex, using one agent, model and effort you choose for the whole document; at a usage limit the run waits for the reset, which can take hours or days. The Enso Method's phase split already rates each phase's build demanding, standard or mechanical in its phase document, but Kiln doesn't read that rating yet.

What we’re building

If any of these is wrong, say so before reading on. The rest of this review is detail within them.

  1. Kiln picks each phase's agent, model and effort from the rating in its phase document, so by default the strongest model, with the tightest usage limits, goes only to demanding phases. Source · 2 · 3
  2. Which model each rating gets is one setting for every requirements document on that computer, on a Model defaults page you rarely need to open. Source
  3. A phase or audit that has started, meaning the model has answered it at least once, finishes on the agent, model and effort it started on, waiting out any usage limit. Source
  4. Every row of the plan shows what it will run on, is running on or ran on, and you can change any phase that hasn't started. Source
  5. If you turn on the fallback switch, Kiln starts the next phase, audit or other session on your other agent when the account it would use is nearly out, and says so on its row and on the current step's panel at the top of the run. Source
  6. The single model choice for a whole requirements document goes away, though a document already underway before this change keeps its saved choice for what it has left. Source

Not included

  • Changing the Enso Method, or Kiln rating a phase or judging a rating. The method's phase split writes the rating; Kiln only reads it.
  • One control that sets every phase of a requirements document at once, before Start or during a run. Change each phase, or change Model defaults for everything.
  • A fallback to a lighter model on the same account.
  • Spending limits. The fallback changes which account a phase uses, not how much it may use.

01 / SECTION

Each phase's rating and model in the plan

Documents found is where you check a requirements document before Start; during a run, the same phase plan shows progress. Each phase's rating and its short reason come from the rating line in its phase document.

Key acceptance criteria & mockups

  • A phase whose document has no rating, or one Kiln can't read, shows Not rated and runs as a standard phase. Source
  • Until a phase starts, Kiln rereads its rating, so an edited rating, or a phase added during the run, takes effect. Source
  • A phase you change is marked Changed by you and keeps your choice, whatever its rating or Model defaults later say, until you press Use the default. Source

02 / SECTION

Model defaults: the models behind each rating

Model defaults is a page of its own, linked from Documents found and a run's settings. Each row has a first choice and a fallback, always on the other agent, used only when the fallback switch in the next section is on.

Key acceptance criteria & mockups

  • Out of the box, demanding phases run on Claude Code · Fable · high, standard on Opus · medium, and mechanical on Sonnet · high. Source
  • The audits, the preflight and the closing session that opens the pull request share the Audits row, Claude Code · Opus · high. Source
  • Their fallbacks are on Codex: GPT Astra · high for demanding, GPT Sol · high for standard and mechanical, and GPT Sol · extra high for audits. Source
  • Each default names a model family, such as Opus or GPT Sol, and Kiln launches its newest version each time, not one fixed when you set it. Source
  • You can also change the Audits choice for one requirements document, in Documents found, the run's settings or on an audit row. Source
  • A change here reaches every phase and audit that hasn't started, in every requirements document, runs underway included. Source
  • On a computer with only Codex, you can start without visiting this page: each phase and audit runs on its row's Codex fallback. Source
  • Nothing here is browser-only: model changes in a run underway and every Model defaults setting have terminal commands, so a script or chat bot can make them for you. Source · 2

03 / SECTION

Start on the other agent when usage is nearly out

Each agent account has usage limits, such as a five-hour and a weekly window, which Kiln's account panel shows as a percentage used. The threshold is the percentage at which a limit counts as nearly out.

Key acceptance criteria & mockups

  • The switch, on Model defaults, covers every requirements document on the computer, runs underway included; no document has its own. Its threshold starts at 95%. Source
  • Weekly limits count as well as five-hour ones. A limit for a different model only, such as a Sonnet-only weekly limit, doesn't count when Opus is about to run. Source
  • Each launch is decided afresh, so once the first choice's account is back under the threshold, the next phase returns to it. Source
  • Only a usage reading sends work to the fallback. A refused model, a sign-in problem or an error never does. Source
  • A phase you changed falls back like any other, unless you moved it onto the fallback's agent; then it has no fallback and runs as if the switch were off. Source
  • If usage can't be read, or the fallback can't be used, the phase starts on its first choice; when the fallback can't be used, its row says why. Source
  • The next phase or audit's row warns ahead of time that it will start on the fallback if usage is still over the threshold then. Source

04 / SECTION

When an agent or model can't be used

Before Start, Kiln checks that each agent the run may use is ready: installed, signed in and, for Claude Code billed through an API key rather than your subscription, approved by you.

Key acceptance criteria & mockups

  • If an agent a phase or audit will run on isn't ready, Start is unavailable, and the message names the work that needs it. Source
  • If only the fallback's agent isn't ready, Start stays available, with a warning that the run will wait at a usage limit instead. Source
  • If the account won't run a phase's model, the run stops before the phase starts and says where to change the model. Source

05 / SECTION

Requirements documents set up before this change

Before this change, each requirements document saved one agent, model and effort, and Kiln filled in Claude Code · Opus · medium, or on Codex GPT Sol at high, in any version, when you didn't pick a model.

Key acceptance criteria & mockups

  • A document not yet started takes its models from the ratings, unless its saved choice differs from what Kiln filled in; then that choice is kept. Source
  • A kept choice shows as Changed by you on each row, and Use the default returns that row to its rating's model. Source

Raise only the audits' fallback to extra high effort, leaving the phases' fallbacks at high?

Yes. When an audit runs on the fallback, extra high spends more of the Codex account's usage on it in return for more thorough checking.

Details and optional reply

If you choose otherwise: Two other answers: every GPT Sol fallback at extra high, standard and mechanical phases included; or the audits' fallback at max, the highest effort, instead of extra high.

On 22 November you confirmed Opus at high for the audits, then added that the backup for GPT Sol should maybe be very high effort. We read the backup as the audits' fallback, since it came in your answer about the audits, and very high as extra high, the effort one step above high. On 21 November you paired Opus at medium with GPT Sol at high; the audits raise Opus one step, so one step above high keeps that pair even. Against it: GPT Sol is the fallback on three rows, and the backup for GPT Sol could mean all three. Max, the highest effort, is also above high.

KEEP-003Confidence: 90%Impact: LowNo reply needed

When a requirements document set up before this change has finished and is continued with added phases, do those phases take their ratings' models, unless you had picked one?

Yes, as for a document not yet started. One exception: if you had picked exactly the model Kiln fills in, Kiln can't tell your pick from its default, so the added phases take their ratings anyway.

Details and optional reply

Continue is how you add phases to a finished requirements document. The audits after the added phases take the Audits choice.

If you choose otherwise: Every added phase runs on the document's old single choice and shows Changed by you, whatever its rating; you press Use the default on each row to get the ratings.

Without this, a document set up the day before the upgrade would run its added phases on one model, while one set up the day after gets ratings. You decided that a requirements document already underway keeps its old choice for everything it has left. A finished one has nothing left, and its added phases have run nothing, so moving them undoes no work. Against it: Continue, written when one choice covered the whole document, says continuations use the existing model settings.
